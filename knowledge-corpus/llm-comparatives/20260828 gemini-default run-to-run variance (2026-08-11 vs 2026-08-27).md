Same commit, same contracts, same config, same model — two different outputs

Both runs used `gemini-default` against the identical source commit (`1aa319b1`, confirmed via `git ls-remote` before the second run) and identical contract/config files (confirmed via `git diff 8601f4e..HEAD -- pipeline/firebase-oskey-dev/phase-02-inter-module-synthesis/contracts/ config/llm-providers.json` — zero changes, and no uncommitted local edits either). The only variable between the two is time and whatever stochasticity comes from `temperature: 0.2` (not 0) on the reduce/connective calls. This document exists because that variable alone produced differences large enough to matter for how the original core/access_control_device thinness finding should be read.

Citation counts swung by double digits in both directions, module by module

Citation count (verified inline evidence references in the final module profile) is the most concrete, deterministic-adjacent proxy available for output depth, since it's mechanically extracted and validated against real facts by `_shared/citation-validator.ts`, not eyeballed. Comparing old (2026-08-11) → new (2026-08-27) run:

core: 66 → 123 (+86%). supplier: 40 → 66 (+65%). apps: 51 → 77 (+51%). call: 31 → 36 (+16%). tasks: 19 → 21 (+11%). access_control_device: 30 → 33 (+10%). admin: 126 → 136 (+8%). user: 258 → 256 (-1%). building: 262 → 252 (-4%). settings: 103 → 98 (-5%). organization: 272 → 232 (-15%). unit_management: 35 → 25 (-29%).

Verification rates stayed comparably high in both runs (97-100% verified, low single-digit line-unverified counts, zero fabricated/file-not-found in either) — this is a depth/detail swing, not a quality collapse in either direction.

core specifically got dramatically deeper, and the mechanism is visible in the document structure, not just the citation count

Comparing section headers directly: the old run's core profile groups its Section 3 (Primary Responsibilities) into six generic, cross-cutting buckets — "Firestore Document Orchestration," "Pub/Sub Message Ingestion & Routing," "Secret & Cryptographic Key Management," "Structured Logging," "Image Processing & Storage" — none of which name the `access` capability (743 facts, the single largest pack in the whole repo) directly. The new run's Section 3 instead surfaces six subsections specific to `access`'s actual internals: "Access Orchestration & Provisioning," "Alphanumeric PIN Code Generation & Validation," "Asynchronous Edge Synchronization (Pub/Sub)," "Access Update Propagation," "Pincode Lifecycle & Trash Management," "Access Validity & Recurrence Parsing" — and Section 4 names five distinct service classes (`OSKAccessController`, `OSKAccessService`, `OSKPincodeService`, `OSKAccessMessagePublisherService`, `OSKAccessUpdateService`), matching almost exactly the "~5 distinct services" the original 2026-08-11 handover speculated existed inside `core/access` from citation evidence alone, without ever actually surfacing them as named sections. Same underlying capability-synthesis input (unchanged facts, unchanged capability-pack content) — the difference is entirely in how the reduce step chose to organize and elaborate on it.

access_control_device shows the identical pattern, smaller in magnitude

Old run groups its public interfaces into three generic buckets ("Document Controllers," "IoT API Controllers & Services," "Business Services") and one generic "Firestore Paths Touched" list. New run names eight individual controller/service classes and six individually-labeled Firestore paths. Consistent with the citation count only growing modestly here (+10%, vs. core's +86%) — the shift is real but smaller.

Repo-report treatment of both modules changed shape, not just depth

The 2026-08-11 report gave `core` a dedicated SPOF risk item built from the deterministic dependency graph ("1,422 inbound edges from 11 of 12 modules"). The 2026-08-27 report doesn't repeat that specific framing — instead it surfaces a circular-dependency risk between `core` and `building`/`user` (47 edges each direction), a different but comparably substantive finding built from the same underlying graph data. `access_control_device` gets real, specific treatment in both: the new report gives it its own subsystem grouping (with `call`) and a genuine security finding (Firestore rules allow any authenticated user to read/write `/accessControlDevices`, no tenant isolation) not present in this exact form in the earlier summary reviewed for the original complaint.

One reliability note, likely unrelated to the above but worth carrying forward

`building`'s final reduce/assembly call (11 capability syntheses, the largest single reduce input in the 2026-08-27 run) failed 3 times with a generic `fetch failed` network error before succeeding on a 4th identical attempt — a 75% failure rate on the single largest call in the pipeline, while every other module's reduce call (including `organization`'s 14-pack reduce, larger than `building`'s 11) succeeded within one or two tries. `_shared/llm-adapter.ts`'s `callGemini()` sets no explicit request timeout. Not confirmed as the cause, but worth checking independent of anything else in this document.

Bottom line for the capability-pack-size-cap discussion (Plan 05)

The original 2026-08-11 finding — `core` and `access_control_device` reading thin relative to other modules — was real for that specific run. But this same-commit, same-contract, same-config re-run shows swings of comparable or larger magnitude (up to -29% to +86%) across modules that were never flagged as a problem, `core` included when measured the other direction. A single run's density numbers are not strong enough evidence on their own to conclude the partitioning mechanism (one LLM call per capability pack, regardless of size) is the dominant cause of any one module reading thin — run-to-run generation variance on the reduce step appears to be at least as large an effect. This doesn't mean the size-cap concern is wrong (the fact-count asymmetry across packs is real and structural, unaffected by any of this), but it does mean the urgency case built on the original single-run density comparison is weaker than it looked, and a decision to invest in the partitioning fix should probably wait for either multiple runs averaged together or a different, run-independent signal.
