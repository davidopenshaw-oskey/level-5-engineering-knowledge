# Knowledge Pipeline Design Journal

## Purpose

This document records the evolution of the Oskey Knowledge Pipeline.

It is **not** part of the knowledge corpus consumed by AI. Instead, it captures the architectural decisions, trade-offs and lessons learned while designing the pipeline.

The objective is that, six months or two years from now, anyone joining the project can understand not only *what* was built, but *why* it was built this way.

---

# Original Objective

The original objective of the project was to improve the quality of AI-generated Atomic PRDs.

Very quickly it became apparent that the real problem was not PRD generation.

The real problem was the absence of a trustworthy, maintainable engineering knowledge base describing the existing Oskey platform.

Atomic PRDs therefore became one possible output of a much larger knowledge platform.

---

# Evolution of the Approach

## Phase 0 – Manual AI Interpretation

The first approach relied heavily on Gemini reading the TypeScript codebase directly.

The workflow was approximately:

Source Code

↓

Gemini Analysis

↓

Engineering Descriptions

↓

Reads / Writes / Fan-Out Analysis

↓

Workflow Catalogue

↓

Workflow Documents

This produced useful documentation but had several limitations:

* prompt dependent
* difficult to regenerate
* difficult to maintain after code changes
* interpretation mixed with extraction
* limited traceability back to the source code

---

## Phase 1 – Deterministic Evidence Pipeline

The project evolved towards separating extraction from interpretation.

Instead of asking an LLM to understand the repository, deterministic tooling extracts engineering evidence directly from the source code.

Current pipeline:

01 Scan Repository

↓

02 Extract AST Evidence

↓

03 Build Module Evidence

↓

03 Build Evidence Graph

↓

04 Benchmark

Characteristics:

* deterministic
* repeatable
* regenerable after every merge
* suitable for CI/CD
* evidence can be diffed between commits
* evidence remains independent of any AI model

The output of this phase is an **Evidence Corpus** rather than documentation.

---

# Key Architectural Decision

Separate **facts** from **knowledge**.

Facts are generated deterministically.

Knowledge is generated later by AI.

Example:

Evidence

* Firestore collections
* Services
* Controllers
* Dependencies
* Permissions
* Call graph
* Exports
* Methods

↓

Knowledge

* Engineering Maps
* Architecture Guides
* Workflow Catalogues
* Workflow Documents
* Impact Analysis
* Onboarding Guides
* Atomic PRDs

This separation significantly reduces hallucination risk because AI no longer attempts to discover engineering facts directly from source code.

---

# New View of the Project

Originally this project appeared to be documentation generation.

It has evolved into an AI Knowledge Platform.

The evidence graph becomes the canonical engineering truth.

Documentation becomes one of many possible projections of that truth.

---

# Knowledge Projections

The same evidence corpus should eventually generate:

* Engineering Module Profiles
* Enterprise Architecture
* Workflow Catalogue
* Workflow Documents
* Impact Analysis
* Developer Onboarding Guides
* QA Guides
* Atomic PRDs

Each projection is generated from the same deterministic evidence layer.

---

# Relationship to Existing Documentation

Previous documents such as:

* Oskey Backend Services & Data Architecture
* Oskey Workflow Catalogue
* Individual Workflow Documents

remain valuable.

However, they should now be viewed as **knowledge products**, not as the primary engineering source of truth.

The new deterministic evidence corpus supersedes the earlier AI extraction process.

Future versions of these documents should be regenerated from the evidence corpus rather than manually maintained.

---

# Current Architectural Principle

The pipeline is divided into two distinct responsibilities.

Evidence Generation

* deterministic
* repeatable
* no interpretation
* no hallucination

Knowledge Generation

* AI assisted
* evidence-backed
* traceable
* regenerable

This separation is considered one of the most significant architectural improvements made during the project.

---

# Long-Term Vision

The Engineering Corpus is only one corpus within a larger enterprise knowledge platform.

Future corpora may include:

* Engineering
* Operating Model
* Product
* Sales
* Marketing
* Competitive Intelligence

All corpora contribute to a common enterprise knowledge platform.

Atomic PRDs are therefore viewed as one downstream consumer of the knowledge platform rather than the primary objective.

---

# Current Thinking

The next phase of the project is no longer engineering extraction.

The extraction problem is largely solved.

The next phase is **Knowledge Generation**, producing evidence-backed knowledge projections such as Engineering Maps, Architecture Guides and Workflow Catalogues.

Only after those projections exist should Atomic PRDs be considered a downstream product.
