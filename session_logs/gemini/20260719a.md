1. High-Level System Understanding
My understanding is that the Oskey Platform is a secure building access system composed of three main pillars:

Mobile Applications (iOS/Android): For residents and guests to gain access via Bluetooth (SecureBLE) or PIN codes, and to manage their unit (e.g., invite guests).
Access Control Devices (ACDs): Physical hardware (Intercoms and Digicoms) installed at entry points that validate credentials and synchronize with the cloud.
Property Manager Portal (PGO): An Angular-based web app for administrative staff to manage buildings, devices, and residents.
The system's backend is built on Google Cloud Platform, primarily using Node.js for its serverless functions (cloud-oskey-io repository) and a separate Node.js middleware layer (node-iot-api-oskey-io) for hardware integration.

2. Core Architectural & Data Principles
From the architectural documents, I've identified several key design principles:

Hybrid Database Model: The system uses a dual-database approach.
Firestore: Acts as the primary system of record and authoritative source for all business entities (users, buildings, roles, access rules). It is consumed by the client-facing backend services.
MongoDB: Serves as a denormalized, read-optimized projection of the Firestore data, specifically for consumption by the physical hardware (ACDs). This decouples the high-traffic hardware polling from the primary business database.
Event-Driven Synchronization: Changes in Firestore do not directly trigger hardware updates. Instead, they publish messages to Google Cloud Pub/Sub. The node-iot-api-oskey-io middleware consumes these messages, transforms the data, and updates the MongoDB projection, which the ACDs then poll for updates.
Data Hierarchy: The platform enforces a strict, five-level data hierarchy to model real-estate assets and enforce security boundaries: Organization > Entity > Property > Building > Unit.
Offline-First Hardware: The ACDs are designed to function offline. They cache all necessary data (PINs, cryptographic keys) locally and validate access without requiring a real-time cloud connection for every entry event. They synchronize opportunistically when a user interacts with them.

4. Core Workflow Synthesis
My understanding of the key system workflows is as follows:

Access Provisioning (OSKAccessService): This is a central orchestration workflow. When access is granted (e.g., a new inhabitant is added), this service:
Generates a unique PIN code via OSKPincodeGenerationService.
Creates "paired" pincode documents in both the user-centric (/users/{id}/pincodes) and building-centric (/buildings/{id}/pincodes) collections for optimized lookups.
Creates denormalized access ledger entries in /users/{id}/accesses and /buildings/{id}/accesses.
Publishes an "access intent" message to a Pub/Sub topic, which triggers the synchronization to the physical hardware.
User Onboarding:
A Property Manager creates a resident record in the PGO, triggering an automated email with an activation code.
The user downloads the app, registers with Auth0 (verifying email and phone), and enters their name.
The backend attempts an Automated Match: If the verified email/phone match the PGO record, the user is automatically linked to their unit.
If the match fails, the user is prompted for the Manual Activation Code from the email to complete the link.
Upon successful linking, the temporary onboardingInhabitants document is consumed and deleted.
