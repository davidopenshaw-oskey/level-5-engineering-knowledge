# ADR-009: Skill+Template Separation Confirmed by External Precedent, and the Real Refinements Testing It Surfaced

## Title
**The ADR-007/008 skill (persona) + template pairing is confirmed by real, primary-source external precedent — and real testing against a second repo and two independent interactive MCP clients surfaced concrete, evidence-backed refinements (per-section strictness, an honesty-about-gaps marker, bounded search effort, evaluation-driven development) not yet built.**

## Status
**Proposed — direction confirmed by real external research and real internal testing; the refinements below are not yet decided which to build first, and no code beyond the skill+template relocation itself has changed as a result of this ADR.**

## Date
2026-09-09

---

## 1. Context

### 1a. What ADR-007/008 proposed, and what had never actually been tested about it

ADR-007 proposed replacing hardcoded pipelines with a generic MCP tool layer plus task-specific agent personas — direction only, agreed 2026-09-06, not yet implemented at the time. ADR-008 proposed a closed `SectionContent` kind system plus template-driven headings with code-enforced conformance/fabrication checks — validated against one real document type (the atomic PRD) and two known business questions (Q1a/Q1b). Neither had been tested against a **second** real document type, a **second** repo with a fundamentally different extraction pipeline (Kotlin, not TypeScript), or an **interactive** MCP client outside this project's own scripted harness.

### 1b. What real testing this week (2026-09-08/09) actually did

- Verified the relocated `mcp-server/` (ADR-007 §2 point 2) reproduces pre-move data, both as direct function calls and over the real MCP protocol (`governance/roadmap/mcp-direction/25-...md`, `27-...md`).
- Ran the full skill+template+tool workflow through two independent interactive MCP clients (VS Code Copilot, Google Antigravity) — Antigravity's run independently verified against live Postgres with zero fabrication (`28-...md`).
- Ran the same pipeline against a brand-new Kotlin repo (`android-intercom-oskey-io`) for the first time, surfacing and fixing (with a peer session, coordinated via cross-session messaging) two genuine extraction bugs and a real description-enrichment mislabeling — none of it a persona or tool-layer problem (`governance/roadmap/android-intercom-oskey-io/16-...md`, `17-...md`).
- Found and fixed three distinct real shapes of the same underlying citation-fabrication weakness (`23-...md`, `24-...md`, `31-...md`), and found a real, structural Vertex AI quota ceiling that is a genuine, separate operational blocker (`30-...md`).
- **Physically relocated the skill+template pair** from two scattered locations (`governance/roadmap/mcp-direction/atomic-prd-agent-skills.md`, a roadmap/decision folder; `mcp-server/agent-poc/templates/atomic-prd.template.md`) into one canonical home, `mcp-server/skills/prd/{skill.md,template.md}` — the first real, physical step toward ADR-007's own claim that "a new task type costs a new persona file, not new code," making the structure ready for a second real pair (e.g. `mcp-server/skills/impact-analysis/`) without yet building one.

### 1c. Real, primary-source external validation, found via commissioned market research (`governance/roadmap/market-research/21-findings-agent-prd-template-vs-dynamic-structure-2026-09-09.md`), not asserted

- **The skill+template pairing itself is Anthropic's own documented, named pattern**: Skill-authoring best practices (`platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices`, fetched and read directly) describe `SKILL.md` holding process instructions and separate reference files holding output templates, explicitly kept apart — "Organize this so the table schema is in a separate reference file" is their own worked authoring example.
- **GitHub spec-kit** independently mirrors the same shape at the project level: `memory/constitution.md` (persistent principles) kept separate from and referenced by the per-feature `spec.md`/`plan.md`/`tasks.md` templates.
- **Cognition (Devin)** runs two deliberately different real products at different points on the fixed-vs-dynamic-structure spectrum — fixed schema for ticket-scoping, fully agent-determined structure for its DeepWiki docs, per-repo — real, shipped evidence this is a dial matched to task stakes, not a settled either/or.

Nothing in this research suggests the architecture direction was wrong. It suggests the *rigidity* of the current single template (borrowed wholesale from traditional human-PM PRD sections, by this project's own deliberate admission — "old fashioned sections... a way of kick starting") is the real, next thing to revisit, not the pairing itself.

## 2. The real, concrete refinements this surfaced — none yet built

1. **Anthropic's "degrees of freedom" framework** (high/medium/low, matched to task fragility — "an open field" vs. "a narrow bridge with cliffs on both sides") — a real, adoptable answer to how strict any given *section's* own instructions should be, applied per-section rather than per-document-type. Directly informs which parts of a PRD should stay agent-determined ("Technical Proposal") versus bounded/consistent ("Acceptance Criteria").
2. **GitHub spec-kit's `[NEEDS CLARIFICATION: specific question]` inline marker**, with a zero-tolerance quality gate ("No `[NEEDS CLARIFICATION]` markers remain") before a document is considered finished — the honesty-about-gaps mechanism this project's own real developer-perspective review of a generated PRD (the intercom home-button case) showed is currently missing: the model silently under-delivered on the one mechanism the business request actually hinged on, rather than saying so. Cognition's own reported (unaudited, no published methodology) 2x correlation between a green confidence signal and merged-PR likelihood is the one piece of evidence found that this class of mechanism affects real downstream outcomes, not just document tidiness.
3. **Anthropic's own recommended "evaluations before documentation" methodology** — three real scenarios, an `expected_behavior` checklist, a measured baseline before iterating — a real, borrowed methodology for the `mcp-server/gold/` set already started this session, rather than inventing comparison logic from scratch.
4. **Kiro's EARS acceptance-criteria notation** (`WHEN [condition] THE SYSTEM SHALL [action]`) as a real, more testable alternative to today's freeform Acceptance Criteria bullets — would likely have made the intercom PRD's unverified "pressing a button triggers a call" claim visibly incomplete rather than quietly assertable.
5. **A real pairing found through this project's own testing, not the external research**: a bounded-search-effort rule (stop searching one specific sub-question after a small, fixed number of attempts) belongs alongside the `[NEEDS CLARIFICATION]` marker, not instead of it — traced directly from why the intercom business request's own test runs spiralled into 47+ tool calls and a real Vertex AI rate-limit crash while chasing evidence for a mechanism that (per a later, separate finding) doesn't structurally exist in the form being searched for. One bounds the process; the other reports honestly when the bound is hit without an answer.

## 3. Relationship to prior ADRs

- **Confirms ADR-007's core claim** ("a new task type costs a new persona file, not new code") with the first real structural step toward testing it — the skill+template relocation — though a genuine second pair (e.g. impact-analysis) has not yet been built to actually prove the claim end-to-end.
- **Confirms ADR-008's `SectionContent`/template architecture** with real, primary-source external precedent it did not have when written, and surfaces that the architecture's own extensibility (arbitrary headings/kinds per template, no code change) is real and unused beyond the one bootstrap template.
- **Does not resolve**: whether to adopt EARS notation (a real schema-level decision, not just wording), whether `[NEEDS CLARIFICATION]` should be a soft persona instruction or a code-enforced gate (same fragility question this project has asked of every prompt-only rule so far), or whether the bounded-search rule needs real code-level enforcement (a per-sub-question attempt counter) versus persona wording alone.
