# ADR-008: A Closed `SectionContent` Kind System, Code-Enforced Validators, and a Structured Audit Trail for Agent-Persona Output

## Title
**Within ADR-007's agent-persona architecture: define document output as a small, closed set of composable `SectionContent` kinds (not per-document-type bespoke schemas), move mandatory safety checks (fabrication, template conformance) into code rather than persona-prompt text, and persist output metadata as structured data alongside rendered markdown.**

## Status
**Proposed — direction settled across a real, cross-session design discussion 2026-09-06. No implementation started.** Downstream of, and scoped entirely within, ADR-007 (the MCP tool layer + agent persona architecture) — this ADR is about the shape of what a persona *produces*, not the tool layer itself. **Decision A (§4) is now answered directly by the user, 2026-09-06**: not "ship on today's hardcoded schema," but move straight to the `SectionContent` migration and leave the current `OUTPUT_SCHEMA` behind — implementation of this ADR's Direction (§2) is the next real work, not a deferred follow-on.

## 1. Context

### 1a. Why this came up

ADR-007 replaced hardcoded, task-specific pipelines with agent personas producing structured output — but the first real persona (`atomic-prd-agent`) constrains its output with a hardcoded Zod schema (`OUTPUT_SCHEMA` in `atomic-prd-agent.ts`) specific to a PRD's shape (`technicalProposal`, `userStories`, `acceptanceCriteria`, `constraints`, `evidenceUsed`). That reintroduces exactly the per-task-code problem ADR-007 exists to move away from: a second document type (impact analysis, corpus-stability report) would need its own hardcoded schema, not just its own persona file.

Separately, the user raised a real, explicitly-hedged future consideration: if this pipeline's output ever feeds a coding agent toward auto-merge (a real but speculative 6+-month trajectory, **not being built now**), acceptance criteria and user stories need to stay programmatically consumable, not prose requiring re-parsing later. The explicit framing throughout: *"we are not trying to design for this outcome today, just making sure we do not design something that cannot be easily adopted six months down the line."* This ADR is scoped to that framing — cheap, non-foreclosing choices now, not a build-out of future capability.

### 1b. The three-way architecture question, and where it landed

The user's original framing proposed a PO-Office-authorable **template** (markdown headings/order) + **rules** (a prompt file) + **persona** (task judgment) split, so a new document type costs no code. Two real gaps surfaced in discussion and were not closed by keeping "rules" as a third prompt file:

1. **A schema enforces structure, not template conformance.** A generic `sections: {heading, content}[]` schema doesn't stop a run from dropping or renaming a required heading — that needs a real, generic post-generation check (compare the run's headings against the template's own list, fail closed on mismatch), which is code, not prompt guidance.
2. **Prompt-based "rules" are best-effort; the model can ignore them.** Fabrication-checking (no claim ships without a real, verbatim-cited `fact_id` actually seen in that run's own tool results) and template conformance are both safety-critical in exactly the way a prompt instruction is not — an instruction the model happens to skip produces silently bad output, not a caught failure.

**Resolution**: the real split is not template / rules / persona (three peer prompt-ish artifacts). It is **template (data) / persona (prompt, best-effort, task-specific judgment) / a small set of mandatory code validators (fail-closed, task-agnostic)**. "Rules" was never a coherent third category — it was two different things (structure the template already encodes, and safety checks that must be code) wearing one name.

### 1c. The content-kind system, checked against real data

Rather than one generic `content: string` per section (which trades away real, already-useful structure — today's `acceptanceCriteria: string[]` and `userStories: {actor, goal, reason}[]` are genuinely parseable arrays, not prose), the agreed shape is a small, closed, composable set of section content *kinds*, checked directly against the real Q1a/Q1b JSON output rather than designed in the abstract:

```ts
type SectionContent =
  | { kind: "prose"; text: string }
  | { kind: "list"; checkable: boolean; items: string[] }
  | { kind: "cited-list"; items: { claim: string; evidenceIds: string[] }[] }
  | { kind: "user-stories"; items: { actor: string; goal: string; reason: string }[] };
```

Two real corrections made during validation against actual output, not designed in advance:
- **`checklist` alone was wrong** — `generate-atomic-prd.ts`'s existing "Information Collected" section is a plain descriptive bullet list, not a checkable one; reusing a `- [ ]`-rendering kind there is semantically wrong. Resolved as `{kind: "list", checkable: boolean, items}` rather than adding a fifth kind.
- **Field-naming drift** — the real JSON uses `point` for `technicalProposal` and `constraint` for `constraints`, an identical `{X, evidenceIds}` shape under two different field names. Normalized to `claim` before this becomes the shared type.

`cited-list` is the load-bearing kind of the four: validated **twice internally already** (`technicalProposal` and `constraints` both use the identical shape in real Q1a/Q1b output — not overfit to one field), and, per §1d below, validated externally in a way the other three kinds already were and it initially was not.

`MetaData` (snapshot freshness, persona/model version, tool-call counts) is **explicitly excluded from `SectionContent`'s closed set entirely** — it is deterministic, code-computed data, not something a persona should author. If it were just another heading with LLM-generated content, the model could hallucinate a commit SHA or a run timestamp. The renderer must special-case it and inject the real, computed values directly.

### 1d. Real external validation, from two live research passes — corrects itself mid-investigation

**Pass one** (`04-findings-document-types-2026-09-06.md`, dev/codegen tooling — GitHub Spec Kit, ChatPRD, Devin, SWE-bench): `prose`, checkable lists, and `user-stories` are real, independently-converged shapes, not this project's invention. No common cross-vendor document *schema* was found — convergence exists only at the content-kind level, validating the small-fixed-set approach directionally rather than any specific vendor's exact structure. `cited-list` (per-claim `fact_id` citation) was **not** found in dev tooling; initial framing was "this project is ahead of common practice" here.

**Pass two** (`06-findings-product-team-artifacts-2026-09-06.md`, broader PM tooling — Productboard, Aha!, Notion AI, Linear, PRFAQ generators, research-synthesis tooling), run specifically because pass one's dev-tooling-only aperture risked missing a real match elsewhere, **corrected pass one's framing**: `punt-labs/prfaq` (an open-source, evidence-grounded PRFAQ generator — its own stated position, *"a document without evidence is fiction"*) does per-claim biblatex citations from a tiered evidence hierarchy, including a dedicated "Four Risks Assessment" section structurally close to `cited-list`. Independently, the research-synthesis tooling world (Dovetail, BuildBetter, Perspective AI) converges on the same discipline: *"link every requirement back to the exact quote and timestamp it came from."* **Corrected framing: not "ahead of the market" — this project is applying a real, independently-converged-on discipline (evidence-grounded, per-claim citation) to a domain (code facts) nobody else has applied it to yet.** `cited-list` is now doubly confirmed — internally (reuse across two real fields) and externally (two independent domains outside dev tooling).

Also from pass two: **Allstacks Product Studio**'s "adversarial review findings" (scores a proposed spec against feasibility/capacity/security/historical-rework-rate before work is greenlit, its own materials call it a pre-mortem) softens — does not reverse — pass one's honest negative that no named "AI-generated impact analysis" product category exists. Real cross-session disagreement over which of this project's two future personas this maps to was resolved by re-reading the source text directly: "scores *every spec*... before greenlight" is a gate on one specific proposed change (per-request), matching `impact-analysis-agent`'s shape, not `corpus-stability-agent`'s ambient, no-proposed-change-in-the-loop scan. One real vendor, not a market trend — noted here as a live example of how a plausible-sounding mapping needs the actual source text checked, not assumed.

Neither pass found an emerging common cross-vendor schema, and neither suggested the fixed-small-set-of-kinds approach itself is the wrong shape — both found real tools converging on a similarly small set of composable outputs.

### 1e. A convergence found late, changing how the audit/compliance angle is framed

Pass one separately found real, dated 2026 research on agent-*action* provenance (EU AI Act / NIST AI RMF / ISO 42001-driven regulatory pressure) and filed it as distinct from this project's claim-to-`fact_id` citation discipline — one about auditing what an agent *does*, the other about justifying what an agent *claims*. A real, sharp insight raised directly by the user, agreed by both sessions: once an agent *implements* a change rather than only proposing one, those two things converge. An audit of "why did the agent do X" needs the same evidence chain this project already builds for "why was X proposed." **The document format is negotiable (PRD, appendix, whatever shape a persona renders); the evidentiary chain — claim → real cited `fact_id` → eventual action — is the part that would actually be regulated.** `cited-list` is structurally that chain already, not a new thing to build for this purpose.

## 2. Direction (agreed in discussion, not yet implemented)

1. **Section output is defined by a small, closed set of `SectionContent` kinds** (§1c's four kinds, with the `list`/`checkable` merge and `claim` field-naming already applied), not a bespoke schema per document type. A new document type is a new persona plus a new template file naming which kinds fill which headings — no new TypeScript schema.
2. **Two mandatory, code-enforced, fail-closed validators run unconditionally after every generation, independent of the persona's own prompt text**:
   - **Fabrication check**: every `cited-list` claim's `evidenceIds` must exact-substring-match real `fact_id`s actually present in that run's own tool-call results — not a schema-shaped/field-walking check, and not enforced by asking the persona nicely. The persona prompt must separately instruct citing `fact_id`s verbatim in backticks, since a paraphrased citation would slip past exact-match undetected.
   - **Template-conformance check**: the run's rendered section headings must match the template's own declared heading list; a dropped or renamed required heading fails the run closed rather than shipping silently incomplete output.
3. **`MetaData` is never part of `SectionContent`'s closed set.** The renderer special-cases it and injects real, code-computed values (snapshot freshness, persona/model version, tool-call counts) directly — never LLM-authored.
4. **Output metadata is persisted as structured data, not only as markdown prose**, alongside the rendered `.md` file — a JSON sidecar (or equivalent) carrying the same persona/model-version/tool-call-count/snapshot-freshness data `writeAgentOutput()` already computes as real in-memory objects before string-interpolating them into the markdown header. This is the audit-trail hook named in §1e: cheap today (no new tracking — the data already exists at write time), expensive to retrofit once a downstream consumer starts parsing it out of markdown prose instead. Recording the structure is the only action taken now; what eventually reads it, and any commercial/compliance framing beyond that, is explicitly out of scope for this ADR.
5. **A deliberate non-foreclosing choice, not yet a commitment**: if a `checklist`-style item is ever promoted from a bare string to an object (e.g. to attach a future verification artifact — a test, a Gherkin scenario), that hook belongs on `cited-list`, not on `list`. A `cited-list` entry already carries a real `fact_id` pointing at exact file/symbol-level code — structurally much closer to "the repository's own real test suite" (SWE-bench's actual verification mechanism, per `04-...md`) than a bare list string ever could be. No kind changes today; this is guidance for whoever revisits the question later.

## 3. Explicitly Left Open (real forks, not resolved here)

- **Given/When/Then**, if ever adopted: a genuinely new fifth `SectionContent` kind, or a specialization of `cited-list` (each clause as a `claim` with `evidenceIds` pointing at what it verifies)? Not decided — a real fork to revisit only if this is actually built, not now.
- **`impact-analysis-agent` scoping**: at least three real variants surfaced in discussion (a pre-spec breadth/impact scan; a PRD appendix, largely overlapping with today's `Constraints` section already; a post-spec scored gate in Allstacks' literal shape, which doesn't cleanly fit any current `SectionContent` kind and may need a scored/rubric shape if pursued). The user has explicitly deferred this until after the next PRD ships — no action needed now beyond preserving the three-way framing so it isn't flattened back into one assumed shape prematurely.
- **`corpus-stability-agent` scoping**: named (surfacing the real 42 cross-repo symbol ambiguities as a live finding), not designed.
- **Persona-file format standardization**: today's `atomic-prd-agent-persona.md` is real but ad hoc; worth standardizing once 2-3 personas exist and real common structure is visible, not designed in the abstract first.
- **"Audit trail as a commercial differentiator"**: a real narrative angle worth keeping in view for how this project is eventually presented, explicitly kept separate from the cheap structural change in Direction §4, which is the only audit-trail action actually being taken now.

## 4. Decision A — Answered by the User, 2026-09-06

**Original question**: does the next real PRD run use today's proven, hardcoded `OUTPUT_SCHEMA` (verified against real Q1a/Q1b results), or wait for a `SectionContent` migration first? Both parallel sessions had independently recommended shipping on today's schema and treating the migration as separate, subsequent work — a recommendation, not a decision either session made unilaterally.

**Real answer, given directly by the user**: neither. Not another verification run on the old schema, and not "ship now, migrate later" — **move straight to the `SectionContent` shape (this ADR's Direction, §2) and leave today's hardcoded `OUTPUT_SCHEMA` behind.** Before treating this as safe to act on, a real check was run (not just recalled): a clean whole-`pipeline/` type-check, a confirmed-empty scan for any leftover diagnostic/one-off scripts, and confirmation that the real Q1a/Q1b evidence proving the architecture (`06-step6-...md`, the backfilled files in `output/agent-runs/prds/test/`) is durably saved and does not depend on the current schema remaining in place. Nothing found hanging. The `SectionContent` migration (§2 of this ADR) is now the next real work, not deferred follow-on.

Entirely downstream of, and scoped within, ADR-007 — this ADR does not revisit the MCP tool layer, persona-file mechanism, or deployment questions ADR-007 settled; it defines the shape of what a persona's output actually is, once ADR-007's architecture is running. Also connects back to ADR-005's long-deferred "sanity/health report" leg (the real 42-symbol-ambiguity finding, now the concrete seed data named for the still-unscoped `corpus-stability-agent`) and to ADR-006's operating principle that "a new task type" should collapse into the cheap case — this ADR is what makes that true for a *document's* output shape, the way ADR-007 already made it true for the *tool* layer.

## 6. Consequences (open questions, not yet resolved)

- No code has changed as a result of this ADR yet — `atomic-prd-agent.ts`'s `OUTPUT_SCHEMA` is still today's hardcoded, PRD-specific Zod schema at the time of writing. Per §4, the `SectionContent` migration is now the agreed next real work, not deferred follow-on — still not built as of this ADR's own text, but no longer an open sequencing question.
- The fabrication-check and template-conformance validators' exact implementation (where they run in the agent loop, how a failure is surfaced/retried vs. hard-failed) is not designed beyond "must be code, must run unconditionally, must fail closed."
- Whether `generate-atomic-prd.ts`'s current output continues to serve as the comparison baseline (`output/atomic-prds/`) through and after a `SectionContent` migration, or gets retired at some point, is not decided.
