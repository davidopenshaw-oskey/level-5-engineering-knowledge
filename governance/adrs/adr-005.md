# Knowledge Pipeline Design Journal — ADR 005

## Title
**Early Whole-Module Synthesis May Not Be the Right Feeder for Impact Analysis or Atomic PRDs — A Retrieval-Over-Facts Split Is Under Consideration**

## Status
**Proposed — surfaced in discussion; not yet decided.** No implementation work has started on the direction described below. Recorded here so the reasoning isn't lost or rediscovered independently later, matching this folder's existing practice of capturing a pivot realization before it's fully resolved (see ADR-003).

## Date
2026-09-01

---

# 1. Context

The pipeline's original framing (ADR-000 onward) was: Phase 1 extracts deterministic AST facts, Phase 2 synthesizes those facts into prose engineering documents, and that document corpus serves the platform's downstream objectives — named elsewhere as things like impact analysis and atomic PRD generation. The evening of 2026-08-31 was spent hardening exactly this: migrating Phase 2's module-level synthesis (`01e-generate-module-level-profile.ts`) from free-text/regex citation handling to schema-enforced structured output, on the reasoning that an unattended production system needs citation reliability regex-based extraction couldn't deliver (see `governance/roadmap/firebase-oskey-dev/11-structured-output-citation-pilot.md`).

In a separate conversation (referenced but not held in this session), the question was raised: why synthesize into prose early at all, when the Phase 1 outputs — AST facts, call-graphs, dependency graphs — are already structured, exact, and arguably better suited to a retrieval-style (RAG) system for serving those same downstream objectives? This document's own session picked that question up and worked through it in detail (2026-08-31 into 2026-09-01), reaching several concrete, checkable conclusions rather than staying purely speculative.

---

# 2. Direction Under Consideration (not a decision)

Splitting the platform's named objectives apart exposes that they likely want different serving mechanisms, not one shared document corpus:

- **Impact analysis** ("what does changing X affect") is a graph-traversal problem, fully answerable from Phase 1's call-graphs and dependency-graphs directly — no LLM involvement needed at all for the "what's affected" question. This already works today in principle; the pipeline just doesn't expose it as a standalone traversal tool separate from feeding it into Phase 2 prose.
- **Atomic PRD drafting / "what exists in area Y"** is a retrieval problem, best served by indexing Phase 1 facts for semantic search (embeddings + a vector-capable store — Cloud SQL/AlloyDB with the `pgvector` extension was discussed as a concrete, boring, GCP-native candidate, not a committed choice) and doing narrow, on-demand synthesis only over the retrieved slice, reusing the exact-fact-ID/structured-output validation machinery already built for Phase 2's citation work.
- **Proactive risk/inconsistency flagging** — the behavior valued most from today's engineering reports (e.g. permission-enforcement asymmetries across sibling capabilities, ownership disagreements) — is neither of the above. Retrieval only answers questions asked of it; it does not proactively surface things nobody thought to ask about. This is a genuinely separate, "push" capability that a pull-based RAG system does not provide by design, not an oversight of the RAG framing.
- **Cross-repo edge-building.** Corrected 2026-09-02, after being stated wrong here originally: this was described above as "the remaining work is a deterministic join... not new research" — that undersold what already exists. `pipeline/cross-repo-synthesis/phase-03-ecosystem-topology/06-build-cross-repo-graph.ts` already performs exactly this join (Angular's `ast-firebase-callable-calls.json` `functionName` against Firebase's `api_contract` `callableExportName`) and has already been run multiple times, most recently 2026-08-29 — real output already exists at `output/cross-repo-synthesis/20260829_140137/enterprise-topology-graph.json`: 118 real cross-repo `HTTP_API_CALL` edges across all three repos. This was missed when this ADR was first written, not re-derived from scratch during the facts-serving-strategy investigation that followed it (see `governance/roadmap/facts-serving-strategy/`), which duplicated some of this by hand before the existing tool was found. The pub/sub side is genuinely harder than assumed here originally, though: the same script's own investigation found topic-name matching is **not** fact-derivable at all — the receiving Firebase handler never references the topic name in its own source, and the real binding lives entirely in GCP's Pub/Sub subscription configuration, external to both repos' code. It's confirmed instead via a manually-maintained table backed by three independent pieces of evidence (GCP subscription naming convention, a code comment, matching payload shape) — a genuine third category of information beyond "fact-backed" and "source-only": **externally-configured**, living in neither repo.

The emerging (not decided) shape: Phase 2's whole-module, cross-cutting synthesis capability — the thing hardened on 2026-08-31 — may find its better-justified home as a **sanity/health report** generator (periodic or post-merge, whole-module scope, proactive flagging), separate from a **new retrieval-feeder** process that turns facts into small, independently-findable descriptions for a RAG index (mostly cheap/deterministic templating, with light batched LLM enrichment only where a fact's literal wording needs translating into how a person would actually search for it). A further, undecided question raised in discussion: whether module-wide sanity flags belong on a post-merge/scheduled cadence versus whether a narrower, diff-scoped version of the same idea belongs pre-merge as a PR gate — current thinking leans toward these being two different, complementary tools rather than a timing choice on one tool.

# 3. Relationship to Prior ADRs

This does not contradict ADR-000/002/003/004. If anything, it's a further application of ADR-004's three-tier classification (structural / deterministic-cross-reference / narrative) to a question ADR-004 didn't ask: *which serving mechanism* should each tier feed — a searchable index, a synthesized narrative report, or a live traversal computed on demand? ADR-004 settled that structural and deterministic-cross-reference facts must be computed once and delivered completely regardless of narrative bundling; this direction extends that by suggesting structural facts may not need LLM synthesis to reach their consumer at all (impact analysis can read them directly), and that even narrative content may be better served in small independently-retrievable pieces for some objectives (PRD scoping) versus a single cross-cutting document for others (sanity flagging).

Nothing about 2026-08-31's structured-output migration is invalidated by this direction — the exact fact-ID infrastructure (`idMap`, `evidenceIds`, schema-validated citations) it produced is foundational to the retrieval-feeder idea too, arguably more central under this split than under the original framing, since it would no longer be an input to one synthesis step but the shared substrate both the sanity-report and retrieval-feeder paths would depend on.

# 4. Consequences (open questions, not yet resolved)

- Whether to continue investing further production-hardening effort in Phase 2's whole-module synthesis at its current scope, or to explicitly narrow its remaining role to sanity/health reporting before deciding how much more rigor it deserves — the reliability bar for "an automated system trusts this unattended" is higher than "a human reads this and applies normal skepticism," and which bar applies changes depending on this decision.
- No retrieval-feeder process exists yet. Open design questions include: chunk/card granularity per fact, how much (if any) LLM enrichment each fact needs versus plain deterministic templating, and the concrete choice of vector store (Cloud SQL/AlloyDB + pgvector was discussed as a plausible boring-tech-first candidate against Vertex AI Vector Search, not decided).
- No cross-repo join script exists yet, despite the identifiers needed for it already being present in Phase 1's facts (see Section 2) — this is real, concrete, buildable work, not blocked on further research.
- The pre-merge-gate-vs-post-merge-sanity-report split is a direction, not a design — neither has been scoped.
- This ADR intentionally does not commit to retiring, reducing, or continuing any existing script or contract. `01e`, `01a`/`01c`/`01d`, and the structured-output migration completed 2026-08-31 remain in production, unchanged, until a real decision is made on the above.
- P3a's investigation (real example questions, scope, what "atomic PRD" actually means) is being tracked in `governance/roadmap/facts-serving-strategy/`, starting 2026-09-01.
