# ADR-007: A Generic MCP Tool Layer and Task-Specific Agent Personas, Deployed for Gemini Enterprise Portability

## Title
**Replace hardcoded, task-specific pipelines (`generate-atomic-prd.ts` and its siblings) with a thin, generic MCP tool layer plus task-specific agent personas — built portably, deployed inside the GCP/Gemini Enterprise world.**

## Status
**Proposed — direction agreed in discussion 2026-09-05/06. No implementation started.** Distinct from, and downstream of, both ADR-005 (retrieval strategy) and ADR-006 (execution model and product-facing interface). This ADR resolves one of ADR-006's open hypotheses with real, current evidence, and answers ADR-006 §2a's "typed interface" gap directly.

## Date
2026-09-06

## 1. Context

### 1a. The real, concrete critique that started this

`governance/roadmap/facts-serving-strategy/15-workflow-clustering-and-angular-ux-facts.md` and `governance/roadmap/market-research/02-findings-retrieval-architecture-2026-09-05.md` document a long real investigation into why the atomic-PRD pipeline's retrieval kept missing the right evidence for two known real questions (Q1a/Q1b). Two hybrid-retrieval experiments (word-token BM25-style, character-trigram) both regressed against known targets. A deeper research pass followed, surfacing that Claude Code itself — the tool this whole project runs inside — had already abandoned embeddings-based RAG for pure agentic tool use, for reasons (precision, freshness) that matched this project's own findings exactly. A follow-up LLM-reranking test then closed the harder of the two gaps (Q1b) for the first time in the whole investigation, using existing graph-expansion infrastructure and one bounded LLM call — real, decisive, quantified evidence that an agent making its own retrieval decisions outperforms a single hardcoded pipeline.

Separately, and just as decisively: the user directly named a real, structural problem with how that work had been done. `_shared/search.ts`'s `RESULT_LIMIT = 25` was tuned by checking whether it made *two known examples* look right — a magic number with no general principle behind it, unable to tell us the right value for a third, different real query. More broadly: "by rolling code i meant, specific qry calls for generate-atomic-prd.ts as an example of being less generic" — the pipeline was accumulating task-specific, example-tuned logic across many files (`sync-facts.ts`, `search.ts`, `graph-traversal.ts`), the opposite of the original vision: a clean pipeline of artifacts, refreshed on merge, read by an LLM with carefully-crafted persona/rules/template files that could respond to arbitrary requests for PRDs, impact reports, and more.

### 1b. The reframe this produced, validated by real evidence

Discussion converged on a specific architecture: P1/P2 stays generic fact extraction only. A thin, generic tool layer sits on top (`search()`, `findGraphNeighbors()`, `walkBoundedCluster()`, already built and tested this session). Task-specific behavior — an atomic-PRD agent, an impact-analysis agent, eventually others — lives in **agent personas**: instruction files defining process, context docs, and output template per task, read by an agent at invocation time, never baked into pipeline code. A new task type costs a new persona file, not new code and not a redeploy.

This directly resolves the exact tension the reranking test surfaced: Q1a (a genuine breadth/impact-analysis question) and Q1b (a specific-flow question) need different retrieval treatment, which no single hardcoded constant (`RESULT_LIMIT`, or any fixed reranking cutoff) can serve correctly for both at once. An agent, given the right instructions, can decide for itself — the same way Claude Code decides whether to grep once or explore iteratively, rather than following one fixed retrieval pipeline for every query.

Real, converging evidence for this shape, found via live research, not asserted:
- **GitHub Copilot's coding agent, real production telemetry** (arXiv 2608.00101): 30.5% of real sessions are "Deep-loop read" — extended, iterative exploration averaging 9 LLM calls per session, not one-shot retrieval.
- **Augment Code, Cursor, Windsurf** all combine initial retrieval with agentic iteration; none treats a single fused score as final.
- **Retrieve-then-rerank, quantified**: reordering the same candidate set improved nDCG@10 from 0.13 to 0.40 on a comparable benchmark (BRIGHT Biology) — close to a direct description of this project's own situation, where the right fact was often already in the pool.

Full detail and sources: `governance/roadmap/market-research/02-findings-retrieval-architecture-2026-09-05.md`.

### 1c. The deployment constraint, and what real research resolved about it

The product must ultimately be deliverable inside **Gemini Enterprise** — named in ADR-006 §2b only as an unverified hypothesis ("Gemini Enterprise is genuinely the right dispatch/agent layer is a hypothesis, stated as such by the person raising it, not a decision"). Real, current research (2026-09-05/06) found:

- **Vertex AI Agent Builder and Gemini Enterprise merged** (April 2026) into one platform: "Vertex AI hosts the engine... Gemini Enterprise is the end-user interface consuming what the AI team built" ([Autenticare Blog](https://somosautenticare.com.br/en/blog/gemini-enterprise-vs-vertex-ai/)).
- **Claude models run natively inside Gemini Enterprise's own model catalog** — "billed and managed as a serverless API with no separate infrastructure to provision" ([Google Cloud docs](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/partner-models/claude)). The agent's reasoning model doesn't have to change to satisfy the platform constraint.
- **Gemini Enterprise added custom MCP server support on 2026-09-05** — the day before this decision: "an administrator registers a Custom MCP Server data store so Gemini Enterprise imports the tool catalog" ([Google Cloud docs](https://docs.cloud.google.com/gemini/enterprise/docs/connectors/custom-mcp-server/set-up-custom-mcp-server)).

This means the platform constraint doesn't force a rebuild onto GCP-native infrastructure (BigQuery, Vertex AI Search) — it can be satisfied by exposing the *existing* Postgres/pgvector-backed tools through a properly-built, standard MCP server.

### 1d. Real alternatives considered for the tool-exposure layer

- **ADK-native function tools** (Google's Agent Development Kit): the simplest possible option if permanently committed to building the agent in ADK — a tool is just a function call, no server, no protocol. Rejected as the *only* mechanism because it ties the tools to one framework, forfeiting the portability found below.
- **Plain REST API + OpenAPI spec**: real, Google-documented pattern ("Grounding with your search API," [Gemini Enterprise docs](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/grounding/grounding-with-your-search-api)). Comparable hosting effort to MCP, but not natively speakable by MCP-native clients without a separate integration per consumer.
- **Full migration to a BigQuery-native Vertex AI stack**: real option — Google provides fully-managed, zero-build MCP servers for BigQuery natively. Deferred, not rejected: a large lift (rebuilding the facts pipeline, `graph-traversal.ts`'s logic, and every P1/P2 sync script on new infrastructure) with no proven need yet at current scale.
- **Continuing hardcoded, per-task TypeScript pipelines** (the status quo): the real failure mode this whole ADR exists to move away from — see 1a.

### 1e. Real SDK, hosting, and portability findings

- **Google's own Genkit framework ships an official MCP server plugin** (`@genkit-ai/mcp`), TypeScript, matching this codebase's existing language exactly, with an official Google Codelab for deployment: *"How to deploy a secure Genkit MCP server on Cloud Run"* ([Google Codelabs](https://codelabs.developers.google.com/codelabs/cloud-run/genkit-how-to-deploy-a-secure-mcp-server-on-cloud-run)). Chosen over Anthropic's own TS SDK specifically because it's Google-maintained, directly relevant to the GCP-delivery constraint, while still speaking standard MCP.
- **Cloud Run is the right-sized hosting choice** for a small (3-tool) server: "cost-effective... pay only for request duration and scales to zero," with an official Codelab for exactly this shape (*"Build and deploy an ADK agent that uses an MCP server on Cloud Run"*). Vertex AI Agent Engine (heavier, fully managed) is the natural upgrade path once the agent itself is also hosted on the platform, not the right starting point. GKE is real overkill at this scale.
- **Confirmed real, independent MCP clients that could consume the exact same server, no extra work per client**: Gemini Enterprise, Claude Code, Claude Desktop, VS Code + GitHub Copilot (generally available, not preview), and Google Antigravity (added early 2026, with an unresolved nuance about its "Managed Agents" mode specifically). Five real platforms, one server.

### 1f. Why the tool surface is expected to stay small

Reranking, query decomposition, and hybrid retrieval all turned out, on reflection, not to need new tools at all — they collapse into the agent's own reasoning process (calling `search_facts` multiple times, or reasoning over its results) once an agent replaces a hardcoded pipeline. New task types need new personas, not new tools, because they all draw on the same two underlying primitives (search the facts, walk the graph). A new tool is only justified by a genuinely new *kind of data access* (e.g., a workflow-catalogue query, a persistence/write action), not by a new task. Expected growth: roughly 4-6 tools over the life of the project, not "very many."

## 2. Direction (not a final decision — real, agreed in discussion, not yet implemented)

1. **P1/P2 stays exactly what it is today** — generic, task-agnostic fact extraction and storage. No change.
2. **A new, thin, generic MCP tool server** (`pipeline/facts-postgres-index/mcp-server/`) wraps the existing `_shared/search.ts` and `_shared/graph-traversal.ts` primitives as MCP tools (`search_facts`, `get_graph_neighbors`, `walk_cluster`), built with Genkit's MCP plugin.
3. **Hardcoded, task-specific pipelines** (`generate-atomic-prd.ts`, `technical-proposal.ts`, `assemble-prd.ts`, `render-evidence.ts`) remain the current, working implementation, but are the intended target for eventual replacement — not the destination. Whether and when they're formally deprecated is not yet decided.
4. **Task-specific behavior moves into agent personas** — instruction files defining process (e.g. "run a broad search; decide whether this is a breadth or specific-flow question; narrow or expand accordingly before writing anything"), which context docs to consult, and the output template — read by an agent at invocation time (Gemini Enterprise's Agent Designer, or ADK). A new task type costs a new persona file, never new tool-layer code, never a redeploy of the tool server.
5. **Local development runs the MCP server over stdio** against the existing local Postgres (docker-compose) — zero new local infrastructure. **Remote deployment runs over HTTP on Cloud Run** — a real transport switch to test explicitly before trusting it, not assumed to behave identically to the stdio path.
6. **The tool surface is expected to stay small** (see 1f) — new tools are added only for genuinely new kinds of data access, not new task types.

## 3. Relationship to Prior ADRs

Downstream of ADR-005 (retrieval-strategy direction: graph traversal, retrieval-over-facts, narrative synthesis, per objective) and ADR-006 (execution model and product-facing interface). This ADR:
- **Resolves ADR-006 §2b's Gemini Enterprise hypothesis** with real, dated (2026-09-05/06) evidence, rather than leaving it as an unverified guess.
- **Directly answers ADR-006 §2a's "typed interface" gap** — "something needs to expose these scripts as callable units rather than CLI invocations driven by environment variables" — the MCP tool layer is exactly that typed interface.
- **Extends ADR-006 §2c's operating principles**, particularly principle 2 ("can we get X from the corpus?" has two honestly different answers — a cheap config change or real new extraction work): under this architecture, "a new task type" collapses fully into the cheap case (a new persona file), and only a genuinely new kind of data access remains in the expensive case (new tool-layer work).

## 4. Consequences (open questions, not yet resolved)

- No MCP server code exists yet — this is direction, not implementation. See `governance/roadmap/mcp-direction/01-mcp-tool-server-tasklist.md` for the concrete build plan.
- Whether `generate-atomic-prd.ts` and its siblings get formally deprecated, removed, or kept running in parallel during a transition is not decided.
- The exact shape of an agent persona file (fields, format, where it's registered — Agent Designer vs. ADK) is not yet designed.
- Whether the (already-superseded) workflow-seeding plan (`governance/roadmap/building-workflows/01-workflow-seeding-tasklist.md`) and the not-yet-built reference-docs plan (`governance/roadmap/facts-serving-strategy/15-...md`, Task 3) get rebuilt as personas/context docs, or reconceived entirely, needs its own review — tracked as a real, separate next step (an audit of all outstanding prior work against this new direction), not resolved here.
- `RESULT_LIMIT = 25` in `_shared/search.ts` and the 92→42 real cross-repo symbol tie-break question (`15-...md`) remain open, independent of this ADR — they are P1/P2 or tool-layer-internal data-quality concerns, not resolved by adopting this architecture.
- The one real, unresolved nuance on Antigravity's MCP support (main IDE vs. "Managed Agents" mode) needs direct confirmation before being relied on for that specific client.
