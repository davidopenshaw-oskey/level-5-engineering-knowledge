# Knowledge Pipeline Design Journal — ADR 006

## Title
**Execution Model and Product-Facing Interface for the Facts-Serving Pipeline — POC Today, Harness/Agent-Orchestrated Later**

## Status
**Proposed — surfaced in discussion; not yet decided.** No implementation work has started on the direction described below. Distinct from, and downstream of, ADR-005: ADR-005 decided (as a direction, not a final decision) *what* serves each downstream objective — graph traversal, retrieval-over-facts, or narrative synthesis. This ADR is about *how the resulting pipeline gets run and triggered*, a different axis, once ADR-005's direction is acted on.

## Date
2026-09-05

# 1. Context

The facts-serving-strategy investigation (`governance/roadmap/facts-serving-strategy/`, `05` through `15`) has been built and run as a sequence of independent TypeScript scripts — `sync-facts.ts`, `build-cross-repo-edges.ts`, `build-intra-repo-edges.ts`, `generate-atomic-prd.ts` — each invoked directly via environment variables, in a specific order, by a human or by an agent driving the CLI. This is appropriate for a POC: it is the fastest way to prove whether the underlying retrieval-and-graph approach (ADR-005) actually works, and this session's real results (verified against `01-qa-vision-and-examples.md`'s real examples) say it does, with real, honestly-reported limitations.

Two real questions surfaced in discussion, once the POC's early results made "what does this look like in production" a live question rather than a hypothetical one: how this execution model should evolve if engineering adopts the underlying concept, and how a Product Office user would ever actually trigger any of this, given no such interface exists today (`01-qa-vision-and-examples.md` B1 answered this only as "for now, a human," explicitly not a final answer).

# 2. Direction Under Consideration (not a decision)

## 2a. Execution model: sequential scripts now, agent harness later — a well-designed POC should allow this evolution without a rewrite

**What's already in the right shape, checked against the real code, not asserted:** every script built this session opens and closes its own database connection, shares no in-memory state with any other script, and leaves a real, auditable, persisted output behind (a Postgres row or a markdown file) rather than an in-memory handoff. The one real paid step in each script (`EMBED=true`, `GENERATE_TECHNICAL_PROPOSAL=true`) is already gated behind an explicit, cost-aware boundary — exactly the shape a harness would want for a task it needs to monitor, retry, or rate-limit independently. `generate-atomic-prd.ts` run multiple times concurrently for different workflows is safe by construction today — no shared mutable state, each invocation writes only its own output file.

**What would genuinely need rework, not hand-waved as free:**
- **Interface.** Scripts take their input via shell environment variables today. A harness would want a typed function call or a message/queue contract instead. This is real work, though shallow — the logic underneath does not change, only how it receives its inputs.
- **Granularity.** `generate-atomic-prd.ts` bundles several conceptually separate steps (search, evidence rendering, graph expansion, the LLM call, template assembly, file output) into one script. Fine for proving the concept; a harness wanting to checkpoint, retry only the LLM call, or observe graph expansion as its own monitored step would need this decomposed further.

**Direction, not a decision:** the POC's real boundaries (bounded units, auditable outputs, fail-loud errors, explicit cost gates, parallel-safety) are the right foundation for an eventual harness — the interface and step granularity are the parts that would need real, additional engineering, to be scoped by engineering if and when this is adopted, not designed now.

## 2b. Product-facing interface: undefined today; a plausible future shape is rules + templates + task definitions dispatched by an agent

No interface exists today for how a Property Manager or Product Office user would trigger any of this directly — every real example this session (`13`, `14`, `15`) was run by a human or an agent driving the pipeline's CLI scripts by hand. Given Gemini Enterprise is the company's actual infrastructure, one plausible future shape (not a commitment) is an agent that receives a natural-language business request — "create atomic PRDs for x, y, z," "do impact analysis for a, b, c," "do risk assessment on repos a & b for flows c and d" — and dispatches it to the right combination of:
- a **template** (document shape — `12-atomic-prd-template.md` is the one that exists today, for exactly one task type),
- a **rules file** (process/quality constraints for how that task type should be executed — not yet built for any task type; the instructions currently live embedded in `technical-proposal.ts`'s own TypeScript source, the same problem the template file already solved for document *structure*),
- a **task definition** (which pipeline, rule file, and template a given request type maps to — a genuinely new layer, not yet conceived in any concrete form).

**A real challenge to this shape, not just an endorsement of it:** this pattern is a good *dispatch* mechanism, but it would be wrong to read "add rules and templates" as sufficient for every new task type on an already-complete, task-agnostic engine. New task types plausibly need different *evidence-gathering* logic underneath, not just new configuration on identical machinery:
- Atomic PRD (built): a retrieval anchor plus 1-hop graph expansion plus one LLM synthesis call.
- Impact analysis: ADR-005 already named this as a different kind of problem — answerable from the call-graph directly, with little or no LLM involvement for the core "what's affected" question. Likely needs the graph traversal (`_shared/graph-traversal.ts`) extended to more hops for a deterministic report, not the atomic-PRD pipeline with a different template swapped in.
- Risk assessment: some real signal already exists for free (a fact's real fan-out count in `cross_repo_edges` is a genuine blast-radius proxy); other plausible signals (test coverage, for instance) aren't captured by anything built so far and would need new P1/P2 extraction.

**A real dependency between 2a and 2b, not two independent questions:** before any agent — Gemini Enterprise or otherwise — can dispatch a business request to this pipeline, something needs to expose these scripts as callable units rather than CLI invocations driven by environment variables. 2b's vision depends on 2a's interface question being resolved first, not the other way around and not in parallel by coincidence.

## 2c. Three operating principles, confirmed by this session's own real experience, not asserted abstractly

1. **P1 extracts; P2 collates and organizes.** P1 (per-repo AST extraction) does not itself join facts across repos or build graph structure — every cross-repo edge, every intra-repo call chain built this session lives in P2 (the Postgres facts index and `cross_repo_edges`). "P1 and P2 should collate and organize facts for downstream phases" is accurate read as a description of the two-phase *system*, not of P1 alone.

   This collation has a real, deliberate boundary, not a gap to eventually close: business and architectural *rationale* (why Firestore vs. MongoDB, why a Property Manager never manages residents) is explicitly excluded from P1/P2's facts and kept as separate LLM context instead (`15-workflow-clustering-and-angular-ux-facts.md` task 3) — a decision made this same week, not an oversight. P1/P2 owns code-derived structural facts and the graph between them; it does not, and should not, absorb narrative intent.

2. **Each new downstream task type costs one of two different amounts, and it matters which.** "Can we get X from the corpus?" has two honestly different answers, not one: "yes, add a rule/template" (cheap, no pipeline change) or "yes, but we need new P1/P2 extraction first" (real engineering work). Collapsing these into a single "yes" when scoping a business ask misrepresents the real cost.

3. **P1/P2 will need real iteration as downstream needs surface gaps — this already happened repeatedly this session, not a risk to plan for hypothetically.** Every real fix in `05-tasklist.md` (union-value extraction, the controller-document link, return-type surfacing) and every enrichment fix in `14-inbound-outbound-surface-graph-tasklist.md` and `15-workflow-clustering-and-angular-ux-facts.md` followed the same real pattern: a downstream question exposed a gap in what P1/P2 had captured, which fed back into a P1/P2 change. This argues for keeping P1/P2's extraction architecture modular and cheap to extend — which this session's twelve description-enrichment fixes already validated in practice (each was a bounded, additive change, not a rewrite) — rather than treating iteration as an exception to design around.

# 3. Relationship to Prior ADRs

Downstream of ADR-005, not a revision of it. ADR-005 decided (as a direction) *what mechanism serves each downstream objective* — graph traversal for impact analysis, retrieval-over-facts for atomic PRD scoping, narrative synthesis for sanity/health reporting. This ADR assumes ADR-005's direction and asks a different question: once built, *how does it get executed, and how does a real user or business request ever reach it*. Section 2c's operating principles are also a direct, practical extension of ADR-005's own "no retrieval-feeder process exists yet" and "no cross-repo join script exists yet" open questions — both were subsequently built and, per 2c point 3, both needed real iteration exactly as this ADR predicts future task types will.

# 4. Consequences (open questions, not yet resolved)

- No typed interface exists yet for any of the scripts built this session — env-var invocation is the only interface today. Scoping this is real work, not yet started, and is a precondition for 2b, not a parallel, independent effort.
- No rules-file or task-definition artifact exists yet for any downstream task type, including atomic PRD (whose process rules currently live embedded in `technical-proposal.ts`'s TypeScript source, not externalized the way the template already is).
- Impact analysis and risk assessment, named here as plausible next task types, have no evidence-gathering design yet beyond what's noted in 2b — this is real, unscoped work, not an extension of an already-complete engine.
- Whether Gemini Enterprise is genuinely the right dispatch/agent layer is a hypothesis, stated as such by the person raising it, not a decision — no commitment is made here to that specific infrastructure choice.
- This ADR does not commit to decomposing any existing script, building any typed interface, or starting work on impact analysis or risk assessment. It exists to record the reasoning and the real operating principles (2c) before they're lost or have to be rediscovered independently later, matching this folder's own established practice (see ADR-005's own opening rationale).
