# ADR-010: Replace `fact_id` as the Identity/Join Key with an Opaque Surrogate Reference

## Title
**`fact_id` currently does three jobs at once — unique identity key, human-readable citation label, and (for `call_expression` facts) verbatim disambiguating source text — and the conflation has caused three separate real incidents. Decision: introduce a short, opaque, fixed reference column as the real identity/join key; keep the existing `fact_id` text purely as a descriptive/citation label, no longer used for equality, joins, or tool-call arguments.**

## Status
**Proposed — direction decided in live discussion, schema/index/code blast-radius verified directly against live Postgres and the real codebase (not assumed). Exact code touch points (which files, how many duplicated ID-generator copies, the migration script itself) are deferred to a dedicated follow-up investigation, not yet enumerated or built.**

## Date
2026-09-17

## 1. Context

### 1a. What `fact_id` is and why it was built this way

`fact_id` is a natural key — built directly from real, verbatim source content (kind, module, file path, symbol, caller, an occurrence counter, and for `call_expression` facts, the literal call-site text) rather than an arbitrary generated value. This was a deliberate choice: a natural key is human-readable and directly debuggable, and doubles as the citation string shown in a generated document's evidence appendix.

### 1b. Three separate real incidents this conflation has caused, in one project (not hypothetical)

1. **Unbounded key length crashed Postgres's btree index.** Fixed earlier this session via `boundedIdComponent()`/`stableFactId()` (truncate + hash-suffix any component over ~2000 chars), duplicated across pipeline copies with per-repo thresholds.
2. **Whitespace-collapse citation bug** — a real, indexed fact's citation was rejected as "fabricated" because whitespace had been reformatted between what the model cited and what was stored. Fixed via `checkFabrication`'s strip-all-whitespace normalization (`mcp-server/agent-poc/validators.ts`).
3. **Content-truncation / transcription-drift bug — not yet fixed.** In a real, live test (`governance/roadmap/graphrag/10-case-2a-fanout-content-truncation-finding-2026-09-17.md`), the model correctly received a full, real fact_id from a tool result, then — several turns later, needing to pass that same id back into another tool call — regenerated it with an entire argument-list segment silently dropped. Traced precisely: the SQL layer passed the correct string through unmodified; the drift happened in the model's own token generation when retyping a long, multi-line identifier from its own working context. Not a SQL bug, not a validator bug — a reliability limit of asking a model to verbatim-reproduce long multi-line strings as tool arguments.

### 1c. The real data behind why this recurs, not a one-off

Corpus-wide (68,902 facts): length min 63, max 10,837, avg 187, median 161, p90 288, p99 496. **`call_expression` (37,859 facts, ~55% of the corpus) is the only fact kind with any embedded newlines at all** (8,865 of them, 23%) — every other kind is short and single-line, structurally safe from this class of problem. Both real incidents above were only a few hundred characters — well inside the "normal" range, nowhere near the extreme tail. **Length is not the trigger; embedded newlines are, at any length** (`governance/roadmap/graphrag/11-fact-id-newline-reliability-finding-2026-09-17.md`). This is a structural byproduct of `ts-morph`/SwiftSyntax faithfully capturing real nested call-site source text (worst real case so far: a 10,837-char SwiftUI view body) — it will keep recurring as more repos are extracted, not shrink on its own.

### 1d. Real blast-radius, checked directly (not assumed) before deciding

- **Only two tables reference `fact_id` anywhere in the schema**: `facts.fact_id` (primary key) and `cross_repo_edges.source_fact_id`/`target_fact_id`. No embedding table, no other join. Confirmed via direct `information_schema.columns` query.
- **Existing indexes on these columns**: `facts_pkey` (unique btree on `fact_id`), `cross_repo_edges_source_fact_id_idx`, `cross_repo_edges_target_fact_id_idx` (both btree). None of the other indexes on `facts` (embedding HNSW, description full-text GIN, kind, payload, repo/module, symbol trigram) touch `fact_id` at all — search is completely unaffected by this change.
- **`cross_repo_edges` already has its own independent opaque surrogate key** (`edge_id`) — this ADR extends a pattern the schema already uses elsewhere, not a new one.
- **Only one code site in the entire codebase parses `fact_id`'s internal structure** — a diagnostic-only "near miss" printout (`atomic-prd-agent.ts:762-763`, splits on `|` to find likely-intended matches for a suspected fabrication). Every real consumer (`db/graph-traversal.ts`, `db/search.ts`, tool schemas in `src/index.ts`, `capability-fanout-prd-agent.ts`'s `seenFactIds` set, `validators.ts`'s `extractRealFactIds`/`checkFabrication`) treats `fact_id` as an opaque string used only for equality/lookup.
- **The rendered document's main body never shows a raw `fact_id`** — only a citation marker (`[#N]`), rendered via `renderCitations` (`section-content.ts`). Only the Evidence Used/Audit Trail appendix (`atomic-prd-agent.ts:439,468`) prints the raw string verbatim, including embedded newlines, inside a single-backtick code span — a separate, minor rendering concern, **explicitly out of scope for this ADR** (see §4).

## 2. Decision

Introduce a new, short, fixed-size, opaque reference column that becomes the real identity/join key:
- On `facts`: replaces `fact_id` as the primary key.
- On `cross_repo_edges`: replaces `source_fact_id`/`target_fact_id` for join/lookup purposes.

This is a **swap of what the existing indexes point to, not an addition** — three indexes get re-pointed to the new column; no net-new index count. Likely form: a content hash (e.g. SHA1), consistent with the existing hash-suffix precedent already in `boundedIdComponent()`, rather than a sequence — preserving the natural key's useful "stable without a DB round-trip" property without inheriting its instability.

The existing `fact_id` text is **kept**, unchanged, purely as a descriptive/citation label — still stored, still shown in the evidence appendix, still human-readable — but is no longer used for equality, joins, or as a tool-call argument. Search (embedding similarity, full-text) is untouched; it never used `fact_id` for matching in the first place.

**Real consequence beyond Postgres**: because tool calls (`get_graph_neighbors`, `walk_cluster`, citation `evidenceIds`) currently require the model to carry and retype the long natural key across turns, switching those to the new short reference directly closes the §1b-3 transcription-drift bug at its source — the model no longer has a long, multi-line string to garble. This is judged the primary real benefit of this change; the Postgres index/query speed-up (shorter, fixed-size comparisons vs. long variable text) is real but secondary, and the biggest practical win is fewer tokens per tool call (cost and latency on every graph lookup), not raw database microseconds.

## 3. Explicitly deferred / out of scope for this ADR

- **The Evidence Used/Audit Trail appendix's verbatim, un-escaped rendering of `fact_id`** (including embedded newlines inside a single-backtick span) — a real, separate, minor rendering concern. Benched deliberately: it doesn't gate this decision and can be revisited independently later.
- **Consolidating the ~5 duplicated `stableFactId()`-style generator copies** across the pipeline into one shared function — real, but an implementation detail for whichever session builds this, not a decision this ADR needs to make.
- **Auditing old PRD outputs under `output/agent-runs/**` for `fact_id` references** — most predate this session's fixes and are disposable trial artifacts, not a live backward-compatibility concern. Not investigated.
- **The exact enumeration of every code call site requiring modification** (which files in `mcp-server/`, how many pipeline copies across which of the 9 repos, the migration/backfill script for 68,902 existing facts and their `cross_repo_edges` rows) — real, necessary build-planning work, intentionally left to a dedicated follow-up investigation prompt that treats this ADR as its reference document, rather than re-deriving or relaying these facts from a live conversation.
- **The still-open, unrelated capability-fanout completion-failure rate** (2 of 5 capabilities failing a turn cap, confirmed on two real cases) — a different reliability problem, not addressed by this decision.

## 4. Relationship to prior ADRs

- Does not reverse ADR-002 (Phase 1 extraction stays fact-based, fully-qualified strings unmodified) — the raw, verbatim `fact_id` text is kept exactly as extracted; this ADR only changes what's used for identity/lookup, not what's captured.
- Extends the capability-fanout architecture (`project_graphrag_two_tier_investigation`, `governance/roadmap/graphrag/01-findings-and-open-questions-2026-09-10.md`) by fixing a citation-integrity failure mode that decomposition alone did not close (§1b-3 was found *inside* a working capability-fanout run, not the one-hit baseline).
- Builds directly on this session's own `boundedIdComponent()` fix — confirmed that fix does **not** cover this ADR's problem (both real incidents were well under its ~2000-char threshold; the trigger is embedded newlines, not length) — this is a materially different, narrower fix, not a tightened version of the earlier one.

## 5. Consequences (open, not yet resolved)

- Which exact files/pipelines need to change, and the real migration/backfill approach for existing data — scoped to a follow-up investigation prompt referencing this ADR.
- Whether the appendix's raw-text rendering (§3) ever gets revisited, and on what timeline.
- Whether the new reference column is a content hash or something else — leaning hash for stability-without-lookup, not finally fixed here.
