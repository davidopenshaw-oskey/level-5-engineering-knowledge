# Knowledge Pipeline Design Journal — ADR 004

## Title
**Structural Facts Must Be Deterministic and Complete Regardless of Prompt Bundling — Only Narrative Synthesis Is Safe to Batch**

## Status
**Approved (principle); implementation plan not yet built**

## Date
2026-08-02

---

# 1. Context

ADR-003 established that every Phase 2+ synthesis stage must bound its own LLM input — no stage may assume its input "just fits" because it's already structured facts rather than raw source. What ADR-003 did not address: *how* a stage should bound its input without silently losing information in the process.

On 2026-08-02, discussing how P2's reduce step should scale as the module/repo landscape grows (today: 11 capabilities for `building`, fits in one reduce call; tomorrow: a bigger module, or cross-repo synthesis reducing many module profiles), the natural next step — split a large reduce input into smaller bundles, reduce each bundle, then reduce the bundle summaries — was found to reintroduce the *exact* failure this pipeline already fixed once today: if capability A (bundle 1) is depended on by capability B (bundle 4), a partial-reduce over only bundle 1 cannot see B's dependency on A, the same way a module's own evidence graph cannot see who depends on it from outside (the reason `06-build-cross-module-dependency-graph.ts` exists). Naive batching recreates cross-module-style blindness at the bundle boundary.

Working through two concrete candidate cases confirmed the fix isn't a clean binary ("structural vs. narrative") but a three-way split:

- **Firestore ownership**: which module *touches* a Firestore path is a deterministic fact. But `building`'s own evidence already shows `/buildings/{buildingId}/accesses` written by four different capabilities — deciding which is "the owner" versus "a fan-out consumer" is interpretation, not lookup.
- **Permission strings**: whether a string exists in `rbac-roles.json` is a deterministic yes/no. Whether its use is *semantically appropriate* for the operation it gates (the `v1.org.settings.create` mismatch found in `building`'s profile) requires judgment.

Both cases have a purely deterministic layer and a purely interpretive layer bundled together, and the interpretive layer is the only part that's safe to lose partial visibility into via batching.

---

# 2. Decision

Classify all information flowing into any P2+ synthesis call into three tiers, and treat each differently with respect to bundling/batching:

1. **Structural** — relationship facts (dependencies, imports, ownership touch-points) that are fully resolvable deterministically from P1 facts, with no LLM judgment involved. Example: the cross-module dependency graph (`06-build-cross-module-dependency-graph.ts`).
2. **Deterministic-cross-reference** — facts that need a lookup/transform but still no LLM judgment (does a permission string exist in the RBAC document; how many distinct modules/capabilities touch a given Firestore path). Not fully built yet as its own artifact class — currently done ad hoc, inconsistently, sometimes by asking the LLM to eyeball a cross-check it shouldn't need to perform itself.
3. **Narrative/interpretive** — anything requiring synthesis judgment (is this permission semantically well-chosen; which of several writers is "the" owner; architectural commentary; business-logic description).

**Tiers 1 and 2 must be computed once, completely, and delivered identically to every synthesis call at a given scope, regardless of how that scope's narrative content happens to be bundled for prompt-fitting purposes.** Only Tier 3 content may ever be split across bundles and reduced hierarchically. A partial-reduce over a subset of bundled narrative content is an acceptable loss of *synthesis nuance* (already confidence-tagged, already understood as best-effort); a partial-reduce that is missing a Tier 1/2 fact because it happened to land in a different bundle is a correctness failure, not a nuance loss.

---

# 3. Relationship to ADR-002 and ADR-003

ADR-002 established that canonical facts stay raw. ADR-003 established that every synthesis layer must independently bound its own input, whatever form that takes. This ADR closes a gap ADR-003 left open: it addressed *volume* (does it fit) but not *safety* (does splitting-to-fit risk silently dropping a relationship). The answer this ADR gives: only if the thing being split is narrative. Structural and deterministic-cross-reference information must never depend on bundling at all — the same principle that already produced `06-build-cross-module-dependency-graph.ts` (compute once, deliver whole, regardless of how many capability calls exist) generalizes into the standing rule stated here, rather than being a one-off fix specific to inbound module coupling.

---

# 4. Consequences

- Before designing *any* recursive/hierarchical reduce mechanism (needed once a module or cross-repo scope outgrows a single flat reduce call), the Tier 1/2/3 classification for that scope's inputs must already be settled — batching design comes *after* classification, never before, or the batching mechanism risks being built around the wrong assumption (that everything is safe to split).
- Tier 2 is currently under-built: today's contracts ask the LLM to perform RBAC existence checks and Firestore ownership disambiguation itself, inside the narrative synthesis call, rather than being handed a pre-computed deterministic answer. The RBAC leaf-role flattening (`governance/roadmap/tasks.md` item 13) is the first concrete Tier 2 artifact identified; Firestore multi-writer/ownership disambiguation is a second candidate, not yet resolved as structural-fact-plus-interpretation split.
- See `governance/roadmap/02-structural-narrative-synthesis-tiers.md` for the implementation plan — audits existing fact types and P2 sections into the three tiers first (with explicit checkpoints on ambiguous cases), builds missing Tier 2 artifacts, and only then designs batching mechanics for Tier 3.
