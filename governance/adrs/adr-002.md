# Knowledge Pipeline Design Journal — ADR 002

## Title
**Extraction Stays Strictly Fact-Based; Presentation and Formatting Decisions Are Deferred to the Synthesis Layer**

## Status
**Approved & Implemented**

## Date
2026-08-01

---

# 1. Context

While adding request/response type resolution to `api_contract` facts (Phase 1 extraction), a concrete case surfaced: TypeScript's checker resolves a handler's parameter/return types as fully file-qualified strings, e.g.

```
import("functions/src/modules/building/models/functions/building_request.model").OSKBuildingGetAllRequestData
```

rather than the bare name (`OSKBuildingGetAllRequestData`) a human would write by hand. The fully-qualified form is more precise — it disambiguates identically-named types defined in different modules — but is noisier to read in a generated document.

The question raised: should the extractor also emit a "cleaned" bare-name field alongside the raw one, for readability?

---

# 2. Decision

No. The extractor emits only the raw, fully-qualified fact. No derived "clean name" field is added at the extraction layer.

This is adopted as a standing principle, not a one-off call: **Phase 1 extraction stays strictly fact-based. Any formatting, simplification, or presentation decision is deferred to whichever downstream layer actually consumes the fact for display (Phase 2 synthesis prompts, generated documents, etc.).**

---

# 3. Rationale

- The moment extraction starts "cleaning up" a fact for readability, it is making an interpretive judgment call (where does the cleanup stop — strip `import(...)`? Also unwrap `OSKDocumentList<...>`? Also unwrap `OSKHttpsSuccessResponse<...>`?). That judgment belongs to whoever builds the actual presentation/synthesis step with full context of what they need, not to the extractor.
- This is consistent with the pipeline's foundational decision (ADR-000): separate **facts** (deterministic, uninterpreted) from **knowledge** (synthesized, interpreted). A "cleaned" type name is knowledge about the fact, not the fact itself.
- This project is a product-team-led POC intended for handover to engineering. Decisions baked into the extraction layer are the hardest to revisit later, since downstream artefacts start depending on their exact shape. Keeping extraction minimal and raw maximizes the options available to whoever inherits this next.

---

# 4. Consequences

- Facts remain maximally traceable and unambiguous — the fully-qualified type string always identifies exactly which file a type comes from, which matters once multiple modules define similarly-named types.
- Generated documents (module profiles, API references) will look noisier than a hand-written equivalent until a presentation/synthesis step explicitly chooses how to simplify these strings for display.
- This tension is expected to resurface any time a new fact type is added to the extractor (not just type strings) — the standing answer is the same: keep the fact raw, solve formatting downstream.
