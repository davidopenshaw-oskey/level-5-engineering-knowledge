# Prompt 1 of 5 — Angular `stableFactId()` bounded-key fix

Copy everything below the line into a fresh Claude Code session in this repo.

---

Real bug, found 2026-09-11: `pipeline/swift/phase-01-ast-extraction/02-build-module-evidence.ts`'s `stableFactId()` folds a fact's `primaryKey`/`secondaryKey` verbatim into `facts.fact_id`, which is that table's Postgres primary key (btree-indexed). A real ~28,000-character SwiftUI call-chain expression used as `primaryKey` broke Postgres's own btree index-row limit (`index row size 2816 exceeds btree version 4 maximum 2704 for index "facts_pkey"`). Fixed there via a `boundedIdComponent()` helper: any component over a length threshold gets replaced with a bounded prefix + a deterministic SHA-1 suffix, so the ID stays stable and readable but can't blow the index limit. Full write-up: `governance/roadmap/ios-oskey-dev/19-swift-family-synced-to-postgres-2026-09-11.md`.

`stableFactId()` is independently duplicated in `pipeline/angular-app-oskey-io/phase-01-ast-extraction/02-build-module-evidence.ts` — same unbounded design, never fixed there. Your job is to fix it correctly for this repo specifically — **not** a blind port of Swift's code, for a real reason found while scoping this: Angular's `call_expression` facts use `primaryKey: item.expression`, and real, current Angular `expression` values already reach up to 6,798 characters (confirmed in `governance/roadmap/consolidation/typescript.md` §2d cross-cutting section) — all currently inserting into Postgres successfully. Swift's fix used a 200-character bound; applying that same number here would re-ID thousands of real, currently-fine facts, and since this repo's facts already have real, paid embeddings, every re-ID means the old fact is deleted (stale ID pruned by `sync-facts.ts`) and a new one inserted with `embedding IS NULL` — real, silent, avoidable embedding loss and re-spend for facts that were never actually at risk.

## What to actually do

1. **Read `pipeline/angular-app-oskey-io/phase-01-ast-extraction/02-build-module-evidence.ts`'s real, current `stableFactId()`** (and `pipeline/swift/phase-01-ast-extraction/02-build-module-evidence.ts`'s fixed version, for the pattern — not to copy verbatim, the two files' `stableFactId()` input signatures differ).

Report the real numbers.

3. **Determine the real Postgres limit this needs to stay under**, don't assume Swift's. `facts_pkey` is a btree index; Postgres's real, hard ceiling is on the *post-TOAST-compression* size of the index row, not raw character count (confirmed empirically in `governance/roadmap/consolidation/typescript.md` §2d — an 8,330-byte raw synthetic value inserted fine on this same Postgres instance). If you have access to the local Postgres instance (`facts-postgres-index-local` docker container), do the same kind of real, empirical check that doc did: insert synthetic values of increasing raw length (start above today's real max, step up) into a scratch table with an identical single-column btree PK, find where it actually breaks, and use that finding — with a real safety margin — to choose your threshold. This is cheap (a local scratch table, not the shared `facts` table) — do it rather than guessing; it's the only way to actually know the real number instead of assuming it. If you genuinely don't have DB access in this session, say so explicitly and pick a documented, reasoned fallback instead.

4. **Pick a threshold with real, deliberate safety margin — not the bare minimum that avoids touching today's facts.** This repo's own patterns trend toward longer, more deeply chained expressions over time (longer template bindings, RxJS `.pipe()` chains, more so if a future design-system-driven rebuild leans further into this) — a threshold barely above today's real max (found in step 2) would leave almost no headroom and likely needs revisiting again soon. Two things to account for, not just "above today's single-field max":
   - **The combined worst case, not one field at a time.** A single `fact_id` can carry a bounded `primaryKey` *and* a bounded `secondaryKey` together — size your threshold against what the *combined* ID looks like when both are simultaneously at the cap, not just one field in isolation, and validate that combined worst case against the real empirical ceiling from step 3.
   - **It's fine if this re-IDs some of today's facts.** If a well-justified, safety-margined threshold happens to be below a handful of today's real longest values, that's an acceptable, small, known cost (a few facts get new IDs and need re-embedding) — better than picking a smaller number just to avoid it. Report how many current facts (if any) this affects, and their real re-embed cost via step 6 below, rather than reverse-engineering the threshold to make that number zero.
   
   Implement `boundedIdComponent()` (or equivalent) using the threshold you land on, applied to every `primaryKey`/`secondaryKey` component the same way Swift's version does. State your reasoning for the exact number chosen so a future session can judge whether it's still adequate.
