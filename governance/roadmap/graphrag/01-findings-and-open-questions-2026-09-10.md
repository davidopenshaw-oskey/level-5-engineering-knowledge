# GraphRAG-inspired architecture — findings and open questions

Real discussion from 2026-09-10, captured at the point the user asked for a dedicated folder. Status: **investigation, not a decision or a plan yet** — no architecture change has been agreed. This doc exists so the reasoning survives a session boundary, per this project's own documentation discipline.

---

## 1. The real motivating question

The current PRD-generation system (`mcp-server/skills/prd/skill.md` + `template.md`) is a single LLM call: one skill, one fixed template (User Stories / Technical Proposal / Acceptance Criteria / Constraints), one conversation that gathers evidence via tools (`search_facts`, `walk_cluster`, `get_graph_neighbors`) and writes the whole document in one shot. The user is not satisfied this is the right shape, on two grounds:

- Real, external tier-1 precedent (`governance/roadmap/market-research/21-findings-agent-prd-template-vs-dynamic-structure-2026-09-09.md`) shows spec-kit and Kiro decomposing generation into multiple stages/documents, not one call.
- If this POC is adopted, it moves into **gemini-enterprise** and becomes **event-driven**: a merge to prod triggers an automated pipeline (AST extraction → corpus update → vector upsert). The system's overall shape needs to make sense as one coherent architecture in that home, not stay a single hand-run LLM call.

## 2. A real distinction the tier-1 precedent doesn't fully capture

spec-kit, Kiro, and Devin's DeepWiki all work by **exploring the live repo at generation time** (reading files, grepping, walking real code fresh each session) — there is no separate pre-built fact/vector corpus standing between their agent and the source. This project's shape is different and deliberate: P2 never touches source directly, it only queries what P1 already extracted and embedded into pgVector. Only **P1** is genuinely analogous to an automated, continuously-triggered pipeline; **P2** is the part that's actually agentic, but the closer precedent for it is retrieval-augmented generation over a pre-built corpus, not a live-code-exploring coding agent.

This reframing is what sent the research toward GraphRAG, Anthropic's own multi-agent research system, and production code-knowledge-graph tools (Infigraph) instead of more spec-kit/Kiro-style precedent.

## 3. Real project history (not previously written down together)

- P1 (ts-morph for the TS repos; SwiftSyntax/tree-sitter for Kotlin/Swift) extracts real AST facts per repo.
- The **original** P2, for the three TS repos, was a real, four-level narrative-synthesis hierarchy, explicitly designed to fold the corpus down small enough for a limited context window — "even a local LLM," per the user directly:
  1. A **self-contained report per module**, with interfaces — the finest real narrative unit, built from capability-level evidence packs (`pipeline/<repo>/phase-02-inter-module-synthesis/01a-generate-capability-syntheses.ts` etc.).
  2. An **intra-repo, cross-module report**, joining that repo's own modules together.
  3. A **repo report** — the whole-repo rollup (`02-generate-repo-report.ts`).
  4. An **inter-repo report**, joining the three TS repos together. **Real state, checked 2026-09-10: this layer exists only as a deterministic JSON graph, not a narrative report.** `output/cross-repo-synthesis/*/enterprise-topology-graph.json` — 5 real runs, most recent 2026-08-29 — is real, generated output, but it's the edge-join data (later feeding `cross_repo_edges`), not an LLM-synthesized narrative document. No markdown "inter-repo report" was found anywhere in the repo. The `pipeline/cross-repo-synthesis/` script directory that produced this JSON no longer exists in the current pipeline folder — `pipeline/facts-postgres-index/build-cross-repo-edges.ts`'s own header says it replaces that script's output without reusing or importing it. So the real hierarchy that got built is 3 narrative levels deep (module → intra-repo → repo) plus one deterministic (non-narrative) inter-repo level — not 4 narrative levels.
- The plan was to feed these reports **directly as prompt context** to generate PRDs/impact analyses. This hit a real context-window wall as the corpus grew.
- The fix applied: index individual atomic AST facts in pgVector instead, and retrieve only the relevant subset per request. This is documented as a proposed (not yet formally accepted) direction in `governance/adrs/adr-005.md` — **status still "Proposed — not yet decided," dated 2026-09-01, never marked Accepted.**
- The MCP server and the one-hit skill+template PRD generator were built **after** the pgVector atomic-facts work was already in place — the one-hit experiment is the newest layer, not a parallel decision made at the same time as the pgVector pivot.
- This is where the system is today: the current one-hit skill+template PRD generator, querying only the flat `facts` table.

**Real, user-confirmed judgment**: the engineering reports themselves were good quality. The only known gap is coverage — some repos were added to P1 after the reports were last generated. Scope of that gap not yet fully confirmed (see §6) — benched as a separate investigation, not solved here.

**Kotlin (android-intercom-oskey-io) and Swift (ios-oskey-dev + 4 swift-*-kit repos) P1 is WIP, real state checked 2026-09-10**: all 6 repos have real capability-pack output (`sync-facts.ts`'s actual input format) already on disk — `android-intercom-oskey-io` is comparatively mature (51 capability-pack files, latest run 2026-09-09); `ios-oskey-dev` and the 4 swift-kit repos are thin/early (1-6 files each, latest runs today, 2026-09-10), consistent with the user's own "WIP" characterization. None of the 6 have any narrative-synthesis layer (no phase-02-equivalent exists for them yet) — only the pgVector/atomic-facts step applies, via the same generic, repo-agnostic `sync-facts.ts` (driven by a `REPO_NAME` env var, not a repo-specific script). **Whether these 6 repos' facts have actually been synced into live Postgres yet is not confirmed by this file-based check** — the user's own caveat ("maybe some of that is also wip") stands; would need a live Postgres check (`SELECT repo, count(*) FROM facts GROUP BY repo`) to confirm, not assumed here either way.

## 4. Real external research findings (2026-09-10, live web search/fetch)

Primary sources fetched and read directly, not inferred from snippets, matching this project's existing sourcing-rigor standard.

- **Infigraph** ([github.com/intuit/infigraph](https://github.com/intuit/infigraph)) — the closest real analog to this project's own P1/P2 split. AST-based (tree-sitter, 59+ languages), **zero LLM dependency at indexing time**, deterministic graph build. Multiple analysis types (PR review, blast radius, impact analysis, dead-code detection, taint analysis) are all **different traversal algorithms over the same graph**, not different LLM skill files. LLM calls are optional, narrow, query-time-only (narrative enrichment on top of an already-computed structural result). Real validation that "different document types" doesn't require re-prompting an LLM to reorganize evidence differently every time — some outputs can be purely deterministic.
- **GraphRAG (Microsoft Research)** ([microsoft.github.io/graphrag](https://microsoft.github.io/graphrag/), [blog](https://www.microsoft.com/en-us/research/blog/graphrag-improving-global-search-via-dynamic-community-selection/)) — the closest real analog to this project's corpus/RAG shape specifically. **Index time (paid once)**: entity/relationship extraction → hierarchical community detection → an LLM summarizes each community once, producing pre-computed "community reports" at multiple abstraction levels. **Query time**: local search (entity-level detail) vs. global search (uses the pre-computed community reports) are different report types from the same graph. Dynamic global search adds a cheap LLM *classifier* pass to prune irrelevant communities before the expensive summarization step — real, measured **77% cost reduction** (1,500 reports pruned to ~470) with comparable quality.
- **Anthropic's own multi-agent research system** ([anthropic.com/engineering/built-multi-agent-research-system](https://www.anthropic.com/engineering/built-multi-agent-research-system)) — orchestrator ("Lead Researcher") plans and spins up 3-5 parallel subagents, each with an explicit objective, output format, and boundaries. After synthesis, a **separate, dedicated `CitationAgent` pass** re-checks that claims are properly attributed to sources — verification as its own stage, not folded into drafting. Real cost data: ~4x tokens vs. single chat, ~15x for the full multi-agent run; justified only for tasks needing heavy parallelization or exceeding one context window — not a free win.
- **Weaker source, flagged honestly**: the Agentic RAG SoK survey (arXiv 2603.07379) was fetched but didn't yield its detailed verification-pattern taxonomy in the extracted text — only high-level mentions (Self-RAG, Reflexion, AttributedQA). Treat as a pointer to read directly, not a confirmed finding.

## 5. Real schema/architecture audit (2026-09-10)

Checked live against the actual files, not assumed:

- `pipeline/facts-postgres-index/schema-proposal.sql` — three tables only: `facts` (flat, one row per atomic AST fact, own 768-dim embedding, no hierarchy), `cross_repo_edges` (flat pairwise edge list), `embedding_calls` (cost accounting). **No table or structure anywhere resembling a precomputed cluster/community summary.**
- `_shared/search.ts` does pure vector search over individual raw facts. Its own header documents that adding a keyword/full-text signal was tried and explicitly rejected (real regression on one query, no benefit on others). Its own `DEFAULT_RESULT_LIMIT` comment records that one real query needed k≈25-30 to surface its target fact, a different real query needed k≈96 — **documented, real evidence that a single flat retrieval mechanism doesn't serve differently-scoped questions well.** This is exactly the problem GraphRAG's local/global split exists to solve.
- `_shared/graph-traversal.ts` — `walk_cluster`/`get_graph_neighbors` do a **live BFS at query time**, every request, discarded afterward. Nothing about a traversal is precomputed or persisted.
- **A real GraphRAG-shaped artifact already exists in this repo, just disconnected**: `pipeline/<repo>/phase-02-inter-module-synthesis/` (see §3) already produces a hierarchical, cited, confidence-tagged synthesis — structurally close to GraphRAG's community reports. But `sync-facts.ts`'s own header states: *"Does NOT import anything from any phase-02-inter-module-synthesis/_shared/ — this stays fully independent of the existing LLM-synthesis pipeline."* `adr-005.md` is the recorded reasoning for that split (impact analysis → pure graph traversal; PRD → raw-fact retrieval with narrow on-demand synthesis; whole-module narrative → a *different* destination, periodic sanity/health reporting) — **and that ADR is still open, never accepted.**

## 7. Real, newly-found bug: cross-repo/intra-repo edge builders are not scoped per repo

Found while confirming the user's own question ("does the cross-repo sync script have to run even if only one repo changed — correct?"). **Answer: yes, and more binding than expected, with a real correctness risk attached.**

- `build-cross-repo-edges.ts` hardcodes specific repo names directly in its queries (`WHERE repo = 'firebase-oskey-dev'`, `WHERE repo = 'angular-app-oskey-io'`) and always does `DELETE FROM cross_repo_edges WHERE connection_type = 'HTTP_API_CALL'` — every row of that type, corpus-wide — before rebuilding. Not incremental; a full recompute every run.
- `build-intra-repo-edges.ts` ([build-intra-repo-edges.ts:134](../../../pipeline/facts-postgres-index/build-intra-repo-edges.ts#L134)) takes one `REPO_NAME` and inserts edges only for that repo — but its delete has **no repo filter**: `DELETE FROM cross_repo_edges WHERE connection_type = 'INTRA_REPO_CALL'` removes every repo's intra-repo edges, then reinserts only the one repo's. Running this for repo A silently wipes B, C, D's intra-repo graph data from Postgres unless they're re-run in the same session immediately after.
- **Not previously known** (confirmed directly with the user, 2026-09-10). Harmless today under a manual, all-repos-together workflow; a real landmine for any event-driven "merge to prod triggers just that repo's pipeline" design, where these scripts would need to either recompute for all repos every time (expensive, not really incremental) or be fixed to scope their deletes by repo first.

## 8. The idea on the table (not decided, not built)

**Superseded 2026-09-11, see §10 — kept intact below because the reasoning here is what led to the correction, not because it's still the live plan.** This section frames GraphRAG's report tier mainly as a *retrieval-routing* mechanism ("search the summaries to find the right area, then search the facts"). §8c and §10 found that framing doesn't hold up against this project's own real evidence — the report tier's genuine value turned out to be as a *synthesis-scoping* unit (small, focused write-ups per capability), not a search shortcut. Read on for how that reasoning developed, but treat §10 as the real conclusion.

A two-tier retrieval design, mirroring GraphRAG's community-report/entity split while preserving this project's existing real-fact-citation guarantee:

- A new table, sibling to `facts` (e.g. `capability_summaries`), one row per capability/module/repo report, own `embedding vector(768)`, same index pattern as `facts.embedding` — no schema redesign, just an added tier.
- Query flow becomes two hops: (1) a new `search_facts_over_reports`-style tool vector-searches the summary tier first, to answer "which capability/module is this request even about," against a far smaller row count; (2) `search_facts`/`walk_cluster`/`get_graph_neighbors` then run scoped to what step 1 found relevant, instead of searching the whole flat corpus — directly attacking the k=25-vs-k=96 problem in §5.
- Final citations still trace only to real `fact_id`s from step 2 — the report tier only ever routes, it is never itself quoted as evidence. `checkFabrication` stays exactly as strict as today.
- **Real, unresolved tension flagged, not solved**: the report tier is only as fresh as its last phase-02 run — a staleness axis raw facts don't have (a fact re-extracts whenever P1 reruns; a report is only as current as whenever phase-02 last ran over it). This needs a real answer before the two-tier design goes further, not an assumption that it's fine.
- Alternative shape raised but not chosen either way: one combined table (reports and facts embedded together, distinguished by a `granularity` column) instead of two separate tables/tools. Not decided.

## 8b. Real, current decision narrowing the two-tier idea's reach (2026-09-10)

A concurrent peer session working on the swift repos asked the user whether to build the engineering-report layer (the narrative-synthesis hierarchy) for the Kotlin/Swift repos, or just the pgVector step. **The user chose just the pgVector.** So `android-intercom-oskey-io`, `ios-oskey-dev`, and the 4 `swift-*-kit` repos will only ever have the flat atomic-fact tier, not a report tier — at least until this is revisited. This means the two-tier idea in §8, if built, would only ever cover the 3 TS repos (`angular-app-oskey-io`, `firebase-oskey-dev`, `node-iot-api-oskey-io`) on its report side; the other 6 repos would need to fall back to fact-tier-only retrieval (i.e., today's behavior) regardless. Any two-tier design needs to handle "no report exists for this repo" as a real, permanent case for a meaningful subset of the corpus, not an edge case that closes over time.

## 8c. Real, already-existing evidence bearing directly on "is the report tier the right lever" (found 2026-09-10, from prior 2026-09-05 work — not new research)

Before investing in fixing up the engineering reports, checked whether this project had already tested something like this. **It had — and the real result reframes §8 materially.**

`governance/roadmap/facts-serving-strategy/15-workflow-clustering-and-angular-ux-facts.md`'s "Task 1: workflow clustering" is functionally the same idea as §8's report-tier-as-routing-layer — a curated, pre-built, embedded summary unit above individual facts, meant to give vector search a stronger anchor. **It was explicitly benched, never built**, for a real sequencing reason: a cluster's auto-generated description would inherit the same semantic poverty as the facts composing it, so clustering before the underlying facts were richer would just recreate the same failure one level up. It remains only a hypothesis ("the best-evidenced candidate," never verified) for one specific failure mode: **recall** (the right fact never reaching the LLM's context at all).

A *different* mechanism — query decomposition + LLM reranking — was actually built and tested on the same two real cases (Q1a/Q1b), per `governance/roadmap/market-research/02-findings-retrieval-architecture-2026-09-05.md`:
- Two hybrid lexical-retrieval attempts (BM25, `pg_trgm`) were tried first and **failed** — real, measured regressions, root-caused to naive-keyword query pollution.
- Retrieve-broad-then-rerank (vector top-150 → one bounded LLM call reranks to top-15) was tried instead. **Real, decisive result on Q1b** (the harder, previously-open gap): target fact reached reranked position #10; its Angular-side counterpart surfaced in evidence for the first time in the whole investigation. 2 LLM calls total, near-zero cost. Strong converging external precedent: Databricks reports up to 3x retrieval-quality gain from reranking alone at ~0.3% latency cost; Claude Code itself abandoned embeddings-based RAG for agentic search, for precision/freshness reasons this project independently rediscovered.

**The same investigation separated two genuinely different failure modes, and this is the load-bearing part:**
- **Recall failure** (Q1b) — the right fact never reaches context. Reranking fixed this; workflow clusters were only ever a hypothesis for it.
- **Judgment failure** (Q1a) — the right fact *did* reach context (rank #22-24, sitting in the LLM's evidence) and **the LLM still never cited it.** No retrieval mechanism of any kind — not clusters, not reranking, not a report tier — fixes this. It needs a different intervention entirely (Task 3: caching real business-rule/reference-doc context into the prompt, e.g. `Oskey Personas and Authority models.md`), not better evidence-finding.
- A further real wrinkle, directly relevant to PRD-vs-impact-analysis specifically: reranking **helped** Q1b (a narrow, specific-flow question) but was an honest **non-improvement** on Q1a (a genuine breadth/impact-analysis question, where the reranker's own defensible read was that wide evidence was correct, not a tighter cut). Different document/question *types* plausibly need different retrieval shapes — not a single universal fix, report-tier or otherwise.

**Conclusion, directly bearing on the user's question ("is this the right approach to get my PRD/impact-analysis output"):** based on this project's own real, already-collected evidence, fixing up the engineering reports is not the best-evidenced next lever for that specific goal. It's an untested hypothesis for one failure mode (recall) that already has a cheaper, tested, working alternative (reranking) sitting next to it in the same investigation — and neither touches the separate, real judgment failure this project already found, which needs Task 3-style context, not more retrieval. The reports' standalone value as a human wiki is real and untouched by this conclusion; as the mechanism to fix PRD/impact-analysis generation specifically, the evidence points elsewhere first — reranking, then judgment-context — before report-tier retrieval.

## 10. Where this lands — real conclusion, 2026-09-10/11

This investigation started from a real, legitimate question — is the one-hit PRD skill+template the right architecture — and went through a real course-correction along the way: GraphRAG was introduced (§4) mainly as a *retrieval-routing* idea (pre-built summaries to help vector search find the right area first). §8c found this project had already tested that exact idea twice — once as its own "workflow clusters" concept (shelved, unbuilt, only ever a hypothesis), once as the GraphRAG framing itself — and both times a simpler, already-tested mechanism (reranking) either already worked or made the report-tier idea unnecessary to prove out further. **The report tier's real, defensible value turned out to be something different: not a search shortcut, but a synthesis-scoping unit** — small, focused write-ups per capability instead of one call reasoning over a large mixed pile of evidence. That reframing is what the three real conclusions below are built on, and it directly answers this project's original 2026-09-XX plan (module reports → capability → repo, folded down for context-window size) and the pgVector pivot that followed it (ADR-005): both were real, sound moves: the reports as a synthesis pattern were right, and pgVector as the storage/context-window fix was right. What was missing was decomposing *generation* the same focused way the reports once were, instead of collapsing back into one big call once retrieval replaced them.

### Three real conclusions

**1. pgVector's storage schema stays as-is.** `facts` + `cross_repo_edges`, as designed, do not need a report/community-summary tier added on top. One separate, smaller, already-validated improvement remains worth shipping regardless of anything else here: **reranking** (retrieve a wide, cheap candidate pool, then a bounded LLM call picks the true best subset) — real, tested, decisive fix for Gap A (recall) per §8c, not yet shipped to production.

**2. The one-hit PRD skill+template should be decomposed — by affected capability/module, not (only) by template section.** Two different decomposition axes came up in this investigation, and they fix different things:
   - **By capability/module** (a variable count per request — however many parts of the codebase a given business request actually touches): a small, focused synthesis pass per capability, reasoning only over that capability's own evidence. This is the real, evidenced fix for **Gap B** (the AI has the right fact in its evidence and still doesn't cite it) — the failure was evidence from one capability getting lost among a large, undifferentiated pile from others, and this project's own original module/capability reports already proved this focused-write-up pattern produces good, cited, confidence-tagged output when scoped narrowly.
   - **By template section** (a fixed ~4-5: User Stories, Technical Proposal, Acceptance Criteria, Constraints): already tested once, narrowly (`40-...md`, the low-freedom Technical-Proposal-only experiment) — real, proven to cut tool-call cost (6 vs 26+) and produce a more honest result (a correctly-earned `[NEEDS CLARIFICATION]`). A real, separate benefit, not the fix for Gap B specifically.
   - **The two combine, in this order**: fan out by affected capability (variable N, fixes Gap B) → collate the resulting focused write-ups into whichever template sections are actually needed (fixed ~4-5, the already-tested cost/focus shape). This also directly answers the session's original, opening question about producing *different kinds of documents* from the same corpus: steps 1-2 (find relevant capabilities, synthesize each focused write-up) stay the same regardless of output type; only the final collation step changes per document type (a PRD collates one way, an impact-analysis doc another) — the same shape Infigraph (one graph, many traversal-driven analyses) and GraphRAG (map-reduce over independently-contributed community reports) both use in their own domains.
   - This also gives the separately-parked "series of skills" idea (`mcp-direction/44-...md` §1) its second real data point and a principled axis to decompose along — it was parked specifically for lack of one; this investigation, read together with the low-freedom experiment, is that second point.

**3. Real bugs/WIP/dead-ends found along the way get cleaned up, but carry no architectural weight** — they don't gate 1 or 2 above:
   - `build-cross-repo-edges.ts`/`build-intra-repo-edges.ts`'s global-delete-then-partial-rebuild scoping bug (§7) — a real correctness risk, worth fixing regardless of any event-driven ambitions.
   - The orphaned `pipeline/cross-repo-synthesis/` script (§3) — superseded by `build-cross-repo-edges.ts`, no longer present in the pipeline folder; worth confirming it was deliberately retired, not silently lost.
   - `adr-005.md` — still formally "Proposed," never marked Accepted, despite most of its direction having since been built. Worth a real status update reflecting what's now decided (§10 here) versus what's still open.
   - Known coverage gaps stay benched, not solved by this conclusion: the 6-repo engineering-report coverage gap (§6), and the Kotlin/Swift report-scope decision (§8b) — both real, both separate investigations.
   - **Update 2026-09-11**: the 5 Swift repos' facts are now genuinely synced into Postgres for the first time (33,714 facts across 7 modules, no embeddings yet — separate paid step) — see `governance/roadmap/ios-oskey-dev/19-swift-family-synced-to-postgres-2026-09-11.md`. This resolves §3's "not confirmed by file check" caveat for the Swift repos specifically; Kotlin (`android-intercom-oskey-io`)'s own sync status is still separately unconfirmed. That same session found a **real, same-class bug** worth adding to this cleanup bucket: `stableFactId()` is independently duplicated across all 5 pipeline folders (TS x3, Kotlin, Swift), and a ~28,000-character real Swift call-chain expression used verbatim as a primary-key component broke Postgres's own btree index-row limit. Fixed in the Swift copy (oversized components now get a bounded prefix + deterministic hash); **the same latent risk was flagged, not fixed, in the other 4 repos' own copies** — none of their real code has apparently been long enough to trigger it yet. Same pattern as §7's edge-builder bug: duplicated per-repo pipeline logic carrying an unstated assumption that hasn't been checked everywhere it's copied.
   - **Update 2026-09-11, later same day — a *third* instance of this exact pattern, found while extending `build-intra-repo-edges.ts` to Kotlin/Swift** (`prompt-6-kotlin-swift-intra-repo-edges.md`): whichever script builds `resolved-engineering-graph.json` computes its own `sourceCallFactId` independently rather than reading the real fact_id `02-build-module-evidence.ts` actually produces — and it was never updated with the `stableFactId()` bounding fix, so it still emits unbounded IDs (one Swift case ran to 28,814 bytes, aborting the first load attempt; transaction rolled back cleanly, verified 0 rows left behind). Fixed defensively in the loader (filter out any edge whose `sourceFactId` isn't a real, currently-live `fact_id` before insert — same never-invent-a-reference principle applied everywhere else, not a guess at repair). **Real, quantified cost, not hypothetical**: Kotlin lost 1 of 3,590 built edges (0.03%, negligible); **Swift lost 1,663 of 8,734 (19.0%)** — a real, non-trivial coverage gap, not wrong data, just silently missing. The actual root-cause fix (make the resolved-graph builder read real fact_ids instead of recomputing its own) is out of scope for the loader and not yet done — a real, open item for whoever next touches Swift's graph-resolution step.
