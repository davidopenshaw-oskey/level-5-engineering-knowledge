## Facts about this environment you must not get wrong

- **DB:** container `facts-postgres-index-local` (port 5433), database `facts_index`, user `facts_index`. It is live and shared; the wiki works from a copy. Use `</dev/null` with `docker exec ... psql -c`, or it can hang.
- **Round-2 baseline:** `governance/roadmap/call-resolution-same-repo-edges/03-baseline-round2-before-2026-10-01.json` (taken by the coordinator 2026-10-01 21:11 UTC, read-only). android-intercom: 10,029 facts, current run `20260925_124505-ee4493bf`; call resolution today: 4,849 `unresolved`, 428 `resolved_via_same_package`, 228 `resolved_via_import`; slices `INTRA_REPO_CALL` 3,716 (md5 `9317f78f…`) and `HTTP_API_CALL` 5 (md5 `a084f18b…`).
- **Upstream:** android-intercom tracks branch `develop`. On 2026-10-01 `develop` = `ee4493bf`, the indexed commit and the clone at `output/clones/android-intercom-oskey-io`. `00-scan-repo` re-clones, so run `git ls-remote git@github.com:oskey-io/android-intercom-oskey-io.git refs/heads/develop` **before any re-extract**. If it moved, **stop and tell the user**: a moved branch mixes upstream changes into your gate.
- **`fact_ref` = `sha1(fact_id)`, generated by Postgres** on `facts` and on both ends of `cross_repo_edges`. **Never change what feeds `stableFactId()`.** Put new information in new fields. Your gate reports `fact_id` **and** `fact_ref` diffs (compare `fact_ref`s, not raw IDs through a line-based tool). The expected answer is 0 changed, 0 pruned.
- **Legacy call fields are frozen** (round-1 decision AM-1): `resolutionMethod`, `declarationFile`, `declarationModule` and every other field that exists today keep their current values, never renamed or re-meant. Step 04 builds the live `INTRA_REPO_CALL` slice from them, and that slice must stay **md5-identical**. Member-level results go in the `member*` fields only.
- **The `member*` fields are read generically, not "for Swift":** W6 discovery (`build-cross-repo-edges.ts` ~:1675) picks up any repo with `memberResolutionStatus = 'resolved'` and a same-repo `memberDeclarationFile`. `descriptionFor` adds `-- calls method: …` for any `call_expression` with `memberResolutionStatus = 'resolved'`, and **drops** the legacy `-- resolves to:` segment when the member tier is `resolved_via_caller_type` / `resolved_via_property_type` / `resolved_via_supertype` and the files differ. So: (a) every member-resolved Kotlin call changes its description text and needs **re-embedding (spend)**; (b) reusing those tier names opts Kotlin into the collision rule, so say whether that's correct for Kotlin. Measure both in the gate; don't assume.
- **W6 target kinds:** W6 targets only declaration facts whose kind ends `_method` or is `function_declaration`. Check which Kotlin declaration kinds exist (`factsPerRepoModuleKind` in the baseline) and whether your targets land on them; report any that don't.
- **Hub fence:** W6 fences callees whose fan-in exceeds `exp(Q3 + 3·IQR)` of log fan-in per repo, falling back to the pooled fence when IQR = 0. Expect Compose/UI hubs; report them, don't fence by hand.
- **CLAUDE.md rules that bind you:** always dynamic (walk the real syntax tree; no hand-typed lists of types, properties or methods); cheap bounded tests first; keep a before baseline and compare; write findings as they happen; delete scratch scripts and scratch DBs afterwards (`DROP DATABASE` only on `facts_index_scratch_k_*`); **no LLM calls; no `gcloud`; any embedding spend is flagged with a fact count and token estimate (measure Kotlin's tokens/fact from `embedding_calls` or a sample; don't reuse Swift's 143) and waits for the user.**

## Procedure

**K1, investigate and confirm the contract (read-only).**
- How Kotlin call sites look in the real tree: member calls on properties (`viewModel.foo()`), on companion/objects (`Foo.bar()`), on `this`/implicit receivers, extension functions, constructor calls, scope functions (`let`/`apply`/`with`), chained calls. - What type information the extractor already has, or could get from syntax alone: property declared types (`val x: Foo`, `val x = Foo(...)`, `by inject<Foo>()`/`by viewModels<Foo>()`-style delegates if present), constructor parameters, class membership of `function_declaration` facts.
- Map the round-1 contract onto Kotlin: which `member*` fields and tiers apply, which need a Kotlin-specific tier name, and what `callerMember`/`callerMemberKind` mean here. Propose amendments where Kotlin differs, with the reason.
- Estimates (labelled as such): how many of the 4,849 unresolved calls and of the 656 resolved in-repo calls each tier would resolve; how many descriptions would change (= the embedding count).
