## 2. The contract (Interface contracts: proposed by the coordinator, to be confirmed or amended by Lane S in writing before code)

### 2a. `call_expression` facts: additive fields (Swift now, Kotlin later)

> **Superseded 2026-10-01 by Lane S's S1 amendments (AM-1 to AM-8, O-1, `propertyScope`), approved by the user. See the Build log entry "[Lane S] S1 CONTRACT CONFIRMED / AMENDMENTS" and the coordinator's approval entry after it.** In short: the legacy call fields (`resolutionMethod`, `declarationFile`, `declarationModule`, `declarationRepo`) stay frozen at today's values; the member-level result goes in new `member*` fields; the property type field is `declaredTypeName` (not `declaredType`, which Kotlin already uses with a different meaning). The TS-name plan below is kept as written, for the record.

The same names and meanings the TypeScript extractors already emit, so `intraRepoCallDeclaredJoin` (W6) can read them unchanged:

| Field | Meaning | When set |
|---|---|---|
| `resolutionStatus` | `"resolved"` / `"unresolved"` | every call fact. Set `resolved` only when `declarationFile` + `declarationLine` point at a real declaration fact |
| `declarationLine` | line of the callee's declaration | when resolved |
| `declarationMethod` | the callee member's name (`userSendInvitation`); `null` when the callee is a type (constructor / bare type reference) | when resolved |
| `declarationClass` | the callee's enclosing type (`OSKCKUserInvitesService`); for an extension member, the extended type | when resolved and the callee is a member |
| `calleeMember` | the called member's name as written at the call site (last segment of the callee), whether resolved or not | every call with a member segment |
| `callerMember` | the enclosing member of the call site, **including computed properties and accessors** (`body`, `headerView`), with `callerMemberKind` (`function` / `init` / `computed_property` / `closure_in_property` …) | every call fact where one exists |

**Unchanged, never renamed or re-meant:** `resolutionMethod` (gains new values only, e.g. `resolved_via_property_type`, `resolved_via_type_member`, `resolved_via_caller_type`), `declarationFile`, `declarationModule`, `declarationRepo`, `calleeExpression`, `callerFunction`, `callerClass`.

**Hard rule: fact ID inputs do not change, because `fact_ref` follows them.** `fact_ref` is not a separate key: it is a Postgres-generated column, `encode(digest(fact_id,'sha1'),'hex')`, on `facts` and on both ends of `cross_repo_edges` (`source_fact_ref`/`target_fact_ref`), per ADR-010. Live-checked 2026-10-01. Any change to a `fact_id` therefore changes its `fact_ref`. That breaks the wiki's citations and joins (the wiki contract: "`fact_ref` stays stable across a re-extract at the same commit"), and it breaks traversal, which joins on `fact_ref` (`mcp-server/db/graph-traversal.ts:262-268`). The pre-sync gate compares `fact_ref`s as well as `fact_id`s and reports both. A Swift call fact's ID is built from `calleeExpression`, `callerFunction` and `callerClass` (live sample: `call_expression|iOS App|<file>|userInviteService.userSendInvitation|sendUserInvitation|OSKInviteGuestViewModel|#1`). `callerFunction` is present on only **5,640 of 17,442** iOS call facts. Filling it in for computed properties such as `body` would change about 11,800 IDs, losing their embeddings and re-pointing their edges. That's why the new caller information goes in `callerMember`, and `callerFunction` stays exactly as it is.

**Open for Lane S to propose:** constructor calls (`OSKAppViewModel(...)`): target the explicit `init` `function_declaration` when one exists, else the type declaration with `declarationMethod: null`? (W6 targets only `*_method` / `function_declaration` kinds; type-level targets stay `PACKAGE_SYMBOL_USE`'s job cross-repo.)

### 2b. `model_property` facts: additive

| Field | Meaning |
|---|---|
| `declaredType` | the property's type: from the type annotation; failing that, an initializer of the shape `TypeName(...)`, `TypeName.shared`, `TypeName.<static>`; generic arguments and optionality stripped to the base name; anything else `null` (no guessing) |
| `declaredTypeSource` | `annotation` / `initializer` / `null` |

### 2c. Resolution order (Swift, step 01)

For each call, after today's `self`/`super` handling and **before** today's flat root lookup:
1. `<own property>.member(...)`: the root is a stored property of the caller's type (or of an extension of it) with a `declaredType` → look up `(declaredType, member)`.
2. `TypeName.member(...)` / `TypeName.shared.member(...)` / `TypeName.<static prop>.member(...)`: look up `(TypeName, member)`.
3. Bare `member(...)` and `self.member(...)`: look up `(callerType, member)` first, then fall back to today's flat lookup.
4. Today's root-only behaviour for everything else, unchanged.

Every `(type, member)` lookup checks the repo's own table first, then the imported kits' **public/open** tables (the existing `resolved_via_import` loading, `01-extract-ast-evidence.ts:112-170`). If a lookup finds more than one declaration (overloads), it resolves to the one with a matching argument-label set if exactly one matches; otherwise it stays unresolved, with the candidates' count recorded. No guessing.

### 2d. Edges (Lane E)

- **Same-repo:** `INTRA_REPO_CALL_DECLARED` (W6), unchanged in type and semantics. Discovery already keys on `resolutionStatus = 'resolved'` plus `declarationFile` (`build-cross-repo-edges.ts:1640`), so Swift repos join automatically once 2a lands. Lane E must check that W6's fallback match by `symbol_name` (`:1698`) works with the Swift `function_declaration` `symbol_name` format (properties are stored as `Parent.name`; check functions) and that the switch-off reader (`:1622-1631`) behaves correctly for the Swift repos.
- **App → kit methods:** a **new connection type**, proposed name `PACKAGE_METHOD_CALL`. Source: an app call fact with `declarationRepo` ≠ its own repo and `declarationMethod` set. Target: the kit's `function_declaration` fact at `declarationFile:declarationLine`. `resolved` only with a target; otherwise `unresolved` with a reason. `provenance = ast_derived`. The existing 389 `PACKAGE_SYMBOL_USE` edges stay byte-identical (user's monitoring case, 2026-10-01: old behaviour unchanged, new edges visible separately). Traversal needs no change (`mcp-server/db/graph-traversal.ts:262-268` has no type allowlist). Final name confirmed by the user before code.
- **node-iot:** W6 currently reads the same `intraRepoEdges.enabled = false` switch as the resolved-graph builder. Lane E proposes how to dry-run W6 for node-iot without turning `INTRA_REPO_CALL` on (e.g. a separate key), and reports the numbers.

#### Amendments (each with its reason)

**AM-1 (blocking): the legacy resolution fields are frozen on every call fact.** `resolutionMethod`, `declarationFile`, `declarationModule` and `declarationRepo` keep exactly today's values, including for calls the new tiers resolve or re-point. That means §2a's "`resolutionMethod` gains new values" is withdrawn; the tier goes in a new field (AM-2). Three readers depend on the legacy values, and changing them breaks A7 and §2d:
- `PACKAGE_SYMBOL_USE` (`build-cross-repo-edges.ts` ~:815-860) selects `resolutionMethod = 'resolved_via_import'` with a foreign `declarationRepo`, and matches on `declarationFile` plus the leading identifier. **41 of its 389 sources** are `Type.shared.method()`/`Type.member()` calls that tier 2 resolves to the member (e.g. `OSKUIToastMessageService.shared.publish`). Re-pointing them, or relabelling the tier, changes or drops edges in a slice that must stay byte-identical. Conversely, a newly resolved cross-repo call labelled `resolved_via_import` would add edges to it.
- Swift step 04 (`04-build-resolved-graph.ts:229-280`), the source of the 5 Swift `INTRA_REPO_CALL` slices, branches on `resolutionMethod === 'unresolved' || !declarationModule` and copies `declarationFile`. Filling these in for newly resolved calls moves calls from `unresolved` to `probable` in slices that A7 says stay byte-identical.
- `descriptionFor` (`sync-facts.ts:430-434`, `kotlinCallResolutionDoc`) prints ` -- resolves to: <declarationFile> (<resolutionMethod>)` for every resolved call, so any change is an embedding.

**AM-2: the member-level result lives in new, prefixed fields, so an unchanged W6 ignores them.** On `call_expression` evidence:
`memberResolutionStatus` (`resolved`/`unresolved`; present whenever the call has a member or bare-call target to look up), `memberResolutionMethod` (`resolved_via_property_type` | `resolved_via_type_member` | `resolved_via_caller_type` | `resolved_via_initializer`), `memberDeclarationFile`, `memberDeclarationLine`, `memberDeclarationModule`, `memberDeclarationRepo` (only when not the call's own repo, the legacy `declarationRepo` convention), `memberDeclarationClass`, `memberDeclarationMethod` (`init` for an initializer target), `memberUnresolvedReason` (when unresolved: e.g. `ambiguous_overload`, `property_untyped`, `no_member`, `root_not_property_or_type`, `implicit_initializer`) and `memberCandidateCount` (overloads), plus `calleeMember`, `callerMember` and `callerMemberKind` as in §2a.
*Reason:* the TS names (`resolutionStatus`/`declarationLine`/`declarationMethod`/`declarationClass`) would put the new line next to the frozen legacy `declarationFile`. W6 discovers by `resolutionStatus = 'resolved'` and joins on `declarationFile:declarationLine` (`:1640`, `:1688-1695`), so wherever the member's file differs from the legacy file it would join the wrong file. That's **~150 calls** (iOS 97, cloud-kit 22, ui 3, ble 3, webrtc 30). They'd become wrong edges the moment anyone ran `pipeline:edges` before Lane E's change. With the prefixed names, an unchanged W6 sees nothing, so syncing Lane S's facts can't create an edge in any order. **Request to Lane E** (Lane E owns the change): W6 and `PACKAGE_METHOD_CALL` read `memberDeclarationFile`/`Line`/`Method`/`Class` when `memberResolutionStatus = 'resolved'`. The precedent is W6's own `aliasedDeclaration*` override (W1).

**AM-3: the property field is named `declaredTypeName`, plus `declaredTypeSource`, with no `declaredType`.** Kotlin's `model_property` already ships `declaredType` as the **full** type text (`List<LanguageOption>`), and `descriptionFor` prints `declaredType` as a fallback (`sync-facts.ts:252`). A Swift `declaredType` holding the stripped base name would mean something different under the same name. It would also change about **3,740** Swift property descriptions (iOS ~2,405, cloud-kit ~661, ui ~255, ble ~83, webrtc ~319, all scopes): about 0.53M tokens. Whether Swift should also carry the full annotation text as `declaredType`, the Kotlin-consistent meaning that changes those descriptions, is a separate `descriptionFor`/spend decision for Lane E and the user. I don't emit it now.

**AM-4: a `TypeName.<static>` initializer takes the static property's own type, not `TypeName`.** §2b reads `TypeName.<static>` → `TypeName`, which is a guess for any static that isn't `Self`-typed.
