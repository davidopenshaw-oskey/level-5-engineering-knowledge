**Status:** ✅ Stages 1-3 done, plus a Stage 4 pivot (prompt caching, not the originally-planned A1 decision) — all against real data, real cost now down ~40% total for `building`. Decision A1 remains open, deliberately deferred.
**Created:** 2026-08-03

*Fourth plan under the numbered-plan-file convention (see `00-capability-based-module-synthesis.md`, `01-cross-module-dependency-graph.md`, `02-structural-narrative-synthesis-tiers.md`). This plan is where the "Economics reassessment" pause in `02-structural-narrative-synthesis-tiers.md` resolves into concrete, sequenced work. It executes on the findings validated across two rounds of cross-model review, captured in full in `governance/roadmap/phase 2-llm q&a/01 facts-vs-decisions-for-review.md` — that document is the evidence trail; this one is the execution order. Work through one stage at a time; don't start a stage whose inputs depend on a prior stage's results.*

---

## Why this exists

A real, full-cost run of the capability-based synthesis flow — one module, `building`, one repository, one model — cost $4.80 and pushed the Anthropic account balance negative. That single number forced a step back from tactical cost-tuning (caching, doc-scoping) to an architectural question: with 15+ repositories in scope and growing, does this approach scale at all, and where exactly does its cost actually come from?

Two rounds of independent cross-model critique (Claude, OpenAI, Gemini reacting to a strawman data model, then Gemini and OpenAI validating a synthesized facts-vs-decisions list) converged on the same core findings, and a real measurement taken afterward corrected a claim this project had made about its own architecture without checking it. The full reasoning and evidence lives in the facts-vs-decisions document; this plan exists to turn the parts of that discussion that are actually settled into ordered, executable work — without waiting on the parts that are still genuinely open (whether to build a full persistent knowledge model, how staged cross-repo connectivity detection eventually works, and so on).

**Guiding principle carried into every stage below:** economics must be traceable with the same discipline this project already applies to facts. Nothing here should ship without being able to say, afterward, exactly where the tokens went and why. Approaching a token or cost ceiling anywhere in this pipeline is treated as a defect in that part of the architecture, not something to route around with a bigger budget or a smaller model.

## Task List

### Stage 1 — No-regrets fixes — ✅ DONE 2026-08-03

These don't depend on any open decision (the persistent-knowledge-model question, how the assembly experiment turns out, anything else). They're worth doing regardless of what Stage 3 finds.

- [x] **Fix the fact-ID format — done, verified against a real full pipeline run.** `stableFactId()` (in `02-build-module-evidence.ts`) no longer folds line number into the ID string; `line` stays a separate provenance field on the fact object, unchanged. Line number is replaced with nothing for fact types whose primary/secondary key is already structurally unique per file (`source_file`, `source_class`, `pubsub_event_route` — which already had its own `routeIndex` disambiguator). For every other fact type, an `occurrenceOrdinal` (the Nth time this exact type+file+key combination has been seen, in source order — stable under line-shifting edits, unlike a raw line number) was added as an explicit disambiguator, because this file's own "Conflicting Identity Guard" fatally crashes extraction if two materially different facts collide onto the same ID.
  - **This caught a real bug during verification, not just a theoretical one.** The first attempt assumed method/function/api-contract/type-alias/enum/model-property keys were already unique per file and skipped the ordinal for them. Running the full pipeline immediately threw `DUPLICATE_FACT_IDENTITY_FATAL` on `firestore_trigger` — multiple triggers with an unresolved Firestore path (`"unknown"`) and the same handler-name pattern legitimately collided in one real file. Added ordinal disambiguation to `firestore_trigger` and, rather than continue guessing type-by-type against costly full-pipeline reruns, added it defensively to every remaining fact type where per-file uniqueness isn't provably guaranteed by the language (method overloads, TS interface declaration merging, etc.), even where no real collision had yet been observed.
  - **Re-ran the full `pipeline:firebase` chain clean afterward**: zero fatal errors, and every downstream count is identical to the pre-fix run (2,222 confirmed cross-module call edges, 21 unresolved, 119 intra-module edges, identical per-module fact and capability-pack counts). The fix changed *how* facts are identified, not *what* gets extracted or resolved.
  - **Migration/alias path**: turned out not to be needed. Nothing currently persists fact IDs across separate runs for comparison (that's the future capability this fix enables, not something already relying on today's format) — each run is self-contained under its own `runId` folder, and the citation validator's fuzzy-matching fallback doesn't assume a fixed ID segment count, so it's already robust to the format change. Checked, not assumed.
- [x] **Compact the two deterministic graph artifacts fed into the reduce step — done, verified against real `building` data.** `06-build-cross-module-dependency-graph.ts` and `07-build-intra-module-coupling-graph.ts` now cap each relationship's `touchpoints` array at 3 entries, adding a `touchpointCount` field *only* when truncation actually happens (keeping the field name `touchpoints` unchanged and the shape byte-for-byte identical when nothing was dropped — see the note below on why this mattered). The only consumer of either file is the P2 reduce prompt, which reads it as raw text and never parses individual touchpoint fields — confirmed by checking both P2 scripts before making this change.
  - **Real before/after, `building` module**: `cross-module-dependencies.json` 99,149 → 14,263 bytes (85.6% reduction — one single relationship alone had carried 6 full import records). `intra-module-coupling.json` 32,740 → 32,740 bytes, unchanged.
  - **First version of this fix was net-negative for the intra-module artifact**, and verification caught it: all 56 real submodule-to-submodule relationships in `building` already had 3 or fewer touchpoints, so capping at 3 removed nothing, and the naive version (always adding a `touchpointCount` field) added ~2KB of pure overhead with no offsetting savings. Fixed by only adding that field when truncation actually occurs.

**New finding, not in the original Stage 1 scope, surfaced only because Stage 2 went and measured it — fixed 2026-08-11.** `formatCallEdges` (`_shared/call-edges.ts`) wrote one uncapped line per call site with no grouping — 591 raw lines here (second-largest component of the whole reduce input at 22.3%, comparable to the capability outputs), even though only 211 of those were actually distinct relationships (one real case: a single relationship repeated as 78 separate lines). ### Stage 4 — Pivoted to prompt caching, per Stage 3's own real finding — ✅ DONE 2026-08-11

Originally scoped as "decide A1." Re-sequenced on the spot: Stage 3's real measurement showed the reduce step improved (-43%/-54%) while the full pipeline total stayed roughly flat, because Stage A's fixed grounding+contract overhead — resent uncached on all 11 sequential capability calls — dominates total cost and was never in Stage 3's scope. That's a bigger, better-evidenced lever than A1, so it jumped the queue. A1 is not abandoned, just still deferred (see below).

- [x] **Found and fixed a real observability gap first.** `_shared/llm-adapter.ts`'s `callAnthropic` only ever captured `input_tokens`/`output_tokens` into `usage`, even though the raw Anthropic response can carry `cache_read_input_tokens`/`cache_creation_input_tokens` — and the raw response itself was never persisted anywhere, so this was unrecoverable after the fact once a call completed. Same category of gap as the earlier notification-dedup bug: real cost-diagnostic data existed but wasn't captured. Fixed: `LlmCallResult.usage` now has `cacheReadInputTokens`/`cacheCreationInputTokens` fields, populated for Anthropic (not yet for Gemini/OpenAI — their own mechanisms need checking on their own terms, not assumed to match).
- [x] **Implemented real Anthropic prompt caching.** Anthropic requires structured content blocks (not a flat prompt string) to place a `cache_control` breakpoint. Added an exported `CACHE_BREAKPOINT_MARKER` sentinel to `llm-adapter.ts`: callers insert it into the prompt at the boundary between the stable prefix and variable content; `callAnthropic` splits on it and builds the block array, with cache_control on the prefix block; if absent, behavior is byte-identical to before. Wired into both `01-generate-capability-based-profile.ts`'s production Stage A loop and the `01d-regenerate-single-capability.ts` dev utility, splitting each capability prompt at the exact boundary between the shared prefix (contract docs + grounding docs + module list) and the per-capability variable content (metadata + evidence pack + resolved schemas + output instructions).
- [x] **Validated with 2 calls before committing the full spend.** `building_pincode_trash` (first): `cacheCreationInputTokens: 64,088`, `cacheReadInputTokens: 0` — the write. `building_accesses` (second, run immediately after): `cacheReadInputTokens: 64,088`, `cacheCreationInputTokens: 0` — the read, same exact token count confirming it's the identical prefix being reused. The 64,088-token figure also independently corroborates the earlier byte-based estimate for the grounding+contract overhead (~55-60K tokens) — a useful cross-check, not just a caching result.
- [x] **Ran the full 11-capability regeneration with caching live and got a clean, complete result: 100% cache-hit rate, all 10 calls after the first correctly reading the identical 64,088-token prefix the first call wrote.** Real cost: **$2.46 (intro rate) to $3.69 (standard) for all of Stage A, versus $3.55-5.32 without caching — a consistent ~30.6% reduction**, isolated entirely to the caching change (same 11 capabilities, same contract, only difference is the cache breakpoint).
  - **Combined with Stage 3's connective-call result, the realistic new total for `building` (Stage A cached + 1 connective call) is ~$2.85 at the currently-active intro rate — versus the original real $4.80 baseline. A genuine ~40% reduction in total pipeline cost**, achieved by fixing the two things real measurement actually identified (Stage B's recooking problem, then Stage A's uncached fixed overhead) rather than guessing at either one upfront.

**Decision A1 — ✅ DECIDED AND IMPLEMENTED 2026-08-11, ahead of schedule.** Two independent reasons made it worth doing now rather than staying deferred: it satisfies Facts 1/2's invalidation needs on its own terms, and — newly surfaced — the tech team's RAG retrieval layer intends to consume our documents, and prose-only citations don't survive that (Fact 8). Implementation: a structured provenance sidecar (`<documentPath>.provenance.json`) per generated document, via an additive extension to `_shared/citation-validator.ts` and a new `_shared/provenance-sidecar.ts` helper, wired into `01c-generate-assembly-first-profile.ts` and `01d-regenerate-single-capability.ts`. Verified for free against real data before trusting it. Full detail in `governance/roadmap/phase 2-llm q&a/01 facts-vs-decisions-for-review.md`, Decision A.

**Decision A2 (the full persistent knowledge model) is not decided, and shouldn't be yet — but its trigger just got sharper and more urgent.** Previously gated on a vague "if the bounded approach isn't sufficient." Now gated on something concrete and time-sensitive: **finding the actual interface with the tech team's RAG/EmbeddingGemma retrieval layer, which the module/repo/landscape-level context-window and prose-fragility constraints (independent of economics) make the clear direction regardless of what their platform turns out to provide.** What their platform already handles (versioning, staleness, conflict representation) determines how much of A2's heavier machinery we'd still need to build ourselves versus get for free. This conversation should happen soon — it's no longer a parked, someday item.
