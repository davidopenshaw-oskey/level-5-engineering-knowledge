## The five items on the table

- [ ] **1. Build the real cross-repo join — IN PROGRESS 2026-08-28.** `pipeline/cross-repo-synthesis/phase-03-ecosystem-topology/06-build-cross-repo-graph.ts` was checked and found to be a **non-functional stub, not a working script** — its `crossRepoEdges` array (meant to hold the actual joins) is declared but never populated anywhere in the file, and its directory-scanning logic (`output/runs/<runId>/repos/<repoName>/...`, a `graphData.modulePersonalities` field) doesn't match the real, current `REPO_NAME`-namespaced structure either repo's pipeline actually produces.
  - **Bigger finding, mid-investigation**: validated the join key against real data from both repos before writing any matching logic. Angular's `functionName` (e.g. `organization-createOnboardingDocuments`) minus its hyphenated module prefix matched Firebase's extracted `handlerName` in **67 of 87 real cases (77%)** — strong, but the 20 misses turned out not to be noise. Checked Firebase's real source directly: callable functions are registered as `{ getCountries: https.onCall(OSKCountryService.onGetCountries) }` — the **object property key** (`getCountries`) is what a client actually calls, but Firebase's own Phase 1 extraction only ever captured the **handler reference** (`onGetCountries`) passed into `onCall(...)`, never the key it's assigned to. Those two names often coincide (explaining the 77%) but frequently don't (explaining the 23%).
  - **This means the join needs a real fix to Firebase's own extraction first**, not just new matching logic on top of what already exists — a genuine, unplanned scope discovery, surfaced only by attempting the real join instead of assuming both sides' data was already complete. Confirmed with the user before touching `pipeline/firebase-oskey-dev/` (off-limits all session as the production pipeline) rather than deciding unilaterally.
  - **Prompt ready**: `gemini-prompt-firebase-capture-callable-export-name.md` (scratchpad). Small, precisely-scoped addition to `01-extract-ast-evidence.ts`'s existing "8d. API Contracts" section — walk one level up from the `onCall(...)`/`onRequest(...)` call expression to its `PropertyAssignment` parent, capture `.getName()` as a new `callableExportName` field, without touching or renaming the existing `value`/`handlerName` fields (confirmed no other registration pattern exists anywhere in the codebase — this one form, consistently).
  - **Firebase fix DONE and verified 2026-08-28.** Exact match to the provided fix, ran clean against a real fresh clone of the production repo (544 files, 0 errors). Re-validated the full join against all 87 real Angular function names using the new `callableExportName` field: **83 matched (95%)**, up from 67 (77%) with the old handler-name proxy — confirms the fix is correct and effective, not just theoretically right.
  - **4 remaining misses, worth flagging rather than force-fixing**: checked two of them directly against real source (`supplier-getStaffMember`, `organization-getAllIntercomCommunicationService`) — these aren't naming-convention variants, they're the *handler method names* (`OSKSupplierStaffService.getStaffMember`, real registered callable is `getSupplierStaff`). Angular's code appears to call a name that doesn't cleanly match either the handler or the real registered callable — possibly genuine drift, possibly an actual latent bug in the Angular app calling a name that isn't what's registered. Not chased further or force-matched — flagged as a real anomaly worth the user's awareness, not swept into the join logic.
  - **DONE and verified 2026-08-28 — the join actually works.** Rewrote `06-build-cross-repo-graph.ts`'s stub completely: fixed the stale shared-runId path assumptions to the real per-repo-namespaced structure, built the join off `callableExportName` (not `value`), correctly stripped only the *first* hyphen (not every hyphen — a subtle detail specified precisely and implemented correctly), and reports both resolved and unresolved edges rather than silently dropping misses. **Real result: 102 real cross-repo edges** (one per actual call site, not collapsed to unique function names — genuinely more useful for traceability) — **98 resolved, 4 unresolved**. Unresolved set matches the 4 hand-identified anomalies exactly (`getStaffMember`, `updateIntercomCommunication`, `getById`, `getAllIntercomCommunicationService`). One self-check miscalibration on my part, not a code defect: my prompt asked for "83 resolved" based on *unique function names*, but also explicitly asked for "one edge per call site" — Gemini correctly did the latter (102 edges, 83 *unique* resolved targets, matching exactly once reconciled) rather than the former; verified the reconciliation by hand before accepting it, not just trusting the raw count. Output: `output/cross-repo-synthesis/<synthesisId>/enterprise-topology-graph.json` + matching markdown. **This closes out item 1 — the multi-repo vision this whole Angular effort was building toward is now real, working, and zero-LLM-cost.**
