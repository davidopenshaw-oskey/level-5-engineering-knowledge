## Why this exists

Discussing how P2's reduce step should scale as the module/repo landscape grows (see `tasks.md` and today's Q&A), the obvious next step — split a large reduce input into smaller bundles, reduce each, then reduce the summaries — was found to risk recreating the exact cross-module blindness `01-cross-module-dependency-graph.md` already fixed once, just at the bundle boundary instead of the module boundary. Two worked examples (Firestore ownership disambiguation, permission-string semantic checks) proved the fix isn't a clean binary "structural vs. narrative" split — it's three tiers, and Tier 2 (deterministic-cross-reference) is currently unbuilt, handled ad hoc by asking the LLM to eyeball checks it shouldn't need to perform itself.

This plan classifies what P2 actually consumes into the three tiers *before* designing any batching/recursive-reduce mechanism — batching design depends on knowing what's exempt from it, not the other way around.

## Economics reassessment (2026-08-02) — PAUSED HERE, resume before Stage 4

Ran the first full, real, end-to-end cost test of the capability-based flow: `building` (11 capabilities) against Anthropic `claude-sonnet-5`. Findings changed the priority order for everything below Stage 3.

**What the run actually cost:** 13 real Anthropic calls (11 capability + 2 reduce, sequential then parallel). Dashboard balance $4.06 → **-$0.74** (went negative; Anthropic let it complete rather than hard-cutting at $0). **Total: $4.80** for one module of one repo. Anthropic balance is currently negative — no further Anthropic calls possible until topped up.

**Real bug found while pulling the per-call breakdown, fixed same day:** `buildNotificationId()` in `run-utils.ts` dedupes on `sourceScript::code::module::file::missingArtifact::key`, but the `SYNTHESIS_LLM_CALL_STARTED`/`COMPLETED` notifications in `synthesis-orchestrator.ts`'s `runDocumentCalls`, and the `CITATION_FILE_NOT_FOUND`/`CITATION_VALIDATION_PASSED` notifications in both P2 scripts, never passed a `file` field — so every capability call's completion notification overwrote the previous one in place. Only the *last* call to finish survived in `run-notifications.json`. **Fixed**: added `file: spec.relPath` (call-site notifications) / `file: relPath` (citation notifications) to the `details` passed into `addNotification` in `synthesis-orchestrator.ts`, `00-generate-module-profile.ts`, and `01-generate-capability-based-profile.ts`. Not yet re-verified against a fresh run (Anthropic balance negative) — the `building` run's data was captured *before* this fix, so only one real per-call number survived: the reduce step's `profile` call — **229,710 input tokens / 26,581 output tokens**. Every other call's usage (all 11 capability calls, and the reduce step's `api-reference` call) is lost to this bug and was never measured.

**New tool built, not yet run:** `01b-rerun-reduce-only.ts` — re-runs *only* Stage B (the reduce step) against a different `LLM_CONFIG_KEY`, reading the 11 already-written `capability-syntheses/*.md` files off disk instead of re-paying for Stage A. Writes to `output/runs/<repo>/<runId>/llm-comparison/<LLM_CONFIG_KEY>/`, not the shared `knowledge-corpus/` path — the ad hoc application of `tasks.md` item 8's candidate fix (separate output side-channel per provider) for this comparison exercise specifically; the general design decision on that item is still deferred. Blocked on `OPENAI_API_KEY` not being set; Gemini comparison also wanted (user: "important exercise for the POC") but not yet attempted.

**Why this triggered a pause, not just a tuning pass:** 15+ repos in scope (iOS, Android, node-iot middleware, Angular ×2, and growing), token economics expected to stay unstable through 2026/2027, and at ~$4.80 for one module of one repo the current architecture doesn't support a CI/CD-triggered "merge to prod → regenerate corpus" workflow. This needs an architecture-level answer, not a per-run cost trim.

**Open questions raised, discussed, not yet resolved:**

1. **P1-side grounding-doc scoping.** `firestore-schema.md` and `rbac-roles.json` are confirmed (by the byte table above) the two largest grounding docs, sent in full to *every* call regardless of module — unlike facts, which are already partitioned per module/capability (`05-partition-capability-packs.ts`). Proposal: filter these two docs down to the module-relevant subset, using facts already extracted (`firestore_path_touched`, `permission_candidate`/`permission_error`) as the join key, the same partitioning principle one level up. **Real risk, not just an implementation detail**: `firestore_path_touched` facts were already found too thin in Stage 3 above (only ~10 for all of `building`, missing known multi-writer paths) — scoping `firestore-schema.md`/`rules.txt`/`indexes.json` on that signal risks silently dropping schema context for a collection a module actually touches. RBAC/permission-string scoping is likely safer (497 `permissionHints` repo-wide, much richer signal). Not started.
2. **Would smaller, more-frequent P2 calls be cheaper?** Reasoned through, not implemented: **no, not without caching.** The dominant cost per call is the fixed grounding+contract overhead resent identically every call; more/smaller calls multiplies that fixed cost for a shrinking marginal benefit. Capability-based splitting exists for context-window fit (`adr-003`, the original `building` overflow), not cost — under the current uncached architecture, more granularity is a cost *loser*. Caching would change this calculus (fixed cost paid once/TTL-refresh, read at ~0.1× elsewhere), but caching and granularity are two separate levers; don't do the second without the first.
3. **Prompt caching itself (Anthropic `cache_control`, prefix-match, TTL-based, `tasks.md` items 10/11)**: identified as the most universally-applicable lever, not yet implemented. Two real complications specific to this codebase's actual prompt structure: (a) the reduce step's contract docs come *before* the grounding docs in the prompt, and differ from the capability calls' contract doc — so Stage A and Stage B do NOT share a cacheable prefix even though both include the same grounding docs; (b) the reduce step's two calls (`profile`, `api-reference`) run in parallel, and a cache entry only becomes readable after the first response begins streaming — so those two specific calls can't cache off each other. Unverified: whether a cache *read* extends/refreshes the TTL, relevant to whether an 11-call sequential Stage A run stays warm throughout. Not started.
4. **Which levels of the corpus actually need narrative (Tier 3) synthesis, and where is it needed most?** — raised last, explicitly the thread to resume on. Directly connected to finding above: if capability-level output could be more compact/structured rather than full narrative prose, that reduces **output tokens at the capability level directly**, and — since those outputs get concatenated wholesale into the reduce step's input — **reduces input tokens at the reduce level too**, compounding up through any future cross-module/cross-repo levels. This reframes Stage 4 (which was scoped as "batching mechanics for Tier 3 content") — the more fundamental question is which levels of the corpus need Tier 3 narrative at all, before designing how to batch it.

**Resume point:** pick up on open question 4 first (it reframes Stage 4 itself), then loop back to 1-3 as concrete implementation once the narrative-level question has an answer.
