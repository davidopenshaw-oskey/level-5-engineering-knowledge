## Three lanes' final capture notes — real, load-bearing, not yet in any other doc

Before releasing each lane, they were asked directly: what do you know that isn't written down anywhere yet? All three answered with real findings. Full text is in doc 43 (search "FINAL CAPTURE"); the headlines:

- **Lane A:** the two new W4d edge types (`FIRESTORE_CLIENT_TRIGGER`/`ACCESS`) have **no hub fence**, unlike W6's `INTRA_REPO_CALL_DECLARED` — a bounded-cluster walk from `/users/{userId}` is already truncated at today's small scale (26/130 and 24/154 members/edges). Not a defect in what shipped, but worth a fence if it grows. Also: W1's dead-Swift-callable finding and W4d's path-based dead-collection finding (`friends`/`friendRequests`/`pendingFriendRequests`/`accesses/{}/invitations`, 21 facts total) are **two independent extraction methods landing on the same conclusion** — stronger evidence than either alone, worth flagging to the wiki team as corroborated, not fresh.
- **Lane B:** a reusable sandbox-testing technique (scratch dir, copied clone, symlinked `node_modules`, fresh run id) used repeatedly this build but never written up anywhere reusable — should go in `pipeline/README.md` or a testing-notes doc so the next lane doesn't reinvent or skip it. Also three real, currently-harmless blind spots worth knowing before extending this code: `resolvePathValue`-family resolvers never look inside constructor bodies, only declaration-site initializers; `loadEnvTable` fails closed on any `${`/`` ` ``/`$(` in an env value; `readMode: "once"` detection is a narrow textual match, not real dataflow. And: `_shared/` helper modules need zero registration (no `package.json` script, no manifest) — just the relative import. And: `pubsub-publish-topics.ts`'s module-level `signatureMemo` cache is safe only because each `pipeline:*` run is a fresh process — would leak across runs if phase-01 scripts are ever made composable within one long-lived process.
- **Lane C:** a latent bug in the shared Swift `firestore-client-calls.ts` — its wrapper-method table is keyed by method name alone, not (class, method), so a future class reusing a common method name (`get`, `delete`, ...) tied to a different path enum would silently corrupt both wrappers' `operation` and `baseClass`. Harmless today (verified: every wrapper name is defined exactly once, on one class), but worth a comment or a key fix before this repo or a future one grows. Also: W2 only checked firebase's 7 wrong-argument publish facts for the `publishMessage`-signature bug — node-iot's own 2 publish facts were never checked for the same class of bug. And: Step U's "+600 net facts" estimate is a rough lines-of-code heuristic, not a count — trust the real gate output when Step U actually runs, not this number.
