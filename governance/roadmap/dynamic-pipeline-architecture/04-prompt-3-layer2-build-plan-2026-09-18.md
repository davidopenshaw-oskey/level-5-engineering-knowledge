## 1. Sequencing — three patterns, one pilot, real reasons

**Build order: `rest_endpoint_call` (Kotlin/`android-intercom-oskey-io`) → `firebase_callable_call` (Swift/`ios-oskey-dev`) → `firebase_callable_call` (Kotlin/`android-oskey-io`, structural-only) → Firestore path facts (both languages, separate/later).**

Reasoning, not just a restatement of "smallest first":

- **`rest_endpoint_call` is the strongest pilot for a second reason beyond size**: it's the only one of the three that proves a **new repo-pair edge** (`android-intercom-oskey-io` → `node-iot-api-oskey-io`) that today's Layer 1 hardcoding has never seen. `firebase_callable_call` on iOS targets `firebase-oskey-dev` — the same backend Angular's existing edges already prove Layer 1 can reach. Starting with the REST pattern gives Layer 1's generalization session a genuinely new case to validate against, not a second instance of one it already handles. This directly serves the sequencing decision recorded in `01-...md`/the session hand-off doc (Layer 1 needs a second real target, not just a bigger one).
- **iOS's `firebase_callable_call` comes second**, not `android-oskey-io`'s, because iOS is already onboarded (real Postgres corpus exists to verify against today) and its match key is a single-hop resolution already grounded in the Swift extractor's own real source (no new verification needed — see §3.1).
- **`android-oskey-io`'s `firebase_callable_call` comes third, structural-only**: same conceptual fact kind as iOS, but real code can be written and dry-run now per the resolution above; it just can't be marked "verified against live Postgres" until the dedicated onboarding session runs it for real.
- **Firestore path facts (`firestore_document_access`/`firestore_collection_access`) come last, deliberately separated from the other three**, for a real reason found while planning, not stated in `03-...md`: **this pattern needs a change to the Swift extractor binary itself** (a new SwiftSyntax visitor over `switch`-statement bodies inside computed properties, to pull literal path templates out of `OSKCKFirestoreDocumentPath`/`OSKCKFirestoreCollectionPath`), not just the TS-layer scripts the other three patterns touch. Confirmed by re-checking `main.swift`'s existing `properties`/`enums` visitors: they capture that a `string` computed property exists on the enum, but not its switch-case bodies or their literal return values — real, additional visitor logic, a Swift Package Manager rebuild, and its own test cycle, categorically heavier than a `.ts` file edit. Kotlin's equivalent (`object`-scoped functions returning template strings) is a different shape again (§3 doesn't cover Kotlin's version at all — `android-oskey-io`'s Firestore paths were found in Addendum 1 of `03-...md` but never AST-verified). Bundling this into the same build pass as the other three risks the whole pass stalling on the hardest part; sequencing it last keeps the first three shippable independently.

## 3. Per fact kind, concrete

### 3.1 `firebase_callable_call` — Swift (`ios-oskey-dev` → `swift-cloud-kit-oskey-dev`)

- **Files to modify**: `pipeline/swift/phase-01-ast-extraction/01-extract-ast-evidence.ts` only. No change needed to `swift-extractor/Sources/swift-extractor/main.swift` — the raw `calls` facts it already emits (`rootIdentifier`, `arguments`, `callerFunction`, `callerType`) carry everything this fact kind needs. No change needed to `02-build-module-evidence.ts`'s Swift copy beyond adding the new fact-kind emission block (mirrors the existing `ble_gatt_constant` block, ~line 465).
- **New derivation logic**: in `01-extract-ast-evidence.ts`, alongside the existing `CBUUID` derivation loop (~line 559), add a new loop over `file.calls` matching `call.rootIdentifier === "OSKCKFunctionService"` (NOT `calleeExpression` — confirmed in `03-...md` §1 that `calleeExpression` varies per response type since the wrapper is generic). Write a new raw evidence file, e.g. `ast-firebase-callable-calls.json`, one entry per match.
- **Fields**: `functionName` (first entry of `call.arguments`, quotes stripped), `region` (the `arguments` entry starting `"in:"`, value extracted), `callerFunction`, `callerType`, `repo`/`module`/`file`/`line` (from `base`, same convention as every other raw fact in this file).
- **`02-build-module-evidence.ts` addition**: new block reading the new raw JSON file, emitting `type: "firebase_callable_call"` fact records — mirrors the `ble_gatt_constant` block's shape exactly (`stableFactId`, `occurrenceOrdinal` via `nextOccurrenceOrdinal`).
- **No known helper gaps.** `rootIdentifierOf`'s `GenericSpecializationExprSyntax` handling (already in `main.swift`) is what makes `rootIdentifier` reliably `"OSKCKFunctionService"` regardless of the response-type generic parameter — already confirmed by reading the real extractor source, no rebuild needed.

### 3.2 `firebase_callable_call` — Kotlin (`android-oskey-io` → `firebase-oskey-dev`), structural-only per §2

- **Files to modify** (once repo has a clone path the pipeline can read — for now, developed/tested against the manual clone path directly): `android-oskey-io`'s own `01-extract-ast-evidence.ts`/`02-build-module-evidence.ts` copies **do not exist yet** — this repo has no `pipeline/android-oskey-io/` directory at all (confirmed: only `pipeline/android-intercom-oskey-io/` and `pipeline/swift/` exist for Kotlin/Swift today). Real, honest scoping note: writing this fact kind's logic requires either (a) standing up a minimal `pipeline/android-oskey-io/phase-01-ast-extraction/` directory now, scoped only to this one fact kind and run manually against the local clone, or (b) writing and verifying the logic as a **library-shaped function** (input: parsed AST / raw call+enum facts; output: `firebase_callable_call` records) that gets wired into a real pipeline directory only once onboarding happens. **Recommend (b)** — avoids half-standing-up pipeline scaffolding (config/repos.json-adjacent structure) for a repo whose onboarding is explicitly deferred; keeps this build pass's output cleanly reusable rather than something the onboarding session has to partially undo.
- **Real, verified AST shape** (confirmed via a bounded `tree-sitter-kotlin` parse of a real representative snippet from `OSKFirebaseFunctionsDataSource.kt`, run as part of writing this plan — not inferred from source reading alone):
  - Enum declaration: `class_declaration` (Kotlin's `enum class` is a `class_declaration` with an `enum_class_body` child) → `enum_entry` nodes, each with a `simple_identifier` (the case name, e.g. `CLOUD_FUNCTION_UPDATE_USER_PHONE_NUMBER`) and `value_arguments` → `value_argument` → `string_literal` → `string_content` (the real literal function name, e.g. `"user-updatePhoneNumber"`) — structurally identical shape to the already-verified Retrofit annotation pattern.
  - Call site: a `call_expression` whose callee resolves through `navigation_expression`/`navigation_suffix` to `simple_identifier` text `"getHttpsCallable"`, whose single argument (inside `call_suffix` → `value_arguments` → `value_argument`) is itself a `navigation_expression` of shape `<EnumTypeName>.<CaseName>.value` — three chained `navigation_expression`/`navigation_suffix` levels (`CloudFunctions` → `.CLOUD_FUNCTION_X` → `.value`).
- **Real, two-hop resolution logic** (confirmed necessary and sufficient by the parse above): (1) find every `getHttpsCallable(...)` call site and extract the referenced `<EnumTypeName>.<CaseName>` pair from its argument's `navigation_expression` chain; (2) separately locate the `enum_entry` named `<CaseName>` inside the `class_declaration` named `<EnumTypeName>`, and read its `string_content` as the real function name. This is NOT a local, single-node match — needs both the call-site walk and a declaration-lookup table (name → literal), built the same way Swift's `01-extract-ast-evidence.ts` already builds `declLocation`/`crossRepoDeclLocation` maps for call resolution — same pattern, reused, not invented new.
- **One real unknown, flagged rather than guessed**: whether Kotlin's existing `enum_declaration` fact-emission logic (already a live fact kind for `android-intercom-oskey-io`, confirmed in `03-...md`'s fact-kind inventory) already captures each `enum_entry`'s constructor `value_arguments`, or only case names. If it already captures constructor arguments, the enum-side half of this resolution may already be sitting in existing raw evidence with no new extraction code needed — only the call-site half and the join would be new. **Check this first, before writing new enum-extraction code** — a real, cheap thing to verify (read `kotlin-ast-utils.ts`'s existing enum-handling code, or dump one real `enum_declaration` raw evidence record) before assuming it needs to be built from scratch.
- **No `findEnclosingClassName` gap here** (unlike the REST pattern) — the enclosing type for these call sites is `OSKFirebaseFunctionsDataSource`, a real `class`, not an `interface`; the existing helper already handles that case.

### 3.3 `rest_endpoint_call` — Kotlin (`android-intercom-oskey-io` → `node-iot-api-oskey-io`)

- **Files to modify**: `pipeline/android-intercom-oskey-io/phase-01-ast-extraction/_shared/kotlin-ast-utils.ts` (extend, don't replace, `annotationNamesIn`/add a sibling helper that also returns an annotation's arguments, not just its name) and `01-extract-ast-evidence.ts` (new derivation loop) and `02-build-module-evidence.ts` (new fact-kind emission block).
- **Real, verified AST shape** (from `03-...md`, already checked against the live parse tree): `annotation` → `constructor_invocation` → `user_type`/`type_identifier` (HTTP method, e.g. `"GET"`) + `value_arguments` → `value_argument` → `string_literal` → `string_content` (the literal path).
- **New helper**: a function (e.g. `httpAnnotationOf(fn: Parser.SyntaxNode): { method: string; path: string } | null`) scoped like `isAnnotatedWith` — walks `fn`'s direct `modifiers` child for an `annotation` node whose `constructor_invocation`'s type name is one of `GET`/`POST`/`PUT`/`DELETE`/`PATCH`, then extracts the method name and the first `string_content` found inside it.
- **No real gap here after all** — corrected during the build itself: this grammar has no separate `interface_declaration` node type at all (`01-extract-ast-evidence.ts`'s own section-2 header comment already says so); `interface Foo {}` parses as a `class_declaration`. `findEnclosingClassName` already matches `class_declaration` and needed zero changes — confirmed directly, the real build emitted all 5 facts with `owningInterface: "OSKApiService"` correctly populated on the first real run.
- **Fields**: `httpMethod`, `path`, `functionName` (the Kotlin method name, already resolvable via existing `declaredNameOf`), `owningInterface` (needs the fix above), `parameters` (reuse existing param-extraction logic already used for `function_declaration` facts).
- **Small, fully enumerable surface**: 5 real endpoints today, confirmed exhaustive by repo-wide grep in `03-...md` — cheap to hand-verify every single fact this produces against the real file, not just spot-check.

**Tier 2 — structural/dry-run verification only (Kotlin `firebase_callable_call` for `android-oskey-io`; not onboarded, per §2):**

2. Confirm it produces exactly 32 records (the real, counted call-site total from `03-...md`'s Addendum 1), each with a real, non-null resolved `functionName` — a null/unresolved `functionName` on any of the 32 means the two-hop join in §3.2 has a real bug, not an acceptable partial result (the whole point of this fact kind is that every one of these 32 names is a real, known literal — there's no legitimate "unresolved" case here the way there sometimes is for cross-repo call resolution).
3. Explicitly do NOT claim this is "done" in the Layer-1-facing sense (§4's table already marks it "no" for live Postgres) — done means "code exists and produces the right structural output against real source," not "verified end-to-end," until the onboarding session closes that gap.
