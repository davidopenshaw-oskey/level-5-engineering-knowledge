5. **MongoDB access is NOT Mongoose-schema-shaped** — correcting the priming brief's speculation. There are no Mongoose `Schema`/`model()` calls anywhere. The real "Mongo fact" here is call-site-based (collection name × operation × calling class), not schema-based — structurally closer to Firebase's `ast-firestore-hints` (collection/operation usage sites) than to a schema-definition fact.

## Decisions (confirmed 2026-08-28)

### Decision 1 — What "module" means here — CONFIRMED: rewrite required

**The problem**: `00-scan-repo.ts`'s current logic (`modules = immediate subdirectories of modulesRoot`) assumes folder-per-module, which is Firebase's convention. This repo's immediate subdirectories under `src/v1` are technical layers (`controllers/`, `routes/`, etc.), not domains — that assumption produces garbage here (six fake "modules," none of them meaningful).

**Recommendation**: Treat `access_control_device` as a **single, hardcoded module name** — not derived from any folder (none exists with that name), but declared explicitly in the extraction logic because it's the true, verified capability boundary (point 2 above). This is honest about the repo's real shape rather than inventing directory structure that isn't there. The alternative — skip the "module" concept for this repo and treat the whole repo as an unlabeled single module — was considered and rejected: `access_control_device` is a real, human-meaningful name that should show up in Phase 2's per-module profile, not be silently absent.

This means `00-scan-repo.ts` needs a genuine repo-specific rewrite here, not a config-only adaptation — more code change than either Firebase (as-built) or Angular (folder-tree walk) needed, because neither of their conventions transfers.

**Open question for you**: if this repo later grows a second business domain (plausible — it's called "iot-api," and access-control-device is presumably one device category among possible future ones), a hardcoded single module name will need revisiting. Fine to defer that until it actually happens, flagging now so it's a known, deliberate simplification rather than a forgotten one.

### Decision 2 — What "submodule" means here — CONFIRMED: import-graph reachability

**Confirmed.** Derive submodules by **import-graph reachability from the 5 real route-root files**, not by filename-prefix string matching. Concretely:
- Treat each file directly under `routes/*.route.ts` as a submodule root; the submodule's name is that file's basename with the `access_control_device_` prefix and `.route.ts` suffix stripped (`accesses`, `configs`, `firmwares`, `intercom_entries`, `activities`).
- Walk local (relative-path) imports transitively from each root; every file reached from exactly one root belongs to that submodule.
- A file reached from 2+ roots (verified real case: `pubsub_message.model.ts`, `pubsub_message.schema.ts`) is tagged `submodule: null` alongside `core/`'s infrastructure files, not force-assigned to one arbitrary owner.
- A file under `core/` is always `submodule: null` regardless of reachability, matching Firebase/Angular's convention for cross-cutting concerns.
- **`src/v1/index.ts` is always `submodule: null` too, hardcoded, never entered into the reachability walk at all** — it's the one file this whole graph is upstream *of* (it imports all 5 `*Routes` objects to build `apiV1`), so walking forward from the 5 route roots can never reach it, the same way it never reaches anything that only ever imports, never gets imported. Classifying it as `_unreferenced` (the naive result of "not reached by any root") would be actively wrong — it's the single most load-bearing file in the repo, not dead code. This is a real edge case, not a hypothetical: caught it while re-verifying file counts for this handoff's prompt (point 1 above), not during the first design pass.
- A file reached from **zero** roots by the forward walk (the 4 verified-dead files in point 4 above — `index.ts` is excluded from this check per the rule just above, not counted here) gets a sentinel `submodule: "_unreferenced"` rather than being silently dropped or failing the run. This keeps them visible and auditable downstream (a Phase 2 profile can legitimately say "this file appears to be dead code," which is a true and useful fact) instead of either erroring out or vanishing.

**Why reachability over filename-prefix matching**: filenames alone don't disambiguate cleanly. `access_control_device_access_activity.schema.ts` reads, by prefix, like it belongs to "access" — it's actually `activities`'. `access_control_device_deltas_base.controller.ts` lives in a folder called `shared/` but isn't currently shared. A prefix heuristic would get both of these wrong; reachability gets them right because it reflects what the code actually does, not what it's named.

**Cost/complexity note**: this is real new logic in `00-scan-repo.ts` (a graph walk, not a directory walk), comparable in effort to Angular's Handoff 1 (the recursive `.routes.ts`-boundary rewrite) — not a trivial port. Worth sequencing as its own isolated, independently-verified handoff once you approve this design, same review discipline as Angular's Handoff 1.

**Still open**: is `astErrorTolerancePercent: 0` meant to gate AST *parse* failures only, or would it also need to tolerate the 4 `_unreferenced` files somehow? Not addressed in the 2026-08-28 approval — proceeding on the parse-failure-only assumption (matching Firebase's usage; the `_unreferenced` sentinel is orthogonal, those 4 files still parse fine) since Handoff 1 doesn't depend on resolving this either way. Flag if that assumption is wrong.

### Decision 3 — `classificationRules` / `normalizationRules` in `config/repos.json` — CONFIRMED: recommendation accepted

The existing provisional entry has `serviceSuffixes: ["Service"]`, `controllerSuffixes: ["Controller", "Handler"]`. Verified against real class names, this mostly holds (`OSKAccessControlDeviceAccessController`, `OSKLoggingService`, `OSKPubSubService`) but **lumps two architecturally distinct things under "Handler"**: the real, load-bearing `*RouteHandler` classes (HTTP glue calling into a `Controller`, one per resource — e.g. `OSKAccessControlDeviceAccessRouteHandler`) and the single dead `OSKPubSubMessageHandler` (Secret Manager access, point 4 above, unreferenced). Since routes → route-handler → controller → DB is a real, meaningful three-tier shape in this repo, worth deciding now rather than after Phase 2 profiles conflate them.

**Done 2026-08-28**: `config/repos.json`'s entry now has `controllerSuffixes: ["Controller"]` plus a new `routeHandlerSuffixes: ["RouteHandler"]` key (and matching `stripRouteHandlerSuffixes: ["RouteHandler"]` under `normalizationRules`) — mechanical config edit, done directly. **Still unverified**: whether `02-build-module-evidence.ts` (or wherever classification actually consumes `classificationRules`) already handles an unrecognized key gracefully, ignores it, or needs its own small update to read `routeHandlerSuffixes` at all — I haven't traced that script's real logic yet, only asserted the general claim (scripts 02–07 are structurally generic) that Angular's plan made about its own new fact types. Handoff 4 (below) needs to confirm this specifically, not assume it.

## Proposed fact vocabulary for Script 01 (replaces Firebase's Firestore/RBAC/Pub-Sub-specific facts)

| Firebase concept | Node-IoT equivalent |
|---|---|
| `ast-firestore-hints` / `ast-firestore-triggers` | MongoDB call-site facts: `OSKMongoDBService.{findOne,findMany,insertOne,updateOne,deleteOne}(dbName, collections.X, ...)` — collection name (resolved from the `collections` constant map) + operation + calling class. **Not** schema-based (point 5 above) — Mongoose was a wrong guess in the priming brief. |
| `ast-api-contracts` (callable functions) | **Route-definition extraction from each `OSKRoutes` object literal**: path, HTTP method, version-date key, `requestHandler` reference, and (when present) the wired Joi `schema` reference. Directly parseable via `ts-morph` off the object-literal shape, no external type resolution needed (point 6, 8 above). |
| (no Firebase equivalent) | **Joi schema shape extraction** from `schema/*.schema.ts`: field names, required/optional, `.valid()` enum values — the request-body contract, joined to routes via the `ast-api-contracts` fact's `schema` reference above. |
| `ast-permission-hints` (RBAC strings) | N/A — no auth/guard/RBAC code found anywhere in this repo's own source (point 9). Drop this fact type. |
| `ast-pubsub-event-routes` | **Two real, distinct fact types** (point 7 above), both real and worth building, unlike Angular's outright drop of this row: (1) **outbound** — `OSKPubSubService.publishMessage(topicName, orderingKey, body)` call sites (topic name + message-shape type); (2) **inbound** — `/pubsub/*` POST routes validated against `pubSubMessageSchema`, decoding `message.data`. **Highest-priority fact type in this whole plan** — `core/protocols/pubsub_message.protocol.ts`'s literal `firebase-oskey-dev` header comment (point 7) makes this the concrete, named cross-repo join-key candidate, the same role Angular's `.call()` extraction plays. |
| `ast-external-hooks` | `@oskey-io/npm-express-framework-oskey-io` (routing + Mongo wrapper, point 8), `@google-cloud/pubsub` (real, see above), `@google-cloud/secret-manager` (listed dependency, but only referenced from the dead `pub_sub_message.handler.ts` — effectively unused in live code, worth extracting the hook fact anyway since it's a true dependency-graph fact regardless of the file's reachability). |
| (no Firebase equivalent, new) | **`submodule: "_unreferenced"` dead-code marker** (Decision 2) — not a fact type per se, but a real, verified property of 4 files that Phase 2 profiles should be able to surface honestly. |

Scripts `02` through `07` are expected to remain structurally generic (operating on `module`/`submodule`/fact-type shape), same as Angular's assessment — **except** Decision 3's proposed `routeHandlerSuffixes` key, which I haven't traced through those scripts yet and am flagging rather than assuming.
