Four things worth designing around before writing a word of contract text:

1. **This repo has exactly one module, always** (Decision 1, Phase 1 doc) — every "capability" here is a submodule of the single `access_control_device` module. Firebase's/Angular's cross-module coupling story literally cannot occur here; anything a contract asks about coupling can only ever be intra-module (cross-submodule). Simpler than either prior repo, not a gap.

2. **A real, concrete cross-pack join gap, found directly in this data, not theoretical**: `configs`'s capability pack has **zero** `joi_schema_field` facts, despite its own `route_definition` records referencing `pubSubMessageSchema` by name (`schemaName` field, from Handoff 2). The 3 `joi_schema_field` facts for `pubSubMessageSchema` actually live in `_module_root` — because `schema/pubsub_message.schema.ts` is imported by 3 different route files (accesses/configs/intercom_entries), making it a genuinely shared file tagged `submodule: null` (Decision 2, Phase 1 doc), not owned by any one capability. So `configs`'s own capability-level synthesis **cannot** resolve its own route's request-schema shape from its own pack alone — same structural limitation Firebase's `api-schema-resolver.ts` already has for genuinely cross-module wrapper types (its own code comment: "a candidate with no match... is simply omitted, not reported as an error"), just triggered here by a shared schema file instead of a cross-module type.

3. **`_unreferenced` is a real, substantial pack (223 facts) — not a near-empty edge case the way a Firebase/Angular repo's smallest module might be.** It's the 4 verified-dead files from Phase 1 (2 unused schema files, 1 unused handler, 1 unused schema file with 2 exports) — genuinely dead code, but with real content (19 `joi_schema_field` facts, 193 `call_expression` facts from the Joi method-chaining itself). A contract that treats every pack as "live code to document" would produce a profile section describing dead code as if it does something in production. Needs an explicit instruction, not silent hope that the LLM infers it from context.

4. **No RBAC/permission facts exist anywhere in this repo — genuinely zero, not a small number.** Verified directly in Phase 1 (design doc point 9): no `jwt`/`Guard`/`RBAC`/`Authoriz`/`Permission` pattern anywhere in `src/`, despite `jsonwebtoken` being a listed (apparently unused) dependency. Every capability pack will have nothing for a "Permissions & Security" section, always — this isn't capability-specific sparseness the way Firebase's smaller modules might have a genuinely small RBAC surface, it's total absence at the repo level.

## Decisions and open questions for you before contract text gets written

### Decision 1 — Where does "Pub/Sub Behavior" go in the section numbering? — CONFIRMED: section 5

Recommend directly after "Route Definitions & Request Contracts" (4) — both are about this capability's external-facing surface, and the `isPubSubPushRoute` flag on a `route_definition` fact is the literal pointer from one section into the other (a route in section 4 that's a Pub/Sub push route should point the reader at section 5 for its operation-dispatch detail, not repeat it). Same open-ended framing Angular used for its own new section — open to your read on ordering.

### Decision 2 — How should the `route_definition` ↔ `joi_schema_field` join be computed? — CONFIRMED, built and verified 2026-08-29

Given finding 2 above (a capability's own schema fields can live in a *different* pack, `_module_root`, when the schema file is shared), I don't think a per-capability contract can safely re-derive this join from its own pack alone — same reasoning Firebase's contract already applies to `api-schema-resolver.ts` output ("use it directly, do not re-derive the join yourself"). Recommend building a small, new, node-iot-specific resolver (not an adaptation of `api-schema-resolver.ts`'s type-expression parsing, which doesn't apply here at all) that:
- Groups `joi_schema_field` facts by `schemaExportName` across the **whole module's** facts (not just one capability's pack — required precisely because the shared-schema case crosses pack boundaries).
- For each `route_definition`, looks up its `schemaName` in that map and hands the calling script a resolved field list to inject into the task message, the same way Firebase's resolved-schema table is injected today.
- This is a small amount of new code (simpler than `api-schema-resolver.ts`, since Joi fields are already flat — no type-expression parsing needed), not a big lift, but it is new code, not a copy-paste of the existing shared module. Flagging as its own small decision rather than silently building it identically to Firebase's version and having it silently no-op (0 matches, always) the way leaving `api_contract`-based `api-schema-resolver.ts` untouched would.

**Built and verified 2026-08-29.** New file `_shared/route-schema-resolver.ts` (`resolveRouteSchemas`/`formatResolvedRouteSchemas`, module-wide join exactly as recommended above, keyed by `${file}#${httpPath}#${method}#${versionDate}` to avoid collisions between routes sharing a schema). Wired into `_shared/capability-synthesis.ts` (`buildCapabilityPrompt`'s injected section renamed "Resolved Route Request Schemas" to match the contract's own Section 4 text) via a new `moduleFacts` field on `CapabilitySynthesisContext`, loaded once per module from `${moduleName}-facts.json` and threaded through both real call sites that build this context: `01a-generate-capability-syntheses.ts` (the real fan-out path) and `01d-regenerate-single-capability.ts` (the manual single-capability override tool — same pattern, same fix). `01-generate-capability-based-profile.ts` deliberately left untouched: it's the retired baseline, has its own separate inline prompt-building logic that never called into `_shared/capability-synthesis.ts` at all, and its `resolveApiSchemas(pack.facts)` call was already a permanent no-op for this repo regardless (0 `api_contract` facts ever exist here) — not a regression, consistent with leaving `00-generate-module-profile.ts` alone earlier.

`npx tsc --noEmit -p .` clean. Then verified directly against the real Handoff 7 run's data (`output/runs/node-iot-api-oskey-io/20260828_165412-a6cba122`), not just typechecked — ran `resolveRouteSchemas` standalone against the actual `access_control_device-facts.json` and each capability's real `capability-packs/*.json`:
- **The exact scenario this decision exists to fix, confirmed real**: calling the resolver with only `configs`'s own pack facts (the naive, Firebase-shaped approach) resolves **zero** fields for its Pub/Sub push route. Calling it with the whole module's facts instead correctly resolves `pubSubMessageSchema`'s 3 fields (`deliveryAttempt`/`message`/`subscription`) — confirmed those 3 `joi_schema_field` facts really do carry `submodule: null` (i.e. live in `_module_root`, not `configs`), exactly as finding 2 claimed.
- Same correct resolution confirmed for `accesses` and `intercom_entries` — the other 2 of the 3 capabilities finding 2 named as affected. `intercom_entries` additionally has a second, non-shared route (`postIntercomEntryDeltaAcknowledgementSchema`) that resolves correctly too, confirming the join isn't accidentally only working for the one shared-schema case.
- `firmwares` (not named in finding 2) correctly resolves to nothing — its one route (`GET /access-control-devices/:accessControlDeviceId/firmwares`) has `schemaName: null` in the real data, i.e. genuinely no schema wired to it at all. Confirms the resolver's "omit, don't fabricate" behavior holds for the ordinary no-schema case, not just the shared-schema case it was built for.

### Decision 3 — How should the `_unreferenced` capability pack be handled? — CONFIRMED: option (b), skip LLM synthesis

**Implementation gap found while wiring this up, not yet closed**: `01-generate-capability-based-profile.ts` (byte-identical across all three repos, confirmed generic) currently enumerates *every* file under `capability-packs/` via a plain `readdirSync` — no exclusion mechanism exists at all. Recommend a small, **generic** addition (not a node-iot-specific hardcode, matching this project's established config-driven pattern for everything else per-repo — `classificationRules`, `normalizationRules`, `tsconfigRelativePath`): a new `config/repos.json` `phase2` field, e.g. `excludeCapabilityPacks: ["_unreferenced"]`, that the (still-generic) script checks before fanning out. Not yet built — flagging now so it isn't silently assumed to already work.

Per finding 3 above — real content, but genuinely dead code. Three options, not yet picked:
- **(a)** Synthesize it like any other capability, with an explicit standing instruction in the contract ("if the evidence pack's own facts show it's unreferenced by any route, say so plainly rather than describing it as active functionality") — keeps the corpus complete (every file gets a profile, including "here's dead code worth removing," a genuinely useful finding for whoever owns this repo) but needs that instruction to be unambiguous, not left to inference.

**Recommendation: (b)**. "This file is unreferenced" is a fully deterministic fact already available from Phase 1 (the `_unreferenced` submodule tag itself) — spending an LLM call to have it *narrate* that finding adds cost without adding information the way real synthesis does elsewhere. Matches the project's existing precedent (Firebase's RBAC catalog) for facts that are already complete without an LLM's help.

### Decision 5 — Repo-Report Stage: how many real LLM calls, given this repo has exactly one module? — CONFIRMED 2026-08-29: one call, Executive Summary only

All three of those sections have nothing to do their job on.

Presented three options to you directly (thin single-call / fully deterministic zero-LLM / keep all four as real calls) — **you chose thin single-call**: keep one real LLM call, scoped to Executive Summary only (repo-level framing genuinely differs from the module's own Executive Summary even at N=1 — deployment/service framing vs. internal-architecture framing). ## Two Post-Cutover `01e` Bugs Ported (2026-08-31)

Found by the peer session during Angular's own variance testing, confirmed present in Firebase's `01e` too, and ported here after checking node-iot's own copy had the identical gaps (same code, same pre-fix shape — no new LLM calls needed, code fix verified with `tsc` + a synthetic test, not a real run).

1. **Content-emptiness check.** `missingModuleWide`'s filter only checked `.has(key)` (header presence), never whether the body was actually empty — a header with a near-empty body would silently pass, `MODULE_LEVEL_SECTION_MISSING` would never fire. Fixed: now also flags a section if its trimmed body is under `MIN_JUDGMENT_SECTION_CHARS = 200` (same threshold `01c`'s retry loop already uses). Deliberately detect-and-warn only, not a retry loop — a full one-shot module-level regeneration costs far more to retry than `01c`'s reduce-only retry did; flagged as its own open decision, matching the peer's own framing.
2. **Notification ID collision.** Four `addNotification` call sites used a bare filename or no file reference at all in `details.file` (`MODULE_TOO_LARGE_FOR_SINGLE_CALL`, `SHORT_ID_RESTORATION_INCOMPLETE`, `SINGLE_CAPABILITY_NAME_REMAPPED`, `MODULE_LEVEL_SECTION_MISSING`) — since `addNotification` upserts by ID (sourceScript+code+module+file), two different `LLM_CONFIG_KEY` runs comparing the same module could silently overwrite each other's notification. Confirmed real on Firebase's side (a misattributed warning, only caught by reading the actual output file). Fixed all 4 to route through a single, early-defined `outputLabel` (moved from its old late definition, right after `outputDocsDir`/`COMPARISON_MODE` are set) — matching what the citation-validation notifications already did correctly. Removed the now-duplicate later `outputLabel` declaration.

Verified via synthetic test (no LLM call): a fake `moduleWide` Map with an empty string, a 5-char stub, and a 198-char near-miss all correctly flagged by the new check (the old key-existence-only check flagged nothing); two synthetic `LLM_CONFIG_KEY` values correctly produced two distinct `outputLabel`-based file paths (the old bare-`relPath` version would have produced an identical, colliding path for both). `npx tsc --noEmit -p .` clean.

## Third Malformed-Range Citation Fix Ported (2026-08-31)

Found by the peer session on Firebase's `organization` at temp=0.4 (a malformation never seen at temp=0.0/0.2): a short-ID range citation with NO inner single-backtick wrapper at all (`` F493-F496 ``, vs. the previously-known `` `F493-F496` `` form) — `SHORT_ID_RANGE_PATTERN`'s inner backticks were mandatory, so this new shape silently fell through as unrestored instead of being expanded. Fixed by making the inner backtick optional on both sides, same tolerance style already used elsewhere in the file. Ported into node-iot's own copy proactively, before this repo's own temp=0.4 test runs (below), since higher temperature is exactly the condition that surfaced it on Firebase. Verified via synthetic test: both the with-backticks and without-backticks forms now expand to identical, correctly-formed output. `tsc --noEmit` clean.

## Temp=0.4 Variance Extension (2026-08-31)

Extended the module-level variance check with a third temperature point, 2 real calls against `access_control_device` (`gemini-default-temp04`/`-temp04-run2`, config entries already existed — shared file, added by Firebase-side work), sign-off given directly in this session.

**A real, novel bug found on the first run, distinct from anything the peer had flagged**: `MODULE_LEVEL_SECTION_MISSING` fired for **all 6 capabilities** (module-wide sections were fine). Root cause, confirmed directly: at temp=0.4 (never observed at 0.0/0.2), the model wrote `` ## CAPABILITY: `_module_root` `` — backtick-wrapped — instead of the expected plain `## CAPABILITY: _module_root`. The parser's exact-string match against real pack names never matched the backtick-wrapped name, so every capability's actual, well-formed content got reported as missing even though it was present and correct. The detection itself worked exactly as designed (the warning fired loudly, nothing was silently lost) — this was a parser-robustness gap, not a detection gap. `temp04-run2` used the correct plain format and had no such issue, confirming this is a temperature-dependent, non-deterministic formatting variation, not a contract-text problem.

Fixed by stripping an optional single-backtick wrapper from the parsed capability name (same tolerance-for-format-variation style already used elsewhere in this pipeline — `splitNumberedSections`'s heading-level tolerance, `FILE_LINE_CITATION_BLOCK_PATTERN`'s optional wrapper). Verified against the **actual real captured response** that triggered the bug (no new LLM call needed): re-parsed `gemini-default-temp04`'s real raw synthesis output with the fix applied — all 6 real capabilities now correctly matched, 0 missing.

The preemptively-ported malformed-range citation fix (see above) was **not** triggered by either temp=0.4 run — no `SHORT_ID_RESTORATION_INCOMPLETE` on either — so this test neither confirms nor refutes its necessity for this repo specifically, but it's in place regardless.

No systematic temperature correlation observed in which findings surface — the one real divergence happened at temp 0.2, not at the highest temperature tested.
