## Real, product-specific hypotheses for the iOS repo (strong — same product, not just same language family)

**Module structure — a real, testable prediction.** The Android app is 5 real Gradle modules: `app` (UI) + `kotlin-ble-kit` (BLE/Bluetooth lock control) + `kotlin-usb` (USB peripheral) + `kotlin-webrtc-domain` + `kotlin-webrtc-data` (WebRTC video calling). If the iOS app is the same product's iOS client, expect an analogous real module split (Swift Package Manager packages or Xcode framework targets) along the same lines — an App target plus separate BLE, USB(if applicable — USB is less common on iOS, may not carry over 1:1), and WebRTC domain/data modules. **Real, concrete thing to check first** when the iOS repo is added, before anything else: does it actually split this way, or is it a monolithic single-target app? Either answer is a real, useful finding, not an assumption to build on blind.

**Domain-specific "wire format" facts — a real, shared design candidate, not just a Kotlin idea that might transfer.** Flagged in `01-standing-principles-...md` as a Kotlin-specific extension candidate: BLE GATT service/characteristic UUIDs, WebRTC signaling event/message-type names, and (if applicable) USB vendor/product IDs and command constants. Since the iOS app almost certainly talks to the **same physical devices and the same backend signaling protocol**, these aren't just "a good idea for Kotlin too" — the *actual UUID/event-name values* are likely identical or overlapping across both apps' real code. Worth designing as a genuinely cross-platform fact type from the start, if/when both repos are in the pipeline together, rather than two independently-designed schemas that happen to describe the same real protocol.

**No Room/local-persistence layer found in the Android app — real, confirmed, not yet known whether it holds for iOS.** A real finding, not a general iOS/Android claim. Check directly whether the iOS app similarly has no CoreData/SwiftData usage, or whether it does — don't assume symmetry either way.

**UI paradigm is Compose-only on Android — real, confirmed, doesn't resolve the iOS-side question on its own.** `market-research/08-findings-swift-kotlin-ast-extraction-2026-09-06.md` already found iOS's SwiftUI/UIKit dual-paradigm risk (22-43% UIKit-exposed apps) is real and more asymmetric than Android's (78%+ Compose-dominant) — now doubly relevant, since this specific Android sibling app turned out Compose-only with zero legacy-View-system code. That's a real, mildly encouraging data point (the team appears to build cleanly in the modern paradigm when given the choice) but it is **not** evidence the iOS sibling is SwiftUI-only — iOS's own dual-paradigm risk needs the same direct check (`grep` for `UIViewController`/`@IBOutlet`/Storyboard usage vs. `View`/`@State`) this session did for Android, not inferred from the Android result.

**Toolchain footprint will likely be at least as heavy, plausibly heavier.** Kotlin needed a real JDK + Gradle + Android SDK (not just `npm install`) for compiler-verified type resolution — confirmed real and working this session (see `00-...md`'s toolchain recipe). Swift's real analog (SwiftSyntax + SourceKit-LSP + IndexStoreDB, per `market-research/08-...md` §1) will likely need a comparable or heavier local toolchain (Xcode itself, in many real setups, not just command-line tools) — an expected, not-yet-confirmed real operational cost, worth planning for the same way this session had to stop and explicitly confirm before installing anything.

**Pinned-version reality check — expect the same, don't assume "current."** The Android app is real-pinned to Kotlin 1.8.10 (pre-K2), not the 2026 K2-era tooling the market research was written against — a real gap between "what's current for the language" and "what a real production repo actually runs," found only by checking the real `build.gradle.kts`, not assumed. Expect the same for iOS: check the real pinned Swift/Xcode toolchain version in the actual repo before assuming the newest SwiftSyntax/Analysis-API-equivalent tooling applies cleanly.

## Language-agnostic lessons (already recorded in full in `android-intercom-oskey-io/01-...md`, summarized here as a pointer)

These came from the TypeScript facts-pipeline history, not from the Kotlin repo itself, but were re-confirmed/re-applied during Kotlin's real onboarding this session and apply identically to Swift whenever that repo starts: facts are pointers not payloads; closed-set values (Swift `enum`, Kotlin `enum class`/`sealed class`) must be captured in full from day one — backed by real retrieval-rank evidence, not just structural risk; generic/wrapper type arguments must be descended into everywhere (wrapper types, heritage/protocol conformance, return types); what gets *extracted* and what gets *embedded for search* are separate design surfaces needing separate audits; a single generic "identity field" extractor isn't safe to assume across fact kinds without testing against real retrieval; extraction must be dynamic (read real structure at scan time — `Package.swift`'s real target list for iOS, the same way `settings.gradle.kts`'s `include(...)` list works for Kotlin — never a hardcoded module/screen list).
