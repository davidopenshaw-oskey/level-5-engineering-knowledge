# Pipeline Restructure — One Shared `pipeline/swift/`, Not One Folder Per Swift Repo

**Status: DONE 2026-09-10, real and verified.** Until now, every onboarded repo (TS x3, Kotlin x1, now Swift) was a unique language, so `pipeline/<repoName>/` doubled as both "this repo's scripts" and "this language's scripts." Swift breaks that assumption on purpose: all 6 repos in this family need the *identical* syntax-tree extraction logic, so the pipeline folder is now named for the language (`pipeline/swift/`), not the pilot repo (`pipeline/swift-ble-kit-oskey-dev/`) that happened to be built first. The user's own instruction: TypeScript's 3 folders (`firebase-oskey-dev`/`angular-app-oskey-io`/`node-iot-api-oskey-io`) will merge the same way later — **not attempted here**, and genuinely harder, since those 3 scripts have already diverged with real per-domain logic (Firestore triggers, Mongo operations, Joi schemas) that Swift's 6 repos don't have yet.

## What changed

1. **`pipeline/swift-ble-kit-oskey-dev/` → `pipeline/swift/`** (plain `mv`, the directory was never `git add`ed yet so `git mv` wasn't applicable).
2. **Removed the hardcoded single-repo guard** in both `00-scan-repo.ts` and `01-extract-ast-evidence.ts` (`if (REPO_NAME !== "swift-ble-kit-oskey-dev") throw`). Replaced with a real, more useful check: `config/repos.json`'s own `astTool !== "SwiftSyntax"` fails closed — this correctly refuses to run against a Kotlin/TS repo by mistake, without hardcoding which Swift repo.
3. **Replaced `HARDCODED_MODULE_NAME` with real dynamic discovery** — per the user's explicit request to use dynamic discovery rather than a new config field. Real, confirmed SPM convention: every direct subdirectory of `modulesRoot` ("Sources") is its own target/module. A file's `module` is simply its own first path segment under `modulesRoot`. **This is not a cosmetic change** — checked directly before implementing: `swift-ble-kit-oskey-dev`/`swift-cloud-kit-oskey-dev`/`swift-webrtc-kit-oskey-io`/`swift-ui-kit-oskey-dev` each have exactly one such directory, but **`swift-ai-kit-oskey-io` has two** (`CxxRecognition`, `SwiftRecognition`) — proof a single hardcoded module name was already wrong for one of the six repos, not just inconvenient for the other five.
4. **Renamed npm scripts**: `cloud:swift-ble-kit-00-scan-repo`/`cloud:swift-ble-kit-01-extract-ast` → `cloud:swift-00-scan-repo`/`cloud:swift-01-extract-ast`.
5. **Fixed a real, pre-existing `tsc` strictness issue found while doing a full project-wide typecheck for the first time** (`npx tsc --noEmit -p .`, not previously run against these two files — only `ts-node` had ever executed them, which transpiles but doesn't fully typecheck): the `resolvedViaImport` tally compared `resolutionMethod` against `"resolved_via_import"`, a value nothing in the function can currently assign (real, deliberate — `resolved_via_import` isn't implemented yet, see `01-extract-ast-evidence.ts`'s own header). TS correctly flagged this as an unreachable comparison. Removed the dead comparison rather than suppressing the warning; `resolvedViaImport` stays a real, honestly-named counter that will start incrementing once Task 11's cross-repo resolution actually exists.

## What did NOT change, and why

- `output/clones/<repoName>/`, `output/<repoName>/`, `output/runs/<repoName>/...` — already keyed by the `REPO_NAME` env var, never by pipeline-folder name. Each of the 6 repos' real output stays fully separate; zero changes needed.
- `config/repos.json`'s per-repo entries — unaffected. The remaining 5 repos still need their own Task 2 (`astTool`/`astErrorTolerancePercent` fill-in) before this shared script can run against them for real — unrelated to this restructuring.
- `governance/roadmap/<repo>/` folders — these document real, repo-specific decisions and findings, not pipeline code. Left as-is on purpose.
- The compiled `swift-extractor` binary needed no code change at all — it already took a directory path as an argument and had nothing repo-specific baked in; it just moved with the folder.

## Verification

Re-ran `00`→`01` against `swift-ble-kit-oskey-dev` from the new shared location, via the renamed npm scripts: **byte-identical real output** to the pre-restructuring baseline — 1 module (correctly discovered as `"OSKBluetoothLEKit"`, not hardcoded), 30 files, 8 classes/9 structs/10 enums/2 protocols/13 extensions/91 functions/141 properties/56 imports/433 calls (71 same-target/334 unresolved), 6 BLE GATT constants. Separately verified the new multi-module discovery logic in isolation against `swift-ai-kit-oskey-io`'s real `Sources/` (its own `config/repos.json` entry isn't filled in yet, so the full guarded script can't run against it): correctly returns `["CxxRecognition", "SwiftRecognition"]`, both real targets, in the right order.

## Real, valuable finding surfaced by this same review, not yet acted on — Firestore/document-snapshot chain-walking risk

While re-checking the TS pipeline's own `01-extract-ast-evidence.ts` history for anything not yet covered in `11-cross-pipeline-lessons-checked-against-swift-2026-09-10.md`, found a real, directly relevant gap that survey missed: **`firebase-oskey-dev/01-extract-ast-evidence.ts`'s `findChainedFirestoreOperation` function was originally a one-hop-only chain walker** — it only matched a simple `db.collection('x').get()` shape, and silently missed almost every real case once a document path nested more than one level (`db.collection('a').doc(id).collection('b').doc(id2).get()`) — confirmed in that file's own comment: *"only 1 of 18 shared Firestore paths in a real run had operation evidence"* before the fix. Fixed by walking the *full* remaining chain, not just one hop.

**Why this matters here, concretely, not hypothetically**: `swift-cloud-kit-oskey-dev` (not yet built — Task 10 territory) is a real Firestore wrapper for iOS, confirmed directly: `Firestore.firestore().document(string)`/`.collection(string)` chained calls, `addSnapshotListener` (Swift's `onSnapshot` equivalent), `getDocument`/`setData`/`addDocument`, and a type literally named `OSKCKDocumentSnapshotChangesHandler`. This is the *same* Firestore SDK API shape across platforms — the chain-walking trap that cost the TS pipeline 17 of 18 real cases is a live risk for whatever Firestore-specific domain-fact extraction (the direct analog of Task 6's BLE GATT constants) eventually gets built for this repo.

**Not a live bug today** — Swift's own generic `calls` extraction (Task 5) is structurally immune to the *general* one-hop version of this bug: it visits every `FunctionCallExprSyntax` node via `SyntaxVisitor`, regardless of chain depth, rather than manually walking forward N hops the way the TS script does — confirmed earlier (a 2-hop `Logger().info` chain was correctly captured as 2 separate call facts). The risk is specific to a *future* Firestore domain-fact detector that needs to correlate "which `.collection()`/`.document()` path call" with "which terminal operation call, however many hops later" — exactly the correlation Firebase's own script got wrong the first time. **Recorded here now, before it's needed, so it doesn't have to be rediscovered painfully like it was in the original Firebase pipeline** — no code to write yet, since Task 10 hasn't reached `swift-cloud-kit-oskey-dev`.
