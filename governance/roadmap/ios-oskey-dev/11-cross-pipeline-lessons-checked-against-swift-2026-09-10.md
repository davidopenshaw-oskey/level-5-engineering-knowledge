**Purpose of this file:** mirrors `android-intercom-oskey-io/06-ts-pipeline-lessons-reflagged-for-tree-sitter-2026-09-08.md`'s role for Kotlin — before continuing Swift's own build (P1 build tasklist, Task 9 onward), audit every real, documented `01-extract-ast-evidence.ts` problem across `firebase-oskey-dev`, `angular-app-oskey-io`, `node-iot-api-oskey-io`, and `android-intercom-oskey-io` for whether the same failure mode threatens `swift-ble-kit-oskey-dev/01-extract-ast-evidence.ts`. ## The single most-repeated lesson across the whole project's history — and a real, confirmed Swift analog

**Pattern, recurring independently at least five times** (Angular's `formControlName` plain-attribute vs. bracketed-binding syntax, 92/160 real cases; Angular's literal `value`/`ngValue` attributes never visited because the walk only checked `node.inputs`; node-iot's route-handler methods written as static-property-arrow-functions instead of `MethodDeclaration`s, invisible to the generic method walk; Kotlin's `@Composable` failing to attach where a synthetic test snippet assumed; TS's option-list arrays needing a structural heuristic instead of a property-name allowlist): **a walker tuned to one syntactic shape of a construct silently misses a semantically-equivalent sibling written a different way** — never erroring, just producing an undercount nobody notices without an independent check.

**Confirmed, real, currently-live Swift analog, checked directly against `swift-ble-kit-oskey-dev`**: the extractor's `functions` fact list only visited `FunctionDeclSyntax`. **All 16 real `init` declarations and all 4 real `deinit` declarations in this repo were completely absent from `ast-functions.json`** — confirmed directly (`grep` found 16 real `init` declarations under `Sources/`; the fact list contained zero). Same failure class as Kotlin's constructor-promoted-properties gap (`13-task6-coverage-verification-2026-09-09.md`, 406 missing properties, ~26% of the true count) — not the same mechanism, same shape.

**FIXED 2026-09-10, immediately after this was reported** — real enough and high-value enough (dependency-injection-style constructors are exactly where a lot of this codebase's real architecture lives) to fix before Task 9 builds on top of `01`'s output, rather than carry it forward. Added `InitializerDeclSyntax`/`DeinitializerDeclSyntax` visitors to `swift-extractor` (schema 2.3.0), pushing onto `functionStack` too (fixes a related, quieter bug: calls made inside an initializer's own body were previously mis-attributed with `callerFunction: null`). Verified: `functions` went from 71 to 91 (+20, exactly 16 init + 4 deinit).

**A second real bug found immediately by verifying the fix, not assumed clean**: indexing "init"/"deinit" into the same-target resolution table caused `declLocation.get("init")` to match whichever class's init was indexed *last* across the whole repo — a real false positive, confirmed directly (a `.init(...)` shorthand call in `OSKBKEncryptionService.swift` "resolved" to its own file only by coincidence of iteration order, not a real match; same-target resolution count briefly went from 71 to 72 on the fix, the tell that something spurious had been added). Fixed by excluding `"init"`/`"deinit"` from the resolution table entirely — they're generic keywords, not distinguishing names, and a bare `.init(...)`/`super.init(...)` always refers to the type already under construction, never a name needing cross-file lookup. Re-verified: same-target resolution back to exactly 71 (the pre-fix baseline), and the `.init` call site now correctly shows `unresolved` rather than a spurious match.

## Kotlin-specific findings, checked and found NOT to transfer

- **`interfaces: 0` — no separate `interface_declaration` node type in tree-sitter-kotlin** (`11-task4-extract-ast-evidence-built-and-verified-2026-09-09.md`). **Does not apply to Swift**: SwiftSyntax has a real, distinct `ProtocolDeclSyntax` node type, already confirmed working correctly (Task 5/7's protocol counts matched `grep` ground truth exactly, no special-casing needed).
- **`composableFunctions: 0` — an annotation parses nested inside the declaration's own `modifiers` child, not as a sibling** (same doc). Checked Swift's equivalent structure directly: SwiftSyntax keeps `@`-attributes (`@Published`, `@available`, `@MainActor`) in a **separate** `attributes` list from keyword `modifiers` (`public`, `static`) — a real, different design from Kotlin's grammar. **Not a live bug** (the current extractor never reads `.attributes` for anything), but a real, concrete caution for future work: **any future Swift fact that needs to detect a specific attribute (the direct analog to `@Composable`) must read `node.attributes`, not `node.modifiers`** — the two are genuinely separate in this grammar, unlike Kotlin's.
- **Sealed-hierarchy same-file-only scope limit** (`11-...md`) — no direct Swift analog; Swift enums are inherently single-file/self-contained (a case can't be added from another file the way Kotlin 1.5+ allows for sealed subclasses).

## The compiler-exact-resolution lesson — already correctly internalized in the Swift build

`07-call-graph-resolution-gap-major-finding-2026-09-08.md`'s real, major finding (TS's `expr.getSymbol()` whole-project symbol resolution is what makes `04-build-resolved-graph.ts`'s "Rule A: confirmed" tier possible; no syntax-only tool, tree-sitter or SwiftSyntax alike, can do this at all) was already correctly designed around in Swift's own `01-extract-ast-evidence.ts` before this audit — `resolutionMethod` is honestly tagged `resolved_via_import`/`resolved_via_same_target`/`unresolved`, never `"confirmed"`, matching Kotlin's own resolution exactly. **No action needed; confirms the current design already matches the hard lesson**, not a newly-found risk.

## Real, open, NOT-yet-checked risk: symbol aliasing defeating text-based resolution

TS's `resolveSimpleRef`/Mongo-collection-name resolver bug (`node-iot-api-oskey-io/00-phase1-ast-extraction-design.md`, Handoff 2): calling `.getSymbol()` on an imported identifier without `.getAliasedSymbol()` first resolves to the **local import binding**, not the real declaration — "silently correct when the import binding's own name happened to match... silently wrong otherwise." Swift's own resolver is pure text-matching (`declLocation.get(call.rootIdentifier)`), so this exact TS mechanism doesn't apply — **but Swift's `typealias` is the same class of risk**: a call through an alias (`typealias Manager = OSKBKCentralManager; Manager.foo()`) would look up `"Manager"` in `declLocation`, find nothing (only the real name `"OSKBKCentralManager"` was ever indexed), and incorrectly tag the call `unresolved` rather than resolving it. **Checked directly: `swift-ble-kit-oskey-dev` has zero real `typealias` declarations** (confirmed via `grep`), so this is not a live bug in this specific repo — but it's real, unchecked, and worth verifying before trusting the resolver's numbers on the larger/more complex repos later in this family (`ios-oskey-dev` especially).

## The recurring field-name-collision bug — checked, confirmed NOT present in Swift's script 01

**Happened independently at least twice** (Angular's `01-next-steps-post-phase1.md` Handoff 4a: a route's own `path` field silently overwrote `base.path`, the file-provenance field, destroying it for 59 records; node-iot's `00-phase1-ast-extraction-design.md` Handoff 2: the identical bug, `path: httpPath` overwriting `...base`'s `path`, 18 records affected) — both real data-loss bugs, not just naming ugliness, both caught only by opening real output and checking field values, not by reading the code. **Checked directly against every `rawX.push({...base, ...})` call site in Swift's own `01-extract-ast-evidence.ts`: no field name collides with `base`'s own keys (`repo`/`module`/`submodule`/`file`)** — confirmed clean on this audit. Worth re-checking this specifically any time a new field is added to an existing fact type (the exact moment both original bugs were introduced).

## Real, open risk: narrow, single-pattern domain-fact detectors

Angular's `external_hook`-family detection (`firebase-oskey-dev/tasks.md` item 22) correctly fires on Pub/Sub/`process.env` patterns but has zero visibility into `@angular/fire`/`@ngx-translate` SDK usage (79 real files) — a real, structurally narrow detector, not a bug, but a named capability boundary. **Direct Swift analog**: Task 6's `ast-ble-gatt-constants.json` detector only recognizes `CBUUID(string: "...")` — if this repo (or a sibling) ever expresses a GATT UUID a different way (a byte-array literal, a computed property, a value passed in from outside rather than constructed inline), it would be silently invisible to this detector, the same way `@angular/fire` imports are invisible to `external_hook` detection today. Not a live gap in this repo (checked in Task 6 — all 6 real UUID constants use the one recognized shape), but worth remembering as the pattern's known boundary before assuming a future repo's UUIDs will look the same way.

## Real, open risk for Task 9: hardcoded fact-type allowlists drifting from real vocabulary

**A systemic pattern, confirmed across 3 of 3 repos it was checked on** (`firebase-oskey-dev/tasks.md` item 23): Angular's port missed 8 fact types in a citation-pattern allowlist; node-iot's own port independently hit the identical failure (63/146 real citations, 43%, silently mishandled); Firebase's own vocabulary had one dormant, unfired instance of the same gap. Separately, `03-build-benchmark.ts`'s hardcoded `REQUIRED_SUMMARY_FIELDS`/`totals` lists needed a mechanical fix on **both** the Angular and node-iot ports because neither was aware of new fact-type names (`angular-app-oskey-io/00-...md` Handoff 7; `node-iot-api-oskey-io/00-...md` Handoff 4). **Direct, real implication for Task 9** (not yet built): whatever downstream aggregation/benchmark/citation logic gets ported for Swift must be checked against Swift's own real, full fact-type vocabulary (`class_declaration`, `struct_declaration`, `enum_declaration`, `protocol_declaration`, `extension_declaration`, `ble_gatt_constant`, ...) — not assumed safe just because it was copied from Kotlin's or TS's own hardcoded lists.

## Lower-priority, honestly-noted completeness gaps (not correctness bugs)

- **Inferred/unannotated property types have no captured type info** — a known, accepted TS/Kotlin limit (`06-ts-pipeline-lessons-...md` item 3; `11-task4-...md`'s own scope-limit note). Swift's current state is actually *further behind* than either: the extractor doesn't capture a `declaredType` field for properties **at all** yet, explicit or inferred — a real, lower-priority gap, not a regression (nothing currently relies on it), worth a future task if property type information ever becomes load-bearing for retrieval.
- **`subscript` and `deinit` declarations** — checked directly: this repo has 0 real subscripts and 4 real deinits, both currently uncaptured by any fact type. Lowest priority of everything found here (small real counts, no evidence anything downstream needs them yet).

## Not re-litigated here

- Kotlin's own call-resolution-volume framing (12% resolved, mostly expected external-framework calls) — Swift's own numbers (71/433 resolved, 334 unresolved, mostly `CoreBluetooth`/`Combine`/`Foundation`) already match this exact, already-accepted shape; not a new finding.
- The TS pipeline's Angular-template "two separate ASTs" 92-of-160 bug itself — already confirmed inapplicable to Swift/SwiftUI (no second parser; SwiftUI view hierarchies are plain Swift code inside the same syntax tree), same as it was already confirmed inapplicable to Kotlin/Compose.
