# Task 1 — Decision: SwiftSyntax (not `tree-sitter-swift`)

**Status: DECIDED, 2026-09-09. Independently confirmed 2026-09-10.** Mirrors `android-intercom-oskey-io/09-task1-decision-tree-sitter-plus-import-aware-resolver-2026-09-08.md`'s role for Kotlin — the real, final Task 1 decision, grounded in a bounded, real parse test against all 6 repos' actual code (`08-swiftsyntax-vs-npm-treesitter-bounded-test-2026-09-09.md`), not research alone. Where Kotlin's Task 1 landed on the npm-only tool, Swift's lands the other way, on SwiftSyntax.

**2026-09-10 confirmation**: before starting build work, the user ran a targeted web-research prompt (covering: whether `tree-sitter-swift`'s `#if`/`#endif` cascading-parse bug is a known/fixed upstream issue, whether a safe preprocessing workaround exists, whether an actively-maintained fork fixes it, and whether SwiftSyntax has any WASM/portable build that would remove its toolchain dependency) in a separate peer session, on the reasoning that a problem this common likely has prior art. Outcome relayed directly by the user: the research did not surface anything that changes the call — SwiftSyntax stands. The research session's own transcript/findings were not merged into this session, so no specific citations from it are recorded here; this line records the outcome and the fact that the check was done, not its detail.

## The decision

**Extraction tool: SwiftSyntax**, pinned to whatever Swift toolchain is actually installed on the machine running extraction (this session used `apple/swift-syntax` `exact: 603.0.2` against a real Swift 6.3.3/Xcode 26.6 install — checked directly, not assumed). **Not** `tree-sitter-swift`, despite it being the npm-only, toolchain-free option that would have matched the TypeScript (`ts-morph`) and Kotlin (`tree-sitter-kotlin`) pipelines' deployment story.

## Why, grounded in real, measured results — and why this is a disqualification, not a tunable tolerance

**Both tools parsed the single-repo test corpus (`swift-ble-kit-oskey-dev`, 32 files) 100% clean** (`08-...md` §1-2). That result did not generalize: re-run across the full 6-repo family (821 files), **SwiftSyntax stayed 100% clean; `tree-sitter-swift` produced real, root-caused parse errors in 40 files (4.9%)** (`08-...md` §5a), dominated by `#if`/`#else`/`#endif` conditional-compilation blocks wrapping a declaration — an ordinary, common Swift idiom in this codebase, not a rare construct.

**The reason this is disqualifying rather than an acceptable tolerance, unlike Kotlin's own 4.4% error rate**: Kotlin's error rate was safe to accept because it was root-caused to a *localized* failure — one unparseable statement (a call-then-navigation-chain assignment) in an otherwise-intact file; every other declaration in the same file, before and after the bad line, still parsed correctly (`android-intercom-oskey-io/09-...md`). `tree-sitter-swift`'s `#if`/`#endif` bug is *cascading*, not localized: it drops a closing brace at the conditional-compilation boundary, and the resulting corruption extends to the end of the file. **A file with this bug doesn't have "one bad line" — it has an unknown, unbounded fraction of its own content silently missing**, with no way to tell from the tool's own output how much. This is a qualitatively different failure mode than a bounded, tolerable error rate; a percentage-tolerance framing (as Kotlin correctly applied to its own case) doesn't apply here.

**Direct, measured proof of the consequence, not a theoretical concern**: the family-wide duplicate-declaration-name scan (`08-...md` §5b), built first on `tree-sitter-swift`'s own output following Kotlin's exact methodology, found 3 duplicate top-level names. Re-run on SwiftSyntax's clean parse of the identical 821 files, it found **5** — two real collisions (`Provider`, `OSKUserIdKey`) were silently invisible in the corrupted version. A production resolver built on `tree-sitter-swift` without first fixing this would under-report real symbol collisions, not merely tolerate a known, bounded gap the way Kotlin's pipeline safely does.

**SwiftSyntax's toolchain dependency, the reason it wasn't the first choice, is real but manageable**: it requires a Swift compiler on whatever machine runs extraction (Xcode or a standalone swift.org toolchain, macOS or Linux) — genuinely less portable than the Node-only `ts-morph`/`tree-sitter-kotlin` pipelines. But it is a known, fixed, one-time environment requirement, not a per-file correctness gap with unknown blast radius. Patching `tree-sitter-swift`'s grammar for 3 known constructs (`#if`/`#else`/`#endif`, `#Preview`, labeled trailing closures) that SwiftSyntax already handles for free was considered and rejected as not worth the maintenance burden versus just requiring a Swift toolchain in the extraction environment.

## What this means concretely for Task 1 build work

- **Extraction library for Swift: SwiftSyntax + SwiftParser**, not `tree-sitter-swift`. The npm-only, single-runtime deployment story that worked for TS/Kotlin does not extend to Swift; document this as a real, accepted asymmetry across the three pipelines rather than forcing artificial consistency.
- **Call-graph / cross-module resolution**: still needs a custom import-aware symbol table on top of SwiftSyntax's parse, per `08-...md` §3 — `resolved_via_import` (cross-target) / `resolved_via_same_target` (Swift's analog of Kotlin's `resolved_via_same_package`, structurally different because Swift's same-target visibility needs no import at all) / `unresolved`. The cross-target shadow case found (`OSKBKCentralManagerHostViewModifier`, `08-...md` §5c) needs an explicit "local/same-module declarations shadow same-named imports" rule built into the resolver, not left implicit.
- **Real, still-open, pre-build blocker**: the 3 same-target duplicate names (`Provider`, `OSKUserIdKey`, `OSKStreetAddressPickerViewModel`, all within `ios-oskey-dev`) cannot be resolved by either AST tool — both are blind to Xcode's `.pbxproj` target membership, which is per-file, not folder-implied. Real next step, not yet executed: read `.pbxproj`'s `PBXNativeTarget`/`PBXSourcesBuildPhase`/`PBXFileReference` sections directly (it's a stable, textual "OpenStep plist" format — Ruby's `xcodeproj` gem or a small hand-rolled reader both work; no third AST tool needed) to get exact per-target file membership for `ios-oskey-dev`, the one repo in this family not using SPM's folder-implies-target convention. Worth building once, since `ios-oskey-dev` is the only repo in this family where target membership isn't folder-derivable, and any future same-target ambiguity here will need the same answer.
- **Known, accepted limitation carried forward, not silently dropped**: the two smaller, still-unexplained count deltas between the two tools on the single-repo corpus (properties ~8% low, calls ~6% low on `tree-sitter-swift` vs. SwiftSyntax, `08-...md` §2) are moot for the tool choice itself now that `tree-sitter-swift` is not being used, but worth keeping on record in case SwiftSyntax's own property/call counts ever need independent cross-validation later.

## Deployment implications, confirmed against the real pipeline architecture (2026-09-09)

Checked directly against `package.json` and the real Kotlin pipeline code, not assumed: every existing phase of every repo's pipeline runs as `node -r ts-node/register <script>.ts` (confirmed for `firebase-oskey-dev`, `angular-app-oskey-io`, `node-iot-api-oskey-io`; Kotlin follows the identical convention). The language-specific parser dependency (`tree-sitter-kotlin`) is only ever imported in **`00-scan-repo.ts`** and **`01-extract-ast-evidence.ts`** — grepped directly across `06-build-cross-module-dependency-graph.ts` and confirmed its one apparent hit was a code comment, not an import. **Phases `02`-`07` and phase-2 inter-module synthesis only ever consume the JSON evidence artifacts those two scripts write to disk — they have no direct dependency on which parser produced them.**

This means choosing SwiftSyntax over `tree-sitter-swift` does **not** make the whole pipeline require a Swift toolchain — the cost is isolated to phases `00`/`01` for Swift repos specifically:
- **Those two steps can no longer be plain `.ts` files calling an npm-native parser binding** (unlike Kotlin/TS) — SwiftSyntax needs a real Swift compiler. The realistic shape: keep them as thin TS wrappers (preserving the existing `npm run pipeline:...` orchestration convention) that shell out via `child_process` to a separately-built Swift executable, passing the repo path in and capturing the same JSON evidence shape back out.
- **Phases `02`-`07` for Swift repos need no changes at all** beyond what any new language port needs — they're already language-agnostic by construction.
- **Real, concrete deployment cost**: whichever machine/CI job runs a Swift repo's pipeline needs both Node and a Swift toolchain (Xcode, or a swift.org toolchain — Linux availability exists in principle but was not tested in this session's build, which pulled a macOS-specific prebuilt `SwiftSyntax` binary). TS/Kotlin/other repos' pipelines are unaffected.
- **Practically near-term, this costs nothing**: per `05-future-trigger-driven-extraction-concurrency-risk-2026-09-09.md`, this pipeline is manual-trigger, run on a real developer machine (this one, which already has Xcode) — not automated CI. The cost only becomes real if/when this pipeline is automated onto shared infrastructure, the same automation question doc `05` already deliberately deferred; this is one more concrete reason not to design that automation prematurely.

## Post-decision literature check, 2026-09-09 (later same day) — real industry precedent, decision not reversed

Before treating this as final, ran a live web-research pass asking two questions: (1) has `tree-sitter-swift`'s conditional-compilation gap already been fixed or worked around somewhere, and (2) how do tier-1 vendors who parse Swift at real scale (security scanners, code-intelligence platforms, big-tech internal tooling) actually handle this. Full detail: `08-...md` §5a-i (the known-issue/npm-staleness findings) and this section (the industry-precedent findings).

**The dominant bug (§5a bug 1, `#if`/`#endif` wrapping a declaration) has a real, merged upstream fix** ([issue #583](https://github.com/alex-pinkus/tree-sitter-swift/issues/583), merged 2026-05-26, in tag `0.7.3`) — **but the npm registry's published `tree-sitter-swift` is still `0.7.1` (2025-06-23), over a year stale**, and this test used the npm package. See `08-...md` §5a-i for the full detail, including the real caveat that consuming the fix would mean installing from a git ref rather than the npm registry, likely reintroducing a `node-gyp` native-build dependency the registry package currently avoids. Bugs 2 (`#Preview`) and 3 (labeled/multiple trailing closures) have **no known upstream fix or even a reported issue** — genuinely open gaps, not just unreleased ones.

**Real, independent corroboration from tier-1 vendors who parse Swift at scale, none of which treat `tree-sitter-swift` as sufficient for correctness-critical extraction:**

- **CodeQL (GitHub/Microsoft)** — the strongest data point found. Its Swift extraction does not parse source independently at all: it works by **build tracing**, intercepting real `swiftc`/`clang` compiler invocations during an actual `xcodebuild`/`swift build` ([GitHub Docs](https://docs.github.com/en/code-security/reference/code-scanning/codeql/build-options-for-compiled-languages)). GitHub's own security-scanning product, run across its entire Advanced Security customer base, sidesteps the conditional-compilation parsing problem entirely by requiring the code to actually build — real, honest tradeoff worth noting: this means CodeQL only ever sees whichever `#if` branch was actually compiled, never both, a different (arguably worse, for a fact-extraction use case) limitation than SwiftSyntax's own both-branches-visible syntax parse.
- **Sourcegraph** has no dedicated Swift SCIP indexer at all (confirmed against Sourcegraph's own list of indexers — Java/Scala/Kotlin, TypeScript, Rust, C/C++, Ruby, Python, .NET, Dart, PHP, no Swift). Swift code intelligence there goes through a generic LSP-to-SCIP bridge, meaning it depends on **SourceKit-LSP** — the same real-compiler-backed tool this decision already chose, not tree-sitter.
- **Meta's Glean** (real, huge-scale internal code-indexing system, "tens of billions of facts") lists dedicated indexers for C++, Hack, Python, Haskell, Flow, .NET, Go, Java, Rust, TypeScript — **Swift is absent**, despite Meta running large real Swift codebases. An honest negative, not proof of anything, but real: no evidence a company operating at that scale has published a solved answer for this either.
- **Semgrep** is the closest real analog — built its Swift support on **this exact same `alex-pinkus/tree-sitter-swift` grammar**, and self-reported a **94% real-world parse rate** at experimental launch (Aug 2022), independently close to this project's own measured 95.1% (781/821). Swift reached GA in Semgrep Code in March 2024, but neither the GA announcement nor Semgrep's Swift docs page mention conditional compilation, `#if`/`#endif`, macros, or trailing closures specifically, or what was actually fixed to reach GA — and Semgrep still lacks cross-file analysis for Swift, a separate acknowledged gap. Semgrep's own grammar-integration layer (`ocaml-tree-sitter-semgrep`) hit real, separate, unresolved grammar conflicts integrating this same grammar.
- General context, not Swift-specific: the "one bad construct cascades and corrupts the rest of the file" failure mode found in §5a is a known general tree-sitter risk class, not a Swift-only quirk — the same effect is documented for tree-sitter parsing Python indentation errors (an indentation error at a definition can swallow the rest of the file into that one block, per real-world dataset-curation reports from the BigCode/The Stack project).

**Net effect on the decision: strengthened, not reversed.** The two vendors whose product actually depends on Swift parsing being *correct* (CodeQL for security scanning, Sourcegraph for precise code navigation) both bypass syntax-only parsing entirely, in favor of the real compiler or a compiler-backed LSP — exactly the SwiftSyntax-style choice already made here. The one vendor that did build on `tree-sitter-swift` (Semgrep) operates it as a pattern-matching tool tolerant of a real, acknowledged ~5-6% gap, not as a precise-extraction tool — a materially different risk profile than this project's own AST fact-extraction use case, where a silently-corrupted file means silently wrong or missing facts. No tier-1 vendor was found treating `tree-sitter-swift` as sufficient on its own for correctness-critical extraction.

**One real, cheap, still-open action item this implies** (not yet executed): re-run `08-...md`'s bounded test with `tree-sitter-swift` installed from GitHub source (`0.7.3` tag or `main`) rather than the stale npm package, to measure how much of the 4.9% file-error rate the real upstream fix for bug 1 actually closes — worth doing for intellectual completeness given how cheap it is, but not expected to change this decision, since bugs 2 and 3 remain unfixed regardless and the underlying cascading-vs-localized correctness argument doesn't depend on the exact error percentage.
