## Real findings from the 2026-09-21 look-and-report pass (don't re-derive these, verify and build on them)

A same-day investigation (not a full build) already found real, checked structural differences between this repo and `android-intercom-oskey-io` that mean the existing screen-map heuristic does **not** transfer cleanly:

- **Path convention differs**: real screens live under `app/src/main/java/io/oskey/app/ui/view/screens/`, not `ui/screens/` — the extraction script's `file LIKE '%ui/screens/%'` filter would match zero rows here even once facts exist.
- **The `navController: NavController` parameter discriminator does not transfer, and fails in the opposite direction from android-intercom.** A real spot-check across all 71 `*Screen.kt` files found roughly half of the real, confirmed screen composables take **zero parameters** (or a `ViewModel`/`FirebaseAuth`/other, never `NavController`) — e.g. `OSKActivitiesScreen()`, `OSKMainHomeScreen()`, `OSKUserDevicesScreen()`. Navigation here is centralized through a real `NavigationManager`/`NavigationDispatcher`/`NavigationCommand` system (`app/navigation/`), not passed into each screen directly. Reusing the android-intercom rule as-is would produce large real false negatives (dropping ~half of real screens), not false positives.
- **File-basename-matching (composable name == containing file's basename) does better but is not clean either**: 64/71 real `*Screen.kt` files matched cleanly, but two confirmed real false positives were found on a direct read:
  - `app/src/main/java/io/oskey/app/ui/view/screens/menu/navigation/Screen.kt` — a `sealed class Screen` with placeholder-looking case names (`MainScreen`, `AnotherScreen`, `EditPersonScreen`) that reads as dead/legacy code, superseded by the real navigation system below — not a real screen.
  - `app/src/main/java/io/oskey/app/ui/view/screens/menu/helpcenter/OSKCallCenterScreen.kt` — contains only `fun launchCallCenter(context, phoneNumber)`, a plain utility that opens the phone dialer. Not a Composable, not a screen.
  - Plus several real near-misses where the composable name doesn't exactly match its file's basename (e.g. `OSKCameraScreen.kt` actually declares `OSKCameraQrScanScreen`) — the same naming-drift pattern already found and manually corrected for on `ios-oskey-dev`'s screen map.
- **A genuinely promising, real signal exists here that neither Android repo nor `ios-oskey-dev` had**: `app/src/main/java/io/oskey/app/navigation/destinations/` holds 11 files (`OSKMenuDests.kt`, `OSKAuthenticationDests.kt`, `OSKAccessesDests.kt`, `OSKActivitiesDests.kt`, `OSKBuildingDests.kt`, `OSKLoadingDests.kt`, `OSKMainDests.kt`, `OSKNotificationsDests.kt`, `OSKProfileDests.kt`, `OSKSplashDests.kt`, `OSKUnitInvitationDests.kt`), each a real `sealed class ... : NavigationAction` whose `object`/`data object` cases declare an explicit `route: String` (62 real route declarations total, confirmed by direct grep). Structurally, this is the closest thing found anywhere in this whole exercise to Angular's real `angular_route` facts — a genuine declarative route registry, not a naming heuristic. **This is the real, concrete lead this investigation should chase first.**
- **A third, different real navigation convention also coexists in this same codebase**: `kotlin-core-kit-oskey-io/utils/src/main/java/io/oskey/utils/OSKScreen.kt` defines type-safe Navigation-Compose `@Serializable` destinations (`object DeviceListScreen`, `data class DeviceDetailsScreen(val macAddress: String)`) — the modern Navigation-Compose 2.8+ convention, distinct from both the `OSK*Dests.kt` pattern and the dead `menu/navigation/Screen.kt`. Not yet wired to real screen UI in that module (its only real `@Composable` is `SignalStrengthBar`, a subcomponent, not a screen) — flag this as a real inconsistency to design around, not something to quietly ignore.
