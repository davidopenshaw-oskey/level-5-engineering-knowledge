# Standing Principles (2026-09-07) + Real Lessons Carried Forward From the TypeScript Facts Pipeline

**Why this file exists:** per direct user instruction 2026-09-07 — significant real time was spent getting the TypeScript facts pipeline (P1 extraction → P2 Postgres/pgvector index → atomic-PRD generation) to actually produce a usable PRD. That history contains real, hard-won, generalizable lessons this repo's own P1/P2 design should inherit rather than re-discover the hard way. This is a working-notes file, added to as research continues — not a finished design doc.

## Standing principles, given directly by the user 2026-09-07 — apply to all future work on this repo

**1. Config shape can differ per language/repo.** `config/repos.json`'s single-string `modulesRoot` field (built for repos with one shared module directory) does not need to be force-fit onto this repo's 5 physically separate Gradle module directories. Resolves the "config-schema gap" flagged in `00-phase1-ast-extraction-design.md` — that's not a problem to solve by generalizing the shared schema, it's fine (expected, even) for this repo's config block to look structurally different. Design it for what this repo actually is.

**2. Extraction must be dynamic — never hardcode names, lists, or counts.** A repo's structure today is not its structure tomorrow: modules get added/removed, functions get added/removed, screens get added/removed. Any P1 script that hardcodes a module name, a fixed screen list, a fixed count, etc. will silently go stale the first time a dev changes the repo, with no error — the same shape of silent failure this whole document's P1 quality lessons are about, just at the "does this even still describe the repo" level instead of "does this fact capture the right content" level.

   **Real, explicit tension with existing precedent, not glossed over:** `node-iot-api-oskey-io`'s own `00-scan-repo.ts` hardcodes `HARDCODED_MODULE_NAME = "access_control_device"` and its submodule-root regex hardcodes the literal prefix `access_control_device_` (see `pipeline/node-iot-api-oskey-io/phase-01-ast-extraction/00-scan-repo.ts` lines 42, 336). That was a deliberate, documented choice at the time (no real folder existed to derive the name from) — but per this new standing principle, **it is not a pattern to copy for this repo**. Concretely:
   - Kotlin's module list must be read dynamically from `settings.gradle.kts`'s real `include(...)` calls at scan time, not hardcoded as a literal array — a module added or removed shows up automatically.
   - The submodule-root-detection technique (candidate: BFS from `OSKIntercomNavigation.kt`'s `NavHost { composable(...) }` blocks, see `00-...md`) must extract the real screen/route list from that file's real AST at scan time — never a fixed list of screen names typed into the script.

**3. Record findings in this folder as research happens, not from memory at the end.** Matches this project's own `CLAUDE.md` discipline. This file, and `00-phase1-ast-extraction-design.md`, are both living documents for this repo's onboarding — update them directly as real findings land, same discipline the TypeScript pipeline's own `05-tasklist.md`/`09-p2-build-tasklist.md` used throughout.

## Real lessons from the TypeScript P1 extraction quality history (`facts-serving-strategy/`)

**A "fact" is a pointer, not a payload — by deliberate design, not a limitation to work around.** Confirmed and settled (`03-finding-facts-are-pointers-not-payloads.md`, `06-scope-clarification-and-staleness-finding.md`): this pipeline's job is to extract/index/organize facts as a snapshot-in-time source of truth; the dev/agent consuming its output is expected to have their own repo checkout and follow the pointers to real source. Don't design Kotlin extraction to try to capture full function bodies or "everything" — design it to capture precise, correct pointers plus specific, high-value structured content (see next point), the same balance the TS pipeline settled on.

**But closed-set/enum-shaped content is high-value enough to capture in full, and the TS pipeline paid a real, measured retrieval-quality cost for missing it initially.** Real chain of evidence: a real enum fact (`ActivityUserType`) always carried its full `members` array; a real type-alias union fact (`OSKAccessValidity`, a plain `'oneTime' | 'permanent' | 'recurrent'` union) originally carried none. This wasn't just a schema asymmetry — a real retrieval test against `OSKBuildingUnitInhabitantType` failed to surface it for a directly-relevant query, and even after the fix made its description genuinely correct ("possible values: owner, tenant, resident"), it only moved to rank 319 of 20,678 — still not top-10, because the query's action-shaped phrasing ("what happens if we **add**...") structurally favored action-shaped facts (methods) over declaration-shaped facts (type definitions). **Two separate, real lessons here, both directly relevant to Kotlin:**
- **Extraction lesson**: capture every closed-set value from day one — Kotlin `enum class` members AND `sealed class`/`sealed interface` subclass names (the item 2 concern from `00-lessons-from-typescript-angular-extraction.md`, now backed by real evidence of *why* it matters, not just structural risk). Don't wait to discover this gap the way TS did.
- **Retrieval-architecture lesson, carried forward as institutional knowledge, not extraction-specific**: pure vector similarity has a real, structural ceiling for declaration-shaped facts against action-phrased queries, even with fully correct content. Relevant when Kotlin facts eventually get served through the same MCP/search layer — not something richer extraction alone fixes.

**Generic type arguments must be descended into, not stopped at.** Real TS finding: `OSKDocument<X>`-wrapped models (this codebase's near-universal Firestore pattern) had their real field shape completely invisible until `collectTypeLiteralProperties` was fixed to descend into `TypeReferenceNode.getTypeArguments()`. Same for inheritance: `OSKBuildingUnitInhabitantController extends OSKDocumentController<OSKBuildingUnitInhabitant>` — the specific generic instantiation, not just the resolved base class — had to be captured via the real heritage-clause expression (`getExtends()`), not the declaration-resolving `getBaseClass()` (which loses it). And return types: `Promise<OSKDocument<X> | undefined>` needed the same generic-argument surfacing.

**Real Kotlin/Android analog to watch for, not yet confirmed against this repo's real code:** anywhere a real domain type is wrapped in a generic container — `Flow<T>`, `StateFlow<T>`, `LiveData<T>`, `Result<T>`, a Hilt `@Provides` function's generic return, a sealed class's typed subclass — the same "descend into the type argument, don't stop at the wrapper" discipline applies. Not yet checked directly against this repo's real code (e.g. do `ConnectionViewModel`/`OSKMainActivityViewModel`'s `StateFlow<T>` properties wrap real domain types worth surfacing this way) — a real thing to check once P1 extraction is actually being built, same "verify, don't assume" discipline as everything else in this repo's onboarding.

**What gets *embedded for search* is a separate design surface from what gets *extracted* — audit both, explicitly, per fact kind.** The single most-repeated real bug pattern across the whole TS history: rich, correct fields already existed in a fact's payload (`requestType`, `handlerExpression`, `callerClass`, `calleeExpression`, `unionMembers`, generic-argument-resolved field shapes) but were never surfaced in the actual text handed to the embedding model (`descriptionFor()` in `sync-facts.ts`) — found five separate times, across five different fact kinds, each requiring its own explicit fix and re-embed. **Direct implication for Kotlin**: when this repo eventually gets its own `descriptionFor()`-equivalent, don't assume getting extraction right is sufficient — explicitly check, per Kotlin fact kind, whether everything worth searching on is actually reaching the embedded text, the same audit discipline, not assumed transferable from TS's fix list (Kotlin's fact kinds will differ — Compose composable parameters, Hilt injection sites, BLE/WebRTC/USB protocol constants — each needs its own version of this same check).

**A single generic "identity/name" field extractor is not safe to assume across fact kinds — verify per kind, against real retrieval, not just the schema.** Real, majority-of-data bug: 56% of the entire TS index (11,530 of 20,678 facts) had their `symbol_name` silently wrong because `symbolNameFor()` only checked a `name` field, while `permission_candidate` facts (and others) actually carried their real identity under `value`, with the real human-readable name nested inside `evidence.name` — found only by noticing junk "(unnamed)" results ranking above real matches in a live retrieval test, not by code review. **Direct implication for Kotlin**: whatever fact kinds get designed (Composable declarations, `@Inject` sites, `sealed class` subclasses, BLE service/characteristic constants, etc.), explicitly verify where each kind's real identifying name actually lives before trusting one generic extractor function across all of them — test against a real query, the way this bug was actually found, not just by reading the extraction code.

## Real lessons from P2 / retrieval architecture (`facts-serving-strategy/09-p2-build-tasklist.md`, `13-atomic-prd-pipeline-tasklist.md`)

**Pure vector search + a calibrated confidence threshold is the proven combination — hybrid keyword+vector search was tried and reverted, a real negative result.** `pg_trgm` fuzzy/keyword matching was built, tested against all real example queries (not just the one it was tuned against), found to never once contribute the actual best result, caused a real regression on a previously-working query, and added noise elsewhere. Reverted. **Don't re-attempt hybrid search for whatever Kotlin's own future retrieval layer becomes without new, real evidence** — this was already tried once, for a real reason, and failed for a real, measured reason.

**A "confident" result can still be substantively, topically wrong — root cause was (again) an under-described fact, not a flaw in the threshold concept.** A query returned `confident: true` under the 0.76 distance threshold with 10 plausible-looking results — all for the wrong actor's code path. Root-caused directly: the *correct* fact was under-described (bare `"{kind} in {module}: {name} (file:line)"`, nothing more for the embedding model to work with), so a generic pattern won by default. This is the same "what gets embedded" lesson above, surfacing again at the confidence-threshold layer — worth remembering as a recognizable failure shape (confidently-wrong ≠ honestly-uncertain) rather than a new problem each time it appears.

**Real, current MCP/agentic-search architecture this whole project already committed to (ADR-007/008, corroborated independently by Sourcegraph's own real 2026 published architecture — `market-research/10-findings-sourcegraph-codebase-analysis-2026-09-06.md` §4)**: deterministic, fact_id-cited facts exposed through an MCP server to an agent persona that decides how to use generic tools (`search()`, `findGraphNeighbors()`, `walkBoundedCluster()`), not a fixed hardcoded pipeline per task and not an embeddings-only RAG fusion. Whatever Kotlin's P2/MCP-serving side becomes should plug into this same existing tool layer, not invent a parallel one — consistent with the `mcp-server/`-coupling question Task 1's peer session is currently resolving.

## Real lesson from the atomic-PRD pipeline shape (`facts-serving-strategy/12-atomic-prd-template.md`, `13-...md`)

Three-layer document split, real and built: **Layer 1** (PM's own words, no LLM), **Layer 2** (deterministic render of real search results + citations, no LLM), **Layer 3** (one single LLM call producing the technical proposal + user stories + acceptance criteria + constraints together, grounded only in Layer 2's real evidence, every citation checked against what was actually retrieved — never fabricated across real runs). Every placeholder is a single, already-fully-rendered string per section, never per-field tokens (a real, twice-repeated bug class before this rule was enforced). This shape is repo-agnostic by design — nothing about it is TypeScript-specific — so a Kotlin-sourced fact making it into this same pipeline later should be able to flow through this exact template unchanged, *if* the fact schema and `descriptionFor()`-equivalent are built with the same care documented above.

## Real, Kotlin-specific extension worth considering — not yet designed, a candidate only

The TS pipeline found real, high-value structured "wire format" facts worth resolving deterministically at extraction time — `firestore_path_touched` (real `.collection()`/`.doc()` chains resolved to clean template paths, proven via a real query returning exactly the right paths in the top 4, and found to be *more* precise and *less* stale than the static `governance/reference-docs/firestore-schema.md` it eventually superseded). **This repo's own domain has real analogs worth the same treatment, once P1 design actually starts**: BLE GATT service/characteristic UUIDs (`kotlin-ble-kit-oskey-io`), USB vendor/product IDs and command constants (`kotlin-usb-oskey-io`), WebRTC signaling event/message-type names (`kotlin-webrtc-data-oskey-io`) — this repo's own equivalent of "what does the wire protocol actually look like," resolvable from real code the same way Firestore paths were, and likely to matter just as much for real PRD questions about edge-device behavior. Not designed here — flagged as a real, concrete candidate for whenever P1's fact-schema design for this repo actually begins.

## Real, related upgrade path for extraction-coverage verification

Sourcegraph's own SCIP tooling publishes a real, named **snapshot/golden-testing** practice (`scip snapshot` — regenerates annotated source from an index, diffed for correctness) as their answer to "did my AST walker actually see everything it should have" (`market-research/10-...md` §5) — a more mature, build-time/preventive version of this project's own reactive grep-cross-check discipline (the "92 of 160" technique). Since `sourcegraph/scip-kotlin` is a real, named tool already identified as a candidate for this repo's own extraction tooling (`market-research/08-...md`), this snapshot-testing technique would come along with it "for free" if SCIP is adopted — worth weighing directly against building a bespoke JSON-emitting extractor without it, when that tooling decision is actually made.
