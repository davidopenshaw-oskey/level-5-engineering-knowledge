## Real gaps found and fixed in `01-extract-ast-evidence.ts` before Task 8 could even start

Task 8 couldn't be built directly against Tasks 4-7's own real output — three real, load-bearing gaps surfaced immediately on inspection, all fixed and re-verified before writing `02`:

1. **`imports_dependency` facts didn't exist.** The real emission was one row per FILE with a raw, unresolved `imports: string[]` array — not the per-import, resolved shape (`resolvedTargetModule`/`resolvedTargetSubmodule`/`importResolutionStatus`) that `06`/`07`'s cross-module/intra-module coupling graphs need, and that the TS pipelines' own `01` scripts already produce via ts-morph's compiler resolution. Fixed: a second walk over each file's real `import_header` nodes, resolved against the same project-wide `declLocation` table Pass 1 already built for call-expression resolution (Kotlin imports are already fully-qualified names, so no further disambiguation is needed the way a call's bare identifier requires). Real result: 1,796 real import statements, 244 resolving in-repo, 38 of those genuinely cross-module.
2. **No parse-error tracking or `astErrorTolerancePercent` enforcement.** `config/repos.json`'s `astErrorTolerancePercent: 5` (a real, measured baseline from Task 1) was recorded but never actually read anywhere. Fixed: `tree.rootNode.hasError` (a property, not a method, in this tree-sitter version — confirmed by hitting a real `TypeError` first, not guessed) flags per-file parse errors into a new `ast-errors.json`, gated against the configured tolerance exactly like the TS pipelines' own established convention. Real result on this run: 6/136 files (4.41%) — matches Task 1's own measured 4.4% baseline almost exactly, a strong real cross-check that both measurements are sound.
3. **No `ast-evidence-manifest.json`.** Every TS repo's own `01` writes this (confirmed by grepping all three), and `02` fail-closed validates every real evidence type/record-count against it before trusting any raw fact file. Kotlin's `01` never wrote one. Fixed: added, with Kotlin's own real `EXPECTED_EVIDENCE_TYPES` list (imports, classes, objects, interfaces, functions, enums, sealedHierarchies, properties, calls, webrtcSignalingTouchpoints, bleGattConstants, usbWireConstants — no methods/exports/typeAliases/mongoOperations/routeDefinitions/joiSchemaFields, none of which exist for this repo).

A fourth, smaller real gap: neither `function_declaration` nor `model_property` facts carried an `owningClass` field for non-constructor-promoted members (only Task 6's own constructor-promoted-property fix had one). Added `owningClass` (via the same `findEnclosingClassName` helper already used for calls) to both, for the same reason TS's own `service_method` facts carry `className` from extraction time — a real identity/context need Task 8 depends on for `stableFactId` secondary keys, not invented signal.

All four fixes re-verified against the real repo after applying: extraction counts (196 classes, 45 objects, 13 interfaces, 589 functions/51 composable, 17 enums, 12 sealed, 1551 properties, 5338 calls, 22 BLE/21 USB/14 WebRTC) are byte-identical to Tasks 4-7's own already-verified baselines — these were real additions, not regressions.

## `02-build-module-evidence.ts` — real re-design, not a port

TS's own `02` is deeply Firebase/node-iot-specific (Mongo operations, route definitions, Joi schema fields, PubSub routing, `classifyMethod` service/controller suffix rules). None of that exists for this repo, and `classificationRules` was deliberately left unset in `config/repos.json` (Task 2's own note: this repo's naming style — `UseCase`/`Impl`/`Manager`/`Helper` — hasn't been properly investigated). Real fact-type mapping built instead, matching Task 7's own pre-verified enrichment spec exactly: `source_file`, `source_class`, `kotlin_object` (Kotlin-only), `source_interface`, `function_declaration` (+ `isComposable`, `owningClass`), `enum_declaration`, `kotlin_sealed_hierarchy` (Kotlin-only), `model_property` (+ `isConstructorPromoted`, `owningClass`), `call_expression` (+ honest `resolutionMethod`), `imports_dependency`, `ble_gatt_constant`/`usb_wire_constant`/`webrtc_signaling_touchpoint` (Kotlin-only). `stableFactId` ported with the same `line`-excluded-from-identity discipline as TS's own (governance/roadmap/03-token-economics-remediation-plan.md Stage 1), with defensive occurrence ordinals on every fact type where a same-file collision is plausible (nested classes, function overloads, repeated call sites).

**Real bug found and fixed post-build, by direct verification, not by re-reading the code:** every non-`source_file` fact type used `item.path` (copied from TS's own field-naming convention) instead of `item.file` — Kotlin's own raw evidence files (`ast-classes.json`, `ast-calls.json`, etc., built in `01`) use `file` as the field name; only `files.json` itself (built in `00`) uses `path`. This silently produced facts with an empty top-level `file` field and a visibly malformed ID (`source_class|app||Access|#1` — note the double `||`). Caught by manually calling `descriptionFor()` against real facts pulled straight from a real capability pack and seeing `(no location)` on every single case, not by reading the script and assuming it worked from the summary counts alone (the console.log summary counts never surface a field-name bug like this — they only count records, not validate field contents). Fixed by replacing every `item.path` with `item.file` outside the one `source_file` block that genuinely reads from `files.json`. Re-verified: all 12 real fact-kind test cases (one per Task 7 enrichment branch) now produce correct, real, located descriptions, e.g. `call_expression in app: invoke -- inside: OSKGetAccessesUseCase -- calls: accessHeartbeat -- resolves to: .../OSKGetAccessesUseCase.kt (resolved_via_same_package) (app/.../OSKGetAccessesUseCase.kt:47)`.

This is the same class of lesson `01`'s own `composableFunctions: 0` and `interfaces: 0` bugs were (Task 4) — a blind port of a field name or grammar assumption from one context (TS field-naming, or a synthetic snippet) silently produces plausible-looking but wrong output, caught only by testing against real data end-to-end, never by code review alone. Recorded here because it's the same real, portable lesson, not a one-off.

Real, verified per-module output (facts sum to 9,750 across 5 modules, matching Task 6's own repo-wide total exactly): `app` 6,493, `kotlin-ble-kit-oskey-io` 1,410, `kotlin-usb-oskey-io` 183, `kotlin-webrtc-data-oskey-io` 1,405, `kotlin-webrtc-domain-oskey-io` 259.

## `04-build-resolved-graph.ts` — real re-design, addresses the flagged eligibility-filter concern

TS's own `04` runs "Rule A: exact compiler declaration match" at THIS stage, because a whole-project compiler symbol table only becomes available after the fact. Kotlin has no such table (Task 1's own real, honest capability gap) — resolution already happened in `01`, so this script's real job is narrower: classify each already-resolved-or-not call's real graph *eligibility*, then aggregate into edges. This directly builds the real eligibility filter `02-p1-build-tasklist.md`'s own Task 8 note called for.

**Real, measured `NOISY_CALL_ROOTS` list** (not guessed): computed the actual root-identifier frequency distribution across all 4,689 real unresolved calls before writing the filter. Top entries confirmed real and external: `Timber` (665), `viewModelScope` (134), `Modifier` (~250 combined across whitespace variants), `Row`/`Box`/`Text`/`Column`/`Spacer` (Compose layout primitives), `remember`/`LaunchedEffect` (Compose state), `UUID`/`Gson`/`Color`/`MediaConstraints`, `withContext`/`delay`/`run` (Kotlin coroutines/stdlib), `mapOf`/`listOf`/`byteArrayOf` (Kotlin stdlib), `composable`/`intent`/`navController` (Android Navigation/Compose). Deliberately did **not** exclude lowercase-starting roots as a general heuristic (`it`, `data`, `scope`, `context`, `viewModel`, `socketIO?`, `mGattManager?`, `usbDevice`, `mBleManager`) — these could genuinely be local variables holding a real in-repo type (e.g. `repository.getAccesses()`) that this syntax-only tool simply can't type-resolve; sweeping them into "non_graph_call" would silently hide a real, honest gap instead of reporting it. They stay in the `unresolvedEligibleCalls` bucket.

**Real bug found and fixed while building the filter:** a naive `expr.split(".")[0]` on a real multi-line Compose modifier chain (`Modifier\n    .fillMaxSize()`) returns `"Modifier\n    "` with embedded whitespace, which silently fails to match a plain `"Modifier"` set entry — confirmed by seeing 4 near-duplicate `"Modifier"` entries (differing only in trailing whitespace) in the real frequency count before the fix. Fixed with `.trim()` in `extractCallRoot`, plus stripping a trailing `?` (Kotlin safe-call syntax, e.g. `socketIO?.emit`) so a root matches consistently regardless of null-safety syntax at the call site.

Real, verified output: 5,338 input calls → 1,748 excluded (known external) → 3,590 graph-eligible → 41 real cross-module call edges (e.g. `app -> kotlin-ble-kit-oskey-io: OSKBluetoothUtility.getBluetoothManager`, `app -> kotlin-usb-oskey-io: OSKCustomUsbIntercomDevice`) + 608 same-module resolved + 2,941 honestly unresolved-but-eligible. Every edge tagged `probable` (resolved via explicit import) or `weak` (resolved via same-package visibility) — never `confirmed`, per Task 1's own established, honest vocabulary.

## `05`/`06`/`07` — mechanical ports, real value confirmed

All three are fully generic (operate only on `fact.module`/`fact.submodule`/`imports_dependency`'s own fields), so no repo-specific redesign was needed — confirmed by reading the TS source first, not assumed. Real, verified output:

- **`05` (capability packs)**: `app` correctly partitions into 13 packs (11 real screens + `_unreferenced` + `_module_root`), summing exactly to `app`'s own 6,493 facts. The 4 library modules each get exactly one `_module_root` pack, per Task 3's own uniform-`submodule=null` decision.
- **`06` (cross-module dependency graph)**: real, sensible layered architecture surfaced — `app` depends on 3 modules (ble-kit, usb, webrtc-domain); `kotlin-webrtc-data-oskey-io` depends on `kotlin-webrtc-domain-oskey-io` (1 outbound); the domain module receives from both `app` and the data module (2 inbound) — a real domain/data-layer split, not noise.
- **`07` (intra-module coupling)**: real and non-trivial for `app` only (13 submodule buckets, every real screen coupling both ways with `_module_root` — expected for shared navigation/ViewModel infrastructure); honestly empty for the 4 library modules (uniform `submodule=null`, same "correctly, honestly stays empty" precedent as node-iot's own zero-signal RBAC section). One real finding, flagged here as unexplained and since investigated: `Home` receives an inbound coupling from `_unreferenced`. **Explained 2026-09-09, see `16-real-downstream-consequence-of-unreferenced-tagging-2026-09-09.md`** — traced to `OSKGetCurrentLocation.kt`'s own real outbound import, itself mistagged `_unreferenced` by Task 3's already-known, deliberately-accepted same-package-without-import limitation (not a new bug; the edge is real, only its source label is wrong). That same investigation found and fixed two other, previously-undocumented real bugs in `00-scan-repo.ts` (unseeded infra files; unmatched qualified companion-member imports) — see that file for the full fix and re-verification.
