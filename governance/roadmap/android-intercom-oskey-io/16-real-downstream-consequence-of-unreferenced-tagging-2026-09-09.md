# Real downstream consequence of the `_unreferenced` reachability tag, found via a live agent query — 2026-09-09

Cross-pipeline finding, surfaced from the MCP-direction side (`governance/roadmap/mcp-direction/`), not from within this repo's own extraction work — reported back here because the root cause is this repo's own reachability heuristic (`00-scan-repo.ts`), not the agent or the MCP tools.

## What happened

First real business-query test of `android-intercom-oskey-io` through the governed `atomic-prd-agent.ts` pipeline (business request: adding a config-driven home-screen button to the Intercom, linked to a Call Directory entry). Two consecutive runs both failed with the same class of error:

```
Error: [Fail-Closed] Graph edge(s) reference fact_id(s) not found in facts: <fabricated-looking fact_id>
```

Investigated directly with `DEBUG_TOOL_LOG` (full tool-call input/output capture) plus a direct Postgres check of the fabricated IDs against `facts` and `cross_repo_edges` — confirmed both fabricated IDs exist nowhere in the real data. **The model itself constructed malformed `walk_cluster` anchor arguments** — not a stale-edge bug, not the tool layer.

## Real root cause, traced to this repo's own known limitation

The model's fabricated IDs closely mimicked real `description` text it had already seen this run, e.g.:

```
source_class in app/_unreferenced: OSKCustomConfiguration (app/src/main/java/io/oskey/intercom/model/OSKCustomConfiguration.kt:18)
```

`_unreferenced` here is the real `submodule` value `00-scan-repo.ts` assigns to any file its reachability BFS finds zero incoming references to (`if (count === 0) submoduleByAppFile.set(f, "_unreferenced")`) — the exact mechanism this file's own inline comments already flag as a real, found-2026-09-09 source of false positives (Hilt `@Module` files, the `Application` subclass, same-package files referenced without an explicit import — all real, live, load-bearing code the BFS still marks `_unreferenced`).

**This business query landed directly on more real instances of that same pattern.** `OSKCustomConfiguration.kt` and `OSKConfigurationData.kt` (both central to `homeButtons` — the exact config-driven button mechanism the business request is about) are tagged `_unreferenced`, alongside `OSKGetCurrentLocation.kt` and `OSKDeviceConfiguration.kt`. Not independently confirmed as true false positives the way the Hilt/Application/same-package cases were (that would need the same direct-evidence check this repo's own Task work already applies), but the pattern — a config/model class plausibly instantiated via deserialization rather than a traceable direct call — looks like the same class of gap, not a new one.

## The real, new piece of information this adds

This repo's own Task 7 (`14-...md`) verified the `descriptionFor()` enrichment "in isolation against real fact objects" — correctly, but that can't surface this: **an LLM agent consuming these facts across a real multi-turn conversation appears to sometimes pattern-match the literal `_unreferenced` text into a constructed fact_id string, rather than copying a real `factId` field verbatim** — the same general citation-fidelity weakness already found and partially fixed on the persona side (`governance/roadmap/mcp-direction/24-fabrication-root-cause-backtick-instruction-2026-09-08.md`), now triggered by this repo's specific description text rather than persona wording. Confirmed by checking two independent failed runs against real tool-call logs and Postgres directly — not inferred from one instance.

## Real, two-sided implication

1. **Reachability side (this repo)**: every file this BFS mislabels `_unreferenced` isn't just a lower-confidence tag — it now has a demonstrated, concrete downstream cost (breaking real agent queries), not just a theoretical accuracy concern. **DONE 2026-09-09, see the section below.**
2. **Persona/agent side (mcp-direction)**: worth considering an explicit instruction that `_unreferenced` (and similar internal markers) are description-only text, never part of a real fact_id — mirroring the backtick fix's approach. Owned by a separate peer session's work on `atomic-prd-agent-skills.md`; not applied by this file.

## Real root cause and fix, 2026-09-09 (reachability side)

Checked all 4 named files directly against the real repo (imports, call sites), not guessed. Two distinct, real, previously-undocumented bugs in `00-scan-repo.ts`, plus one already-known, deliberately-accepted limitation:

1. **`OSKCustomConfiguration.kt` / `OSKDeviceConfiguration.kt`**: both referenced ONLY from `OSKApplication.kt` (the `Application` subclass, real on-device JSON config loading). The BFS already correctly pins `Application`-subclass/`@Module`/`NavHost`/sealed-`Screen`-class files to shared (`null`) — but never used them as additional BFS *seeds*, only as reassignment-exempt leaves. Their own real outgoing imports were dead ends nothing ever traversed. **Fixed**: these "infra seed" files now get their own BFS pass (`infraSeedFiles`/`sharedReachableFiles`, same `edges` graph, no new edge types, no reintroduced cascading risk) — anything reached only that way is genuinely shared/core, not `_unreferenced`.
2. **`OSKConfigurationData.kt`** (app's `utils` one) — **correction, checked directly after an initial overclaim**: first pass here reported this file as a second real bug, based on finding that ~19 real screen/ViewModel files reference it exclusively via qualified companion-member imports (`import io.oskey.intercom.utils.OSKConfigurationData.Companion.DEFAULT_LANGUAGE`, a real, common Kotlin idiom the import-matching code's bare-top-level-name-only lookup genuinely can't resolve). **That diagnosis of the underlying bug is correct and independently confirmed** (verified directly: `packageAndImportsOf` really does return the full qualified string as one token, which never matched `declLocation`'s bare-name keys) — but the claim that this file itself was mistagged was never checked against its actual before-fix `submodule` value before reporting it. Direct check of the real `files.json` from both runs shows `OSKConfigurationData.kt` was **already correctly tagged `null` (shared) before any fix**, via 3 of its ~19 real referencing files using a plain, unqualified `import io.oskey.intercom.utils.OSKConfigurationData` that the original exact-match code already resolved. The original finding doc's own caveat ("not independently confirmed as true false positives") was correct to flag this risk; it should have been checked before being reported as a confirmed instance. **Fixed anyway, and kept**: `resolveImportTarget()` now tries the full qualified text first, then progressively strips trailing `.Segment` pieces until a real `declLocation` entry matches — a real, general fix for a real, common Kotlin idiom this pipeline should handle regardless of today's data, but **not demonstrated to change any file's final tag in this run** (every real case checked already had a fallback bare-import path). Only fix 1 above (`infraSeedFiles`) is confirmed, by direct before/after comparison, to have changed any real output.
3. **`OSKGetCurrentLocation.kt`**: confirmed this is NOT a new bug — it's the already-known, already-documented same-package-without-import limitation from Task 3 (the general fix for that class of gap was tried twice and reverted after real re-runs showed cascading collapse through shared utility packages). Left as-is, deliberately. As a direct, now-*explained* consequence: `07-build-intra-module-coupling-graph.ts`'s own real output showed `Home` receiving an inbound coupling edge from `_unreferenced` (flagged as an open, unexplained anomaly in `15-task8-downstream-scripts-built-and-verified-2026-09-09.md`) — traced directly to `OSKGetCurrentLocation.kt`'s own real outbound import to `OSKConfigurationViewModel`; the edge is real, only its *source* label is wrong, for the same accepted reason. Not a new anomaly, not fixed further.

**Verified end-to-end, not assumed**: re-ran `00` through `07` fresh (new run `20260909_123417-a15cce18`). `_unreferenced` file count dropped from 24 to 22 in the fresh `00` output — matches exactly the 2 real files fix 1 (`infraSeedFiles`) changed (`OSKCustomConfiguration.kt`, `OSKDeviceConfiguration.kt`); `OSKConfigurationData.kt` was already `null` before any fix (see the correction above) and `OSKGetCurrentLocation.kt` correctly unchanged. All other extraction counts (9,750 total facts, every declaration-kind count) identical to the pre-fix run — confirming this was a pure submodule-tagging correction, zero facts added/removed/miscounted. Re-synced all 5 modules into Postgres: only 23 facts had their `description` text actually change (the ones belonging to the 2 reclassified files, whose `submodule` value change is embedded directly by `descriptionFor()`) — re-embedded those 23 for real (trivial cost), the other 9,727 kept their still-valid embeddings untouched. Confirmed directly against Postgres: zero remaining `_unreferenced` text in any fact belonging to those 2 files.

This does not fully close side 2 (the persona/agent instruction fix) — that remains a separate, real next step, owned elsewhere. But the specific trigger text this incident's own two failed runs actually fabricated from (`app/_unreferenced: OSKCustomConfiguration`) no longer exists in the live index.
