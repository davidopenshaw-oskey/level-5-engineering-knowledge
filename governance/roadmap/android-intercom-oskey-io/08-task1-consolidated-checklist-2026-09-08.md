## Where we actually landed, in one paragraph

No single tool wins outright. The real shape: a syntax-only tool (tree-sitter-kotlin, or `kotlinx.ast` as a second candidate) can very likely handle the bulk of declaration-level facts (enum members, sealed subclasses, generic type-argument descent) — confirmed by re-reading the real TS extraction code, most of that turned out to be pure syntax-tree walking already, not real semantic resolution (`06-...md`). But real, compiler-exact call-graph/RBAC/cross-module-dependency resolution — this repo's most valuable outputs — depends entirely on whole-project symbol resolution that no syntax-only tool can do at all (`07-...md`). That's the real fork the checklist below needs to resolve.

**Test harness used**: `tree-sitter@0.21.1` + `tree-sitter-kotlin@0.3.8` (npm), a small Node script parsing real files directly from `output/clones/android-intercom-oskey-io` and walking the resulting tree for `ERROR`/`isMissing` nodes. Run session-local (scratchpad, not preserved) — every result below is reproducible from these exact package versions plus the specific real file paths and isolated repro snippets cited inline.

### A. Bounded parse test — does tree-sitter-kotlin actually choke on *this* repo's real code?

Tree-sitter-kotlin self-reports 61.2% structural accuracy overall, with two specific known bugs (`market-research/20-...md`) that may or may not actually trigger on this repo's real files. Test each, using this repo's actual source (`output/clones/android-intercom-oskey-io`):

- [x] Parse `OSKIntercomNavigation.kt` — **zero errors.** 22 real `composable(...)` trailing-lambda calls, all structurally clean (`call_expression → call_suffix → annotated_lambda → lambda_literal → statements`, correctly nested). The `lambda_nesting` bug did not fire on this repo's real usage.
- [x] Parse real constructor-bearing enums — **zero errors, on both real domain examples.** `OSKAccesses.kt`'s `AccessRightsValidity`/`AccessMethodsType` (`PERMANENT("permanent")`, `Pincode("pincode")`, etc.) and `OSKTestBenchState.kt`'s `MotorPosition(0.toByte())` all produced correct `enum_entry(simple_identifier, value_arguments)` shapes — member name AND constructor arg both cleanly extractable. The `enum_entry_constructor` bug did not fire here either.
- [x] Parse a real sealed hierarchy — **zero errors.** `OSKIntercomScreens.kt`'s `sealed class Screen` plus its 11 real `object` subclasses (`Home`, `Settings`, `OpenDoor`, etc.) all parsed cleanly with correct `delegation_specifier` inheritance clauses. Confirms the "not in the known-issue list" read was right.
- [x] Checked for an indirect enum/sealed reference (bare-identifier `when` branch) — **not found anywhere in this repo** (direct grep across all `.kt` files). This specific gap from `06-...md` item 1 is real in general but not applicable to this codebase today.
- [x] Checked an unannotated/inferred `val` (`OSKMainActivityViewModel.kt`'s `_currentRouteFlow = MutableStateFlow<String?>(null)`) — **the generic type argument (`String?`) is still recoverable** even with no top-level type annotation, because it's written explicitly on the constructor call itself (`type_arguments` node parsed correctly). The `06-...md` item 3 gap looks smaller in practice than feared, at least for this repo's real style.
- [x] **New finding, not in either documented bug list**: ran tree-sitter-kotlin across all 136 real `.kt` files in this repo. **130/136 (95.6%) parse with zero errors** — meaningfully better than the grammar's own generic 61.2% self-reported number (that number is against a broader, more adversarial cross-validation corpus, not representative of this specific codebase's style). **6 files (4.4%, 22 error nodes total) do have real parse errors**, including two in this repo's actual BLE/USB motivating-content modules (`kotlin-usb-oskey-io/UsbIntercomDevice.kt`, `kotlin-ble-kit-oskey-io/OSKBleAdvertiseHelper.kt`). **Root cause found for the majority case (4 of 6 files): a genuine, previously-undocumented tree-sitter-kotlin bug — assignment through a call-then-navigation chain.** Isolated precisely: `obj.method(args).property = value` fails to parse; `obj.property = value` (no call) parses fine; `val x = obj.method(args).property` (reading the same chain, not assigning) also parses fine. This is not either of the two officially-tracked issues (`lambda_nesting`, `enum_entry_constructor`) — a real, new finding. In practice it's one specific real line — `OSKBluetoothUtility.getBluetoothManager(context).adapter.name = OSKBluetoothUtility.bluetoothDeviceName` — copy-pasted across `OSKMainActivityViewModel.kt` (twice), `OSKSettingsScreen.kt`, `OSKBaseBenchmarkViewModel.kt`, and `OSKBleAdvertiseHelper.kt`. One real bug, one repeated line, not four independent problems. The remaining 2 files (`OSKGetAccessesUseCase.kt`, `UsbIntercomDevice.kt`) have a different, not-yet-isolated cause — checked the most likely suspect (`suspend operator fun invoke` with a default parameter) and it parsed fine in isolation, so it's something else; not pursued further given diminishing returns relative to the decision already made. **Checked the blast radius directly, and it's real good news**: in the worst-affected file (`OSKMainActivityViewModel.kt`, 10 error nodes, 771 lines), all 19 real function declarations and 99 real property declarations across the whole file — including an enum well before the error region and a function declared well after it — still parsed correctly. The errors are localized to specific problematic statements, not cascading corruption of the whole file. **Net read: 4.4% of files have a handful of unparseable statements, not 4.4% of files being unusable.**

### B. Cross-module call-resolution feasibility — how bad is "heuristic-only," really?

The TS pipeline's real "Rule A" (compiler-exact) isn't available to a syntax-only tool; only "Rule B" (heuristic, normalized-name matching) would be. Test how well that actually holds up here, not in the abstract:

- [x] Picked a real cross-module case: `OSKMainActivityViewModel.kt` (`app`) calling `OSKAnalyticsService.shared.identifyAcd(...)`, where `OSKAnalyticsService` is declared in `kotlin-ble-kit-oskey-io`.
- [x] Ran a repo-wide duplicate-name check across all 5 modules' top-level `class`/`object`/`interface` declarations (136 files). **Real result: only 4 duplicated names in the entire repo** — `ExampleUnitTest`/`ExampleInstrumentedTest` (Android Gradle test scaffolding, auto-generated per module, never called cross-module, irrelevant) and two real, substantive ones: **`OSKAnalyticsService` (3 declarations: `kotlin-ble-kit-oskey-io`, and two different packages inside `app` itself) and `OSKConfigurationData` (2 declarations: `app` and `kotlin-webrtc-domain-oskey-io`)**. Bare-name-only matching would be genuinely ambiguous for these two.
- [x] **The real fix is cheap and still syntax-only**: checked the actual call site's imports — `OSKMainActivityViewModel.kt` line 49 has an explicit, unambiguous `import io.oskey.intercom.utils.OSKAnalyticsService`. Kotlin requires an explicit import for any cross-package reference (no barrel/re-export indirection the way TypeScript has) — so a heuristic resolver that reads each file's own `import` statements (still pure syntax, no type-checker) and only falls back to same-package/bare-name matching when nothing was imported would resolve this correctly, cleanly, deterministically. **This is a real, meaningful upgrade over blindly porting the TS pipeline's own "Rule B" (bare normalized-name matching only, no import awareness)** — and it suggests Kotlin's own resolution model is mechanically simpler to replicate via pure syntax than TypeScript's ever was (real collisions are rare — 2 substantive cases in the whole repo — and resolvable via each file's own explicit, unambiguous import).

### C. Decide, based on A and B's real results

Three real options, from `07-...md` — pick one, don't default to the easiest without checking A/B first:

- [ ] Option 1 — Accept heuristic-only confidence, no import awareness. Dominated by Option 2 below — rejected, since import-parsing is nearly free and closes almost all the residual risk Option 1 would otherwise carry.
- [x] **Option 2 — DECIDED, 2026-09-08.** Build a lightweight, import-aware project-wide symbol table ourselves on top of tree-sitter-kotlin's per-file parses: walk every file's package/import/declaration names, build a lookup, resolve each call site using that file's own real imports first, same-package fallback second. A/B's real results directly support this: 95.6% clean parse rate, real name collisions rare (2 substantive cases in the whole repo) and cleanly resolvable via each file's own explicit imports (Kotlin has no barrel/re-export indirection the way TypeScript does, so this is more tractable here than the TS pipeline's own equivalent problem ever was).
- [ ] Option 3 — Hybrid with `kotlin-compiler-embeddable`. Rejected for now — its marginal accuracy benefit over a well-built Option 2 looks small given how rare and resolvable real collisions turned out to be. Revisit only if Option 2's real build surfaces collision/ambiguity rates much higher than this bounded test found.
