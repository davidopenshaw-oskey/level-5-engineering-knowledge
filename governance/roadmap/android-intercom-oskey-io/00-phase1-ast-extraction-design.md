## Real review of the existing TypeScript P1 pipeline (2026-09-07), per user instruction

All 3 existing repos' `pipeline/<repo>/phase-01-ast-extraction/` share the identical 8-script shape (`00-scan-repo.ts` → `01-extract-ast-evidence.ts` → `02-build-module-evidence.ts` → `03-build-benchmark.ts` → `04-build-resolved-graph.ts` → `05-partition-capability-packs.ts` → `06-build-cross-module-dependency-graph.ts` → `07-build-intra-module-coupling-graph.ts`), each with its own `_shared/` (deliberately duplicated per repo — see the POC-duplication note above). Real roles, read directly from the scripts' own header comments and, for `00`, the full body:

- **`00-scan-repo.ts`** does the *real* clone (deletes any existing `output/clones/<repo>` and re-clones fresh every run — I cloned by hand for this investigation, but the actual pipeline run would blow that away and reclone itself), enforces exactly one of `branch`/`commit` in `config/repos.json`, then assigns every file a `module`/`submodule`. For node-iot specifically (the closest analog to this repo's own open question): submodule assignment is a real BFS over the TS import graph, seeded from files matching `routes/access_control_device_(.+)\.route\.ts` as "roots" — a file reachable from exactly one root gets that root's submodule name; reachable from 0 gets `_unreferenced`; reachable from ≥2 gets `null` (shared/core).
- **`01`** extracts raw AST facts (23 normalized categories) via `ts-morph`. **`02`** aggregates into per-module evidence graphs. **`04`** is "the graph" in the sense the user meant — real call-graph edges, compiler-exact declaration matching, API-to-service linking, RBAC matrix. **`06`/`07`** build cross-module and intra-module (submodule-to-submodule) coupling graphs from each module's own resolved `imports_dependency` facts, specifically because Phase 2 runs one module at a time and otherwise can't see who depends on it from outside.

**Real, positive finding this surfaces for Kotlin — module boundaries are free here, unlike any of the 3 existing repos.** Firebase needed a folder convention, Angular a route-tree convention, node-iot a hardcoded name plus real BFS (because no folder was actually named after its one real domain). This repo's 5 Gradle modules (`app` + 4 libraries) are a real, already-authoritative module boundary straight from `settings.gradle.kts` — no reachability heuristic needed at that level, unlike all 3 precedents.

**Real candidate for the submodule question, inside `app` specifically** (item 3, `ui/screens/*` → submodule): `app/src/main/java/io/oskey/intercom/navigation/OSKIntercomNavigation.kt`'s single `NavHost { composable(Screen.X.route) { XScreen(...) } }` block is a direct, real structural analog to node-iot's `routes/*.route.ts` file-per-root convention — except here every route root is enumerated in one file, not one file per root. A same-shape BFS (walk the real Kotlin import graph outward from each `composable(...)` call's screen-composable argument) is a real, concrete candidate technique for the future `00-scan-repo.ts` Kotlin port — not yet built, this is a design candidate surfaced by real inspection, same discipline as everything else in this doc, not a decision to build from yet. **Standing constraint (2026-09-07, principle 2 in `01-...md`): the real screen/route list must be extracted from `OSKIntercomNavigation.kt`'s AST dynamically at scan time, never hardcoded as a fixed array of screen names** — explicitly the same anti-pattern node-iot's own `00-scan-repo.ts` used (a hardcoded module name, a hardcoded route-prefix regex) that this repo's onboarding is deliberately not copying.

**Config-schema shape — resolved, 2026-09-07, per standing principle:** `config/repos.json`'s `modulesRoot` field is a single string because all 3 existing repos have one shared root directory containing every module; this repo's 5 modules are 5 physically separate top-level directories. Per the user's direct guidance (`01-standing-principles-and-lessons-from-ts-facts-pipeline-2026-09-07.md`, principle 1), this is not a gap to force-fit into the shared schema — this repo's config block is free to look structurally different. Real candidate mechanism, consistent with principle 2 (dynamic, not hardcoded): read `settings.gradle.kts`'s own `include(...)` list directly at scan time as the authoritative, always-current module list, rather than hardcoding an array of module names in `config/repos.json` either.

**Real, verified dead-weight finding:** the root `build.gradle.kts` declares the `com.google.devtools.ksp` plugin, and `app/build.gradle.kts` actually applies it — but zero `ksp(...)` dependency declarations exist anywhere in the repo (confirmed via grep), and the real `:app:compileDevelopmentDebugKotlin` run I did earlier shows no `kspDevelopmentDebugKotlin` task executing. Hilt runs entirely through `kapt` (`kapt("com.google.dagger:hilt-android-compiler:2.45")` etc. across `app` and 2 of the 4 library modules). KSP is applied but does nothing — a real, verified fact about this codebase, not a guess, and not something P1 extraction needs to account for as a real annotation-processing pathway.
