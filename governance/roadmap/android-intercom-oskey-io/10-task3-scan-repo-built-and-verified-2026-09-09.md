## What it does

Real clone + checkout (same fail-closed branch/commit validation as the TS repos' own scripts) + dynamic module discovery from `settings.gradle.kts`'s real `include(...)` calls (5 modules, confirmed exact match to the real file) + a full `.kt` file inventory + real submodule detection inside `app` via BFS over a plain Kotlin import graph, seeded from the real screen roots found by walking `NavHost`'s actual `composable(...)` calls (found structurally, never a hardcoded filename or screen list).

**Final, verified result**: all 11 real screens discovered (`Splash, Home, Users, Digicode, TestBenchFactory, TestBenchInstaller, ResetFactory, OpenDoor, CallRTC, FaceRecognition, Settings`) — matching exactly the 11 real `object` subclasses of `Screen` found during Task 1's bounded parse test. 91 real `app` files split across 11 named submodules + `null` (shared/core) + `_unreferenced`, with each category's membership spot-checked against real code, not just counted.

## Real bugs found and fixed, in the order they were found

**1. `CallRTC` missing from the screen roots entirely.** Root cause: its screen render is guarded behind a null-safety `if` block (`if (residentName != null && ...) { OSKCallRTCScreen(...) }`), not a direct top-level statement in the `composable(...)` lambda the way the other 10 screens are written. Fixed by matching any call whose immediate parent is a `statements` node (covers a nested block's own statements, not just the lambda's outer ones), taking the last such match.

**2. Real, load-bearing files (Hilt `@Module`s, the `Application` subclass) misclassified `_unreferenced`.** These are activated by annotation processing / the Android manifest, never by an explicit code reference from any screen — structurally identical in role to `NavHost`/`Screen` (real shared infrastructure) but invisible to a pure reachability BFS. Fixed by structurally detecting an `@Module` annotation or an `Application` superclass and pinning those files to shared (`null`) directly, the same treatment already given to `NavHost`'s and `Screen`'s own files.

**3. Real ViewModel files misclassified `_unreferenced` — the most instructive bug.** Kotlin doesn't require an import for a same-package reference (confirmed directly: `OSKTestBenchFactoryScreen.kt` and `OSKTestBenchFactoryViewModel.kt` share a package with zero explicit import of the ViewModel anywhere in the repo) — unlike TypeScript, where node-iot's own equivalent BFS could rely on imports alone. **Two fix attempts were tried and reverted after re-running and checking real output, not trusted on theory:**
   - Blanket same-package edges (any two files sharing a package are connected): caused a real regression — broad, non-screen-specific packages (`model`: 12 files, `utils`: 8) bridged *unrelated* screens transitively, collapsing 89 of 91 files into a single shared bucket with zero screen-specific submodules surviving.
   - Whole-word textual-reference same-package edges, restricted to small packages (≤4 files): still cascaded through longer chains of small packages, collapsing 75-80 of 91 files the same way.

   **Real, working fix**: treat this as a narrow, scoped graph edge — only from a screen root's own file to its own same-package `*ViewModel` sibling, added as a real edge only at the 11 known root files (never a general rule the BFS could exploit anywhere else). A first version of even this narrow fix pinned the ViewModel as a post-hoc leaf *after* the BFS had already run, which correctly attributed the ViewModel itself but left *its own* real dependencies (a `UseCase`, a `Repository`, reached via the ViewModel's own imports) still `_unreferenced`, since nothing continued the walk from a leaf added after traversal finished. Fixed by adding the edge *before* the BFS runs, so it's a real graph node the traversal continues from.

## The general, portable lesson

**Any transitive graph edge a broadly-shared file can carry will eventually bridge unrelated parts of the reachability graph, no matter how the edge is locally qualified (whole-word match, small-package threshold).** The only safe way to add a same-package/no-explicit-import edge is to scope it to a *specific, small set of known anchor points* (here: the 11 real screen roots' own files, and only for their own `*ViewModel` sibling specifically) — never as a rule the BFS applies uniformly at every node it visits. Worth carrying into any future language's own import-graph BFS (Swift/iOS's own `00-scan-repo.ts` port will likely hit the same class of problem, since Swift also has same-module implicit visibility rules that don't require an explicit import).

## Real, remaining, honestly-acknowledged imperfection

24 of 91 `app` files remain `_unreferenced` after all three fixes. Spot-checked: this is a real mix of genuine dead-or-boilerplate code (Android's own `ExampleUnitTest.kt`/`ExampleInstrumentedTest.kt` test scaffolding) and real files this syntax-only, narrow-edge-scope BFS still can't reach (Compose theme files likely referenced via `MaterialTheme.*` rather than direct import, and at least one further same-package chain not covered by the narrow `*ViewModel`-only edge rule). Not chased further — same discipline as `astErrorTolerancePercent`'s real, measured, accepted-imperfection posture already set in Task 2's config, rather than an open-ended precision hunt. Revisit if Task 4's actual fact extraction finds this materially affects real retrieval quality, the same trigger condition already used elsewhere in this repo's onboarding.

## Update 2026-09-09 (later) — the trigger condition fired, via a live agent query rather than Task 4

Both fixed, re-verified end-to-end (fresh `00`-`07` run, re-synced/re-embedded). `OSKGetCurrentLocation.kt` remains `_unreferenced`, deliberately — it's a real instance of the same-package-without-import limitation this section already documents, not a new gap.
