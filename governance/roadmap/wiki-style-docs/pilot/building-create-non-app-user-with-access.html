Create a non-app user with access

A callable operation that creates a unit-scoped record, provisions access, and returns identifiers including a pincode. Non-app access is an onboarding/access mechanism, not a business persona. [1] [2]

Contract: inputs and outputs

The named request is OSKCreateNonAppUserWithAccessRequest. A parameter check names context, building ID, unit ID, full name, inviter ID, and optional door IDs. [4] The service also calls OSKUserSecurityChecks, but the retrieved fact does not state its enforced rule. [5]

Evidenced operation sequence

  1. Validate named parameters and make a security-check call. [5] [4]
  2. Resolve the unit, generate an ID, create the record, and call _createNonAppUserAccess. [10]
  3. Retrieve a pincode record using building, unit, user, and pincode identifiers. [11]

The architecture document says this operation reads the PIN record after creation to return its value. That is documented architecture context, distinct from retrieved call facts. [12]

Documented business context

The architecture document describes non-app users as unit-scoped people without the mobile app who receive a pincode, and calls this a one-shot workflow. [13] The persona document says access mechanisms are technical onboarding states rather than personas; non-app access may use a time-bound or permanent PIN. [2]

The authority document states the documented delegated-authority principle that a lower-level inhabitant should not receive more access than the ResidentAdmin who created or invited them. This is policy context, not verification of enforcement by this call. [14]

Evidence and limitations

The implementation passes { validity: 'permanent', isValidOnce: false } to its access helper. [10] The persona document separately describes permanent guests as app users with a one-year maximum validity. [15] No retrieved evidence maps this operation to that persona; this is not an established contradiction.

This page does not establish authorization rules, transaction behavior, pincode-generation implementation, or business trigger. It uses a historical database snapshot. Under the full-sync working assumption, unobserved relationships are not established in this database snapshot; they are not evidence against the wiki architecture.
