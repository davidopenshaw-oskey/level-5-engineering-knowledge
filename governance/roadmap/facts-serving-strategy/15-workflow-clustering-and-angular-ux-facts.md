## Task 1: Semi-automated workflow clustering — BENCHED 2026-09-05

**Explicitly deprioritized, not cancelled.** Task 2 judged more urgent; this stays fully documented below so it can be picked up later without re-deriving the reasoning, but no work should start on it until re-prioritized.

**The chicken-and-egg, stated precisely:** clustering is technically possible today — Task 5's `findGraphNeighbors`/`expandWithGraphNeighbors` already walk real edges from an anchor. But a cluster's *auto-generated* portion of its description would inherit the exact semantic poverty Task 2 (below) exists to fix: a cluster built from "uses `mat-radio-button`"-shaped facts describes itself no better than the facts it's made of. Building the full clustering pipeline before Task 2 would produce clusters that still can't be found by the query that should find them — the same failure mode this whole investigation started from, one level up.

**Recommended sequencing:** prototype the clustering *mechanism* now against Firebase-only examples (already fact-rich, per this session's own repeated description-enrichment work) to validate the approach without waiting — but don't invest in the full Angular-inclusive pipeline until Task 2's first pass lands.

1. **Define what a cluster actually is.** Two candidate shapes, not yet decided: (a) an anchor fact + everything `findGraphNeighbors` reaches within N hops (mechanical, cheap, but N needs a real bound — task 5b already found depth 1 alone yields 9 edges from one anchor); (b) a human points at a real starting fact (e.g. a specific component or `api_contract`) and the tool walks outward automatically to assemble the chain, stopping at natural boundaries (a new module, a new repo) rather than a fixed hop count. Prototype (b) first — it matches how the real chain actually reads in this session's own worked examples (UI component → `firebase_callable_call` → Firebase `api_contract` → downstream `INTRA_REPO_CALL` edges).

2. **Build the clustering walk**, reusing `_shared/graph-traversal.ts` directly rather than a parallel traversal implementation — extend depth beyond 1 hop specifically for this use (bounded, with a real stopping rule from step 1, not unbounded).

3. **The one human-authored part, kept deliberately minimal** to avoid recreating the WG-docs staleness risk (`05-tasklist.md` item 4): for each real cluster the walk produces, a person supplies only a short name and one-line purpose (e.g. "Add Inhabitant to Unit — lets a PM assign an owner, tenant, or resident to a building unit"). Everything else in the cluster's description stays auto-generated from the real facts it contains, so it can be regenerated for free as the underlying code changes — only the name/purpose needs occasional human review, not the whole cluster.

4. **Store clusters as their own real, embedded, searchable unit** — a new fact kind (e.g. `workflow_cluster`) or a small new table, TBD at build time — so a future query can anchor directly on the workflow itself, not just on one of its constituent facts.

5. **Re-verify against this session's own known-weak case**: does a query like "how do I assign a resident to a unit" now anchor on the new `Add Inhabitant to Unit` cluster directly? This is the concrete test of whether clustering closes the exact gap that motivated it.

**Added strength for this approach, found after Task 2/Part D landed, 2026-09-05 — reconsidered directly rather than left as an open worry.** Part D's Q1a/Q1b re-verification found vector search doesn't reliably anchor on the exact `model_property`/`angular_template_attribute` fact_id its new `FIELD_BINDING` edge touches — a *graph-neighbor-expansion-time* failure, since that path only reaches the Angular component by expanding outward from whatever facts vector search ranks in the top 10 first. A workflow cluster is a structurally different mechanism, not a repeat of that same failure: built once, offline, by walking the graph server-side (using Task 2's real edges, `FIELD_BINDING` included), then stored and embedded as a single business-language unit. A query would only need to rank *that one bundle* in the top 10, never needing to first land on one specific low-level fact_id among many near-duplicates. Plausibly a real fix for the exact gap step 5 above is designed to test — but a hypothesis to verify once built, not a certainty, since it still depends on the cluster's own description quality (the human-authored name/purpose especially).

### Part A — new fact kind `angular_template_option` (Phase 1 extraction)

Real, exact location: `01-extract-ast-evidence.ts`'s `visitNode` function (~lines 815-870), which already walks every component's real template via `@angular/compiler`'s own `parseTemplate` — no new parsing infrastructure needed, just a fuller walk of the AST already being traversed.

**Two distinct, real gaps in the current walk, confirmed by reading the code, not assumed:**
1. **Literal (non-bound) attributes are never visited.** The walk only checks `node.inputs` (Angular property bindings, `[x]="expr"`) and `node.outputs`. A plain attribute like `<mat-option value="tenant">` isn't a "bound input" in Angular's own template model at all — it lives on `node.attributes`, currently never read. Fix: add a loop over `node.attributes`, scoped to an allowlist (below).
2. **Text/interpolated content inside an element is never captured.** The recursion (`node.children.forEach(visitNode)`) only acts on children that have `.name` (further elements) — a Text node or a BoundText/interpolation node (e.g. `{{ 'INHABITANT_TYPE.TENANT' | translate }}`) has no `.name` and is silently skipped today. Fix: add a branch capturing a direct text/BoundText child, but only for an element that Gap 1 already flagged as carrying a literal `value`/`ngValue` — the same tag-agnostic condition, not a separate tag list. Literal text for a Text node, the raw interpolation expression source for a BoundText node (same "keep the raw expression when it's not a plain literal" convention `bindingValueRaw` already uses).

**Revised 2026-09-05 — a tag allowlist was the wrong scoping mechanism, caught before building, not after.** The first draft above scoped by element *tag name* (`mat-option`, `mat-select`, ...). Real, direct objection: that list is a snapshot of what happens to exist in the codebase today — a future `mat-button-toggle`, a new Material version's component, or a custom company component would be silently invisible, and the list would need manual upkeep forever. Checked whether a tag-agnostic alternative is real and low-noise rather than assumed: pulled the real binding-name distribution across all 730 `angular_template_binding` records. `('input', 'value')` already appears 46 times as a *bound* property (`[value]="expr"`) — confirming `value` is an established, cross-component convention in this codebase already, not tied to any particular tag.

**Revised scope: by attribute name, not element tag.** Capture a literal (non-bound) `value` or `ngValue` attribute on *any* element, regardless of tag — `ngValue` is Angular's own convention specifically for non-string option values (`<option [ngValue]="obj">`), so both need covering. This is tag-agnostic by construction: it doesn't care whether the element is `mat-option`, `mat-radio-button`, a future `mat-button-toggle`, or a custom company component — only that it follows the standard value-attribute convention nearly every Angular form control already uses, current or future. Honest residual limit, not papered over: a hypothetical future component using a completely bespoke API (e.g. `[choiceData]="x"` instead of `value`/`ngValue`) would still be missed — no static heuristic covers every possible novel convention a developer could invent. This covers the realistic range (native HTML, Material, third-party libraries, custom components following the standard convention), which is a reasonable, industry-normal scope boundary, not a gap to apologize for.

**Output:** new raw array `rawAngularTemplateOptions` → `ast-angular-template-options.json`, registered in `ast-evidence-manifest.json` — same `writeJsonAtomically`/manifest convention every other category in this file already uses.

**Built and verified 2026-09-05, Gap 1 only — Gap 2 (label text) deferred, not needed to unblock Part D.** New fact kind renamed to `angular_template_attribute` (more accurate once scope grew beyond "options" — see below) in `01-extract-ast-evidence.ts`, folded into capability packs in `02-build-module-evidence.ts` (block 23, same pattern as every prior fact kind), enriched in `sync-facts.ts`.
