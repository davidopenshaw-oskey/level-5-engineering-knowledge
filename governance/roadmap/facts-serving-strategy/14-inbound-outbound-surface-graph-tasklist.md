`sync-facts.ts` already ingests **every** fact type present in a module's capability-packs — it never filtered by kind. The original draft's claim that these needed *loading* was wrong; checked and corrected in place rather than left standing.

**The real cause, confirmed by reading actual descriptions:** these kinds never got any of the enrichment already applied to `api_contract`/`call_expression`. A real `firebase_callable_call` fact's description is literally `"firebase_callable_call in features/authentication: core-getMfaPhoneNumber (file:line)"` — its own name restated, nothing else — despite the raw payload already containing real, rich, unused content: `requestTypeText: "{ userId: string }"`, `responseTypeText: "{ phoneNumber: string }"`. Same story for `route_definition` (payload has real `httpPath`, `method`, `handlerMethod`, all unsurfaced) and `pubsub_operation_route` (payload has real `operationValue`, `targetCalls`, unsurfaced). This is why vector search never found them: not absence, invisibility.

**The Angular→Firebase join is real and automatable, but not a plain string match — and a real collision risk was caught before being built, not after.** Checked real samples on both sides:
- Angular `firebase_callable_call`'s functionName lives at `payload.evidence.functionName` (not top-level `payload.functionName` — first check of this looked broken because it queried the wrong path; corrected before drawing any conclusion from it): `"core-getMfaPhoneNumber"`, `"user-updateUserProfileAndPhoneNumber"` — module-prefixed.
- Firebase `api_contract.handlerName`/`.value`: `"getMfaPhoneNumber"`, `"updateUserProfileAndPhoneNumber"` — bare, no prefix.

Asked directly: what if two different Firebase modules each define a handler with the same bare name (e.g. `user-getUser` vs `organization-getUser`)? Checked for real, not hypothetically: **confirmed, twice, in real Firebase data** — `removeInhabitantFromUnit` exists in both `admin` and `unit_management`; `getAllOrganizations` exists in both `admin` and `organization`. A join that strips the prefix and matches on bare handler name alone would be ambiguous for these — and worse, would *appear* to work correctly on every other case, making the bug invisible until the wrong pair collided in a real query.

The fix: the prefix is not noise to discard, it's the disambiguating module qualifier. Verified across all 102 real Angular facts: **every single prefix matches a real Firebase module name, 100%, no exceptions** (`core`, `organization`, `user`, `building`, `settings`, `supplier` — real counts checked). Neither of the two confirmed colliding handler names is actually called by Angular today (checked — zero matches), so the collision hasn't yet bitten in practice, but that's the current call pattern, not a property of the system — the join must be built as a **compound key** (`firebase.module == angular.prefix` AND `firebase.handlerName == angular.suffix`), never bare-name matching, and should fail loud (not silently pick one) if a future compound lookup ever returns zero or more than one match.

**Pub/sub is genuinely unresolved, and node-iot's own pipeline output already says why.** Firebase's `pubsub_event_route.dataType` (e.g. `"nonAppUser"`, `"state"`, `"activities"`) and node-iot's `pubsub_operation_route.operationValue` (e.g. `"insert"`, `"delete"`) are different axes — a payload-type discriminator vs. a CRUD-style operation kind. Neither payload contains the actual pub/sub topic name. Node-iot's own `resolved-graph-matrix.md` already attempted this exact join and recorded the same conclusion independently: *"Not joined... there is no evidenced link in source between a publish call's topic name and a push route's URL path."*

Reading further into *why* changes the shape of the fix: node-iot's real `Receivers` are **HTTP push endpoints** (`/access-control-devices/pubsub/accesses`, `/access-control-devices/pubsub/configs`, `/access-control-devices/pubsub/intercom-entries`), not topic subscriptions in code. The actual topic→endpoint wiring is GCP Pub/Sub push-subscription infrastructure configuration — outside both repos' application source entirely. No amount of AST analysis on `firebase-oskey-dev` or `node-iot-api-oskey-io` can resolve this link; it would need a third source of truth (infrastructure-as-code, currently out of scope). This makes the manually-curated mapping the practical answer, not just the cheaper one:
- **(a) New extraction from infrastructure config** — out of scope for this task list; would need its own investigation into where/how that config is stored before it's even a real option.
- **(b) A small, manually-curated mapping**, built once by directly reading the handful of real integration points. Bounded: node-iot's own report already lists the real candidates — one topic name at `pubsub.service.ts:19` (`confidence: candidate`) plus one confirmed topic name `accessControlDevice_activities`, against 3 real push-route receivers and Firebase's 7 `pubsub_event_route` facts. This is genuinely small, hand-traceable work, consistent with "even if pub/sub stays a simple mapping, automating everything else is still a big win."

**The aggregated intra-repo graph (`resolved-engineering-graph.json`) is not uniformly trustworthy, and treating it as one blanket "load it" step was wrong — caught before writing that code, per explicit warning that this kind of reporting/extraction tends to lag and get left to last.** Checked directly, not assumed:

- **Real evidence the step lags behind the rest of the pipeline**: node-iot's graph `generatedAt` is `2026-08-30T18:45:58Z`, but that same run's extraction started `2026-08-29T13:57`Z — over a day later. Confirms the concern directly rather than leaving it as an untested worry.
- **Usefulness varies enormously by repo, not just by confidence label**: Firebase resolves 57% of its call expressions into the graph (3,793/6,655 `graphEligibleCallExpressions`) with 2,222 confirmed cross-module edges — genuinely load-bearing. node-iot resolves only 8% (62/761) with **zero confirmed cross-module and zero confirmed intra-module call edges** — for node-iot, the call-graph portion is close to useless; what *is* valuable there is the separate pub/sub publisher list (see above), not the call graph. Angular sits in between (13% graph-eligible).

   - **Supplier Recurring Pincode** (confident): 2 real graph neighbors, both genuinely useful — the actual downstream document-creation implementations (`OSKBuildingPincodeService.createPincodeSupplierDocument`, `OSKSupplierStaffPincodeService.createPincodeDocument`) that persist the pincode, directly relevant to a developer needing to add recurrence to this flow.

   **Dedicated test of the actual motivating claim — a real, honest limitation found, not glossed over.** Re-ran the PGO-flavored query from task 1 (which surfaces Angular facts directly in its top 10: `deleteResident`, `updateResidentDialog`, etc.) and got **zero graph neighbors**, despite Firebase and Angular facts both being present as anchors. Root-caused rather than assumed broken: Angular's real `firebase_callable_call` fact for this exact action (`organization-deleteResident`) exists as a *separate* fact_id from the `service_method`/`class_method` "deleteResident" facts vector search actually ranked as anchors — the edge lives on the nested call-site fact, not the container method fact. Verified the edge itself is real and correctly resolves when queried directly against the right fact_id (`findGraphNeighbors` on the actual `firebase_callable_call` fact_id returns the correct Firebase target). So the edges and traversal (5a/5b) are both working exactly as designed — the real, remaining gap is that vector search's anchor selection doesn't always land on the exact fact_id that carries an edge, when a codebase has both a coarser "container" fact and a finer "call site" fact for what a human would call the same real action. **Documented as a known, real limitation of this round of work, not fixed here** — a future enhancement (e.g. also checking sibling facts in the same file/symbol family, or enriching container-fact descriptions to mention nested callable calls) is a real, separate task, out of scope for 5a-5d.
