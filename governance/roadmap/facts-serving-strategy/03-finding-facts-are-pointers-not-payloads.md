# Finding — Phase 1 Facts Are Pointers, Not Payloads

**Surfaced:** mid-way through the Example A1.1 (Owner Non Resident) hand-trace, when directly asked whether reading the real repo source (not just facts) counted as "cheating" the test. Confirmed, then corrected further (2026-09-01) after direct pushback that labeling a source-read finding as a "pointer" does not make it a valid demonstration of what a facts-only system can do — it demonstrates a different, out-of-scope capability (an agent with full repo access), which was never what this exercise was meant to test. Both hand-trace documents (`02-...md`, `04-...md`) have been rewritten to reflect this. This document records the general lesson, verified concretely, not assumed.

**The finding:** a Phase 1 fact for something like a type alias records its **name, file, and line** — enough to tell you *where* something interesting is. It does not record the **content** — confirmed by direct, precise comparison: a real enum fact (`ActivityUserType`) carries its full `members` array; a real type-alias fact (`OSKAccessValidity`) carries only `{repo, module, submodule, path, line, name, isExported}` — no members field at all, even though it's a plain three-value string-literal union. Nothing in the fact schema records what's inside a function body either: no fact type captures that a `switch` case is an empty stub, that a block of logic is commented out, or that one code path silently ignores a field another path reads. This is a specific, verified schema gap (enum members are extracted, type-alias union members are not), not a vague generalization.

**Why this matters for the P3a investigation, stated as strongly as the evidence supports:** re-running both hand-traces with a hard "facts only, no source reads" constraint showed the two real examples land very differently. Example 1 (Owner Non Resident) mostly survives — the useful content happened to already be visible in fact fields (a call expression's own `expression` field stores the literal array text; an import fact's `namedImports` array made a real cross-repo match possible without reading anything). Example 4 (Supplier recurring pincode) almost entirely collapses — every decision-relevant finding (the type already has a `'recurrent'` option, the shape already matches the ask, the supplier module never uses it, the validation is a no-op stub, the device handler silently drops the schedule) required reading source, and none of it is recoverable from today's facts. **The corrected conclusion is not "this is a nuance to label" — it's that Phase 1's current fact schema cannot serve a meaningful fraction of real questions like Example 4 on its own, for a consumer with no source-reading ability of their own.**

**The labeling discipline this leads to, going forward:** every claim in a hand-trace should be marked as one of two kinds, never blended silently:
- **Fact-backed (🟢)** — traceable directly to a real Phase 1 fact (a name, file, line, or a deterministic graph edge, including literal text already stored inside a fact field like a call expression's `expression`). This is the only category that represents what a facts-only P2 could actually produce.
- **Source-only (🔵)** — found by reading the actual file. Real, correct as of that reading, and worth recording as part of an honest exercise write-up — but **not evidence of what the target system can do**, and must never be presented as if it were, however clearly labeled. Whether this content ever becomes reachable depends on a real design choice (see Consequences below), not on how carefully it's labeled after the fact.

**Consequence for what P1/P2 might need to become, if questions like Example 4 matter:** either Phase 1's extraction needs to get richer (e.g. capturing a type alias's literal union values the same way it already captures an enum's members — a small, concrete, scoped fix), or the intended consumer needs to be an agent with its own source-reading ability rather than a pure search interface, or both. This is a real open question for `01-qa-vision-and-examples.md`, not resolved here.
