1. **Extend Phase 1's type-alias extraction to capture literal union values, the same way enum extraction already captures `members`.** Found 2026-09-01 (`03-finding-facts-are-pointers-not-payloads.md`): a real enum fact carries its full member list; a real type-alias fact (even a plain `'a' | 'b' | 'c'` string union, e.g. `OSKAccessValidity`) carries only `{name, file, line, isExported}` — no values at all. Confirmed via direct comparison of two real fact records, not assumed. This is a small, specific, scoped extraction fix, not a source-reading workaround — it would make claims like "this type has exactly these three values" fact-backed instead of requiring a source read. Not yet started.

   **Real-world confirmation, 2026-09-02** (`09-p2-build-tasklist.md`, task 7): this stopped being a theoretical gap. A real vector-search retrieval test against `OSKBuildingUnitInhabitantType` failed to surface it for a query directly about its actual meaning (owner/tenant/resident categorization) — even after an unrelated symbol-naming bug was fixed and the fact's identity became correctly findable, its *meaning* still wasn't, for exactly this reason. Raises this item's priority: it's no longer just a schema asymmetry, it's a demonstrated cause of a real retrieval miss.

2. **The connecting thread: which controller manages which document type.** Asked directly ("do we leverage this rich data yet") after confirming `firestore_path_touched` and `OSKDocument` field shapes both already work — checked rather than assumed, and found a third real instance of the exact same bug class: `extendsClass` already named a controller's base class (e.g. `OSKDocumentController`), but the base class's own generic type argument — the actual document type it manages, e.g. `OSKBuildingUnitInhabitantController extends OSKDocumentController<OSKBuildingUnitInhabitant>` — was dropped entirely. Without it, "this controller manages this document type" existed only as a naming-convention guess, never a fact.

   **Fixed and verified across all three repos, 2026-09-02.** `getExtends()` (the real heritage-clause expression) used instead of `getBaseClass()` (which resolves the declaration and loses the specific instantiation). Real, honest results per repo, not assumed to generalize: **91 real controllers** in `firebase-oskey-dev` now have their exact document type(s) captured; **node-iot** has exactly **1** real instance; **Angular has zero** — a real, honest finding, not a gap, since `Controller extends DocumentController<X>` is a backend/Firestore-access pattern Angular's frontend code doesn't have. `sync-facts.ts`'s `descriptionFor()` updated to surface this in the embedded text (`"... extends OSKDocumentController<OSKBuildingUnitInhabitant>, manages document type(s): OSKBuildingUnitInhabitant ..."`), propagated through Firebase's index (55 facts re-embedded); nothing to propagate in Angular (0 affected); node-iot still not in the index (deferred).

   **Real proof this closes the loop, tested honestly both ways:** the original "owner who doesn't live in the unit" query's top 10 was unchanged by this fix — expected, since a controller's document-type relationship answers a different question than that one. Tested against the question this data is actually built for instead: "which controller class manages building unit inhabitant documents in firestore" → `OSKBuildingUnitInhabitantController` ranks **#1**, by a clear margin (0.5591 vs. 0.5815 for second place). Confirms the three-piece chain works end to end: Controller → Document type (this fix) → Document field shape (the `OSKDocument` generic fix) → Firestore path (`firestore_path_touched`, already working before today).
