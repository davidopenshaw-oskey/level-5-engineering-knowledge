## A real, decisive business-domain finding, easy to forget and costly to re-derive

The PGO (Property Manager Portal) manages **only owners and tenants** — never residents directly. A resident is added later, by an owner or tenant acting as `residentAdmin`, via the Oskey Apps, never by a PM. This is already written precisely in `governance/reference-docs/Oskey Personas and Authority models.md` (line ~19), which also already fully specifies "Owner Non Resident" as a real persona — meaning `01-qa-vision-and-examples.md`'s Q1/Q1a/Q1b questions aren't asking about a new concept, they're asking about an already-specified authority model the code hasn't caught up to. Phase 1 has zero awareness of this document today (it only processes source code) — this is exactly the gap Task 3 exists to close.

A concrete instance of this rule mattering, found via Task 2's Part D: the real backend union type for `inhabitantType` (reachable from `OSKCreateOrganizationInhabitantComponent`) includes `resident` as a technically valid value, but per this business rule, `resident` should never be selectable from this specific PGO form. Flagged in `15-...md`, not fixed — a reminder that "the type allows N values" and "this UI should offer N values" are different questions, and a UI offering fewer values than its type permits is often correct, actor-scoped behavior, not a gap.
