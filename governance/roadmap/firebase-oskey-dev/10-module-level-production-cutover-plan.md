Real quality read-through: deterministic sections correct in every case including accurately reporting "no facts evidenced" where genuinely true; LLM sections substantive and specific (real cross-capability architectural observations, real per-capability open questions, nothing generic).

**Two minor rough edges found, not blockers:**
- Section 5 (Internal Structure) is currently a raw JSON dump of the coupling graph rather than the short prose note production's reduce step writes — functional, less polished. Undecided whether to add a light LLM pass for this or leave it as structured data.
- A stray `---` separator artifact appears in a couple of spots in the per-capability assembly (from how capability blocks get split from the raw response) — cosmetic, not a citation/content problem.

**Both rough edges investigated and fixed after a real read-through by the user, not left as accepted debt:**

- **Citation readability regression, root-caused, not just "consolidation makes documents longer."** The real production contract (`00-capability-synthesis.md`) explicitly offers two citation forms: fact-ID (one specific fact) and file+line (for summarizing several related facts, or when one fact's own `id` is long/unwieldy — some `call_expression` IDs embed multi-line call arguments verbatim). The experimental contract only ever taught the model the fact-ID/short-ID mechanism, silently removing the file+line option — confirmed by finding a real case where the *old* architecture's output used a clean file+line citation for exactly this kind of gnarly fact, while the new contract had no way to produce the same choice. Fixed: restored both citation forms in the experimental contract's instructions.
- **A second, separate real bug found in the same investigation**: the model wrote a citation as a range (`` `F201-F203` ``) instead of one reference per citation. `restoreFactIdCitations` didn't match it (silently left untouched) AND `citation-validator.ts` doesn't either (requires a known fact-type prefix) — meaning a malformed short-ID citation disappears from evidence tracking entirely rather than being flagged as fabricated or unverified. Fixed two ways: (1) contract text now explicitly forbids ranges/combined IDs, requiring one citation block per fact; (2) new `findUnrestoredShortIdCitations()` in `run-utils.ts`, a looser safety-net pattern run after restoration specifically to catch what the strict restoration regex won't — verified against three real/synthetic cases (the real malformed range, a clean real citation with no false positive, and a simple unrestored short-ID).
- **Section 5 JSON explosion, confirmed and fixed.** Real check: `organization`'s raw intra-module-coupling JSON is 43,549 chars vs. `apps`'s 3,305 — already 13x bigger, and combinatorial with submodule count. New `formatIntraModuleCoupling()` applies the same group-and-cap treatment `call-edges.ts` already uses for cross-module edges (which had the identical problem, already fixed there). Real measured result: 73% reduction on `organization` (43,549 → 11,761 chars), genuinely readable prose instead of a JSON dump.
- **Stray `---` artifact fixed**: trimmed from captured section bodies in `splitByNamedHeader`.

Re-ran `apps` end-to-end after all four fixes: 71/71 citations verified, all sections/capabilities present, Section 5 now readable. Not yet re-tested against a larger module with the full fix set — worth doing before Steps 2-7 to confirm at scale, especially the citation-form choice and the coupling-graph formatter.

## Footnote-style citations — real, user-driven design change, implemented and verified

Comparing the new architecture's real output against an old (2026-08-01) reference document (`knowledge-corpus/firebase-oskey-dev/20260801_173721-1aa319b1/engineering-profiles/building-engineering-profile.md`) surfaced something bigger than a formatting nit: that old document has **zero inline citations** — every claim is just tagged Confirmed/Inferred, which is why it reads so cleanly, but it predates this pipeline's entire citation-verification discipline (citation-validator.ts, provenance sidecars) and isn't independently checkable. Current real documents (old architecture and new alike) carry dense inline fact-ID citations by design — genuinely checkable, genuinely harder to read, especially for `call_expression` facts whose own `id` embeds multi-line call arguments verbatim.

**Fix, proposed by the user**: keep every citation exactly as real and checkable, move the verbose text out of the prose into a numbered evidence appendix — `(FactId:#001)` inline, the real fact-ID or file:line content listed once in a genuine Section 14, not the promissory "see inline citations above" note every document (old and new) wrote instead of an actual list.

**Implemented in `run-utils.ts`**: `renderCitationsAsFootnotes()` (recognizes both this pipeline's real citation wrappings — the LLM's nested/padded double-backtick form and the deterministic-assembly code's plain form — dedupes by real content so the same fact cited twice shares one marker), `formatEvidenceAppendix()`, and `resolveFootnotesForValidation()` (reconstructs the real-citation-inline form in memory, never persisted, so `citation-validator.ts` validates a footnoted document exactly as it always has, unmodified).

**Real end-to-end verification against `apps`**: 105/105 citations verified (0 fabricated), 91 unique deduplicated entries in the appendix, main body reads as cleanly as the old reference document while every claim stays fully traceable. Written to `apps-FINAL-ASSEMBLED-FOOTNOTED.md` (kept separate from `apps-FINAL-ASSEMBLED.md` for a direct before/after comparison, at the user's request).

This is now the target rendering for the real production cutover — worth locking in before Steps 2-7 rather than treating as optional polish, since it directly addresses a real readability gap between this pipeline's current output and its own historical best example.

## Part A, Step 2 — loud-failure size check, done

Added a real threshold check in `EXPERIMENTAL-module-level-test.ts`, right after prompt construction, before the real API call: estimates tokens from real prompt char length (3.6 chars/token, deliberately a bit stricter than the real measured ratio for `organization`'s largest tested prompt, ~3.77), throws `[MODULE_TOO_LARGE_FOR_SINGLE_CALL]` above 700,000 estimated tokens rather than silently proceeding. No confirmed real context-window ceiling exists for this model as of this writing (checked Google's docs and the Vertex AI `models.get()` API directly — neither exposed a usable number), so 700K is a deliberate, named safety margin above the largest real module actually tested (`organization`, ~383K real tokens), not a guess at the model's true limit. Verified both directions: real `organization` prompt size (1,441,458 chars) estimates to 400,405 tokens, comfortably under the threshold; a synthetic 3M-char case correctly throws.

## Blank lines between top-level bullets — real, cheap readability fix, done

User-requested after reviewing the footnoted `apps` output. Measured before implementing: adding a blank line between every top-level bullet costs ~4.7KB repo-wide (extrapolated from `apps`'s real 145-bullet count against its real 471 facts, scaled to the repo's ~15,244 total facts) — negligible against hundreds of KB of real document content. Implemented as `addBlankLinesBetweenTopLevelBullets()` in `run-utils.ts`, a deterministic post-process (not an LLM instruction, so it's 100% consistent regardless of model output) that only touches non-indented top-level bullets — Section 4's indented per-class method lists are deliberately left untouched, since those are dense reference listings, not narrative prose, and spacing them out would just make scrolling worse for no reading benefit. Verified end-to-end against `apps`: 108/108 citations still verified after the change, spacing confirmed correct in both module-wide and per-capability sections.

**Section 0 exclusion fix**: the blank-line rule was also spacing out Section 0's compact runId/repoName/etc. metadata list, a key-value block, not narrative bullets. Fixed by only applying `addBlankLinesBetweenTopLevelBullets` to the document from Section 1 onward. Verified with a synthetic check (Section 0 stays tight, Section 3's real bullets get spaced).

**Full fix set re-verified against `organization` (largest module, 14 capabilities) after being proven on `apps` (smallest)**: all 14 capabilities present, no missing sections, no collapse (all module-wide sections healthy: Executive Summary 626 chars, Firestore/Ownership 6,223, Permissions 5,686, Risks 3,496), 472/472 citations verified (0 fabricated), 394 unique entries deduplicated, 382,602 real input tokens. Confirms Step 1's readability fixes hold at both size extremes tested, not just the smallest case.

Also measured (and worth recording precisely, since the intuitive answer was wrong): footnoting does NOT reduce total file size — for `apps`, the fully-inline body was 21,194 chars vs. a footnoted body+appendix total of 22,300 chars (~5% *larger*), because most citations (91 of 105 instances) are cited only once, so footnoting adds a marker cost without a matching deduplication saving. The real win is the readable BODY shrinking 60% (21,194 → 8,578 chars) — the appendix isn't something a reader scans start-to-finish the way the narrative is, so the reading experience improves substantially even though disk size does not.

## Part A, Steps 3-5 — real production script, done

New `01e-generate-module-level-profile.ts` (real notification load/persist, real COMPARISON_MODE, real provenance sidecars validated against a resolved-for-citations reconstruction so the footnoted rendering doesn't make provenance look like it has zero citations, real `[Fail-Closed]` checks, API Reference companion doc at 0 LLM calls). Contract promoted to `contracts/03-module-level-synthesis.md`. New `phase2.moduleLevelProfile` config block added to `config/repos.json` for `firebase-oskey-dev`, alongside (not replacing) the existing `capabilityBasedProfile` block, which stays as the deliberate fallback.

**Two more real bugs found and fixed during the first real production-script test run (`tasks`)**, both from stochasticity the smaller `apps`/`organization` test batches happened not to surface:
- **Single-capability naming**: on a module with exactly one capability, the model wrote `## CAPABILITY: tasks` (the module's own name) instead of `## CAPABILITY: _module_root` (the real submodule identifier) -- an understandable mistake when there's only one thing to talk about, but it broke exact-name lookup and would hit every single-capability module in this repo (`tasks`, `call`, `unit_management`, `access_control_device`). Fixed with a deterministic fallback (not a contract-wording fix, since a naming choice like this isn't reliably preventable in text): if there's exactly one real capability and the response has exactly one capability block, remap it to the real name regardless of what the model called it, logging `SINGLE_CAPABILITY_NAME_REMAPPED` when it fires.
- **Dangling backtick artifact in footnoted file-line citations**: the real observed structure is `` `` `file.ts` (line 37) `` `` -- the outer double-backtick closes AFTER the parenthetical, not before it. The prior file-line footnoting regex assumed the close came first, so it only matched part of the citation and left a stray `` `` `` behind in the rendered text. Fixed by making the outer double-backtick wrapper optional on each side independently, with the inner single-backtick-wrapped file path as the only mandatory part (matching citation-validator's own convention). Verified against the real file that had the bug: 0 dangling artifacts after the fix.

Also surfaced (not a new bug, a genuine artifact of how notifications work): `addNotification` upserts by a deterministic ID, so a conditional warning from an earlier failed run can remain in `run-notifications.json` at its old array position even after a later successful run never re-triggers it -- querying "the last N entries" without checking `updatedAt` can pick up a stale entry mixed with fresh ones. Not a bug to fix, just a real gotcha worth remembering when reading this log.

## Part A, Step 6 — all 12 real modules run, done

Full real batch via `01e`, COMPARISON_MODE, `gemini-default`. **Real timing result, not just token savings**: all 12 modules combined took 8m 28s wall-clock total. For comparison, the OLD architecture's real per-module timing for just `organization` (14 sequential capability calls + 1 reduce call, pulled from real notification timestamps) was 19m 23s alone -- the new architecture processed the entire 12-module repo faster than the old one processed a single large module, because eliminating 13 extra sequential round-trips per large module removes far more wall-clock time than any single call's own latency.

**One more real bug found and fixed at this scale, then a false alarm chased and resolved**: the range-citation problem (found on `tasks` at 1-occurrence scale) recurred far more at 12-module scale -- 20 total malformed range citations across `organization` (14) and `user` (6), the two largest modules, confirming it scales with citation volume rather than being rare. Added `expandShortIdRangeCitations()` to `run-utils.ts`: expands a malformed `` `F150-F157` `` -style range into one real, individually-resolvable citation per fact (capped at 100 facts per range as a safety limit against a qualitatively different kind of error), called before `restoreFactIdCitations`. Verified fixed against the real data that had the bug.

**Then a real false alarm, worth recording as a genuine gotcha**: re-running `organization`/`user` afterward still showed `SHORT_ID_RESTORATION_INCOMPLETE` warnings that looked identical to before, appearing to mean the fix hadn't worked. Root cause: `addNotification` upserts by a deterministic ID and only touches an entry when the same code+module combination fires again -- a run that finds zero issues never clears a prior run's stale warning, which stays sitting in the log at its old timestamp. Confirmed by checking real timestamps (the "still failing" notification's `createdAt` didn't match the just-completed run at all) and by directly grepping the real, current final documents for the malformed pattern -- zero matches in both. Added a raw-response-preservation diagnostic (`.raw-before-restore.txt`, written only when a real problem is found) for forensic inspection if a genuine future occurrence needs root-causing, since the true pre-fix text was otherwise overwritten in place and unrecoverable after the fact.

Also fixed at this scale: single-capability naming (`## CAPABILITY: tasks` instead of `_module_root`) -- confirmed recurring on a *different* single-capability module (`call`) in this batch, validating the deterministic remap fallback generalizes rather than being a one-off patch for `tasks` specifically.

**Final real state across all 12 modules**: every module completed, every citation-validation check passed (0 file-not-found anywhere), both real bugs found during this step are fixed and verified against real data, not just believed fixed.
