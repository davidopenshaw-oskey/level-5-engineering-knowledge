**14. (New, resolved 2026-08-11) The 2026-08-01 `gemini-3.6-flash` 404 was a region gap, and there's a second, sharper distinction underneath it: catalog visibility ≠ generation entitlement.** `config/llm-providers.json`'s `gemini-default` had been pinned to `europe-west1`, which on this project only serves the Gemini 2.5 generation. `ai.models.list()`/`.get()` (free metadata calls) showed `gemini-3.5-flash`/`gemini-3.6-flash` as catalog-visible in BOTH `us-central1` and `global` — but a real `generateContent` call against `us-central1` still 404'd with the same "not found or your project does not have access to it" message, while the identical call against `global` succeeded. So `.get()`/`.list()` returning a model is not proof it can actually be generated against in that specific region — always verify with a real (small) `generateContent` call before trusting a region for a new model. `global` is confirmed working end-to-end: ran the full `01a`+`01c` path for real against `gemini-3.5-flash` on module `tasks` (~53.6K+1.5K then ~49.3K+1.3K input/output tokens across the two calls), written to `output/runs/.../llm-comparison/gemini-default/tasks/` so it never touched the canonical Claude output. `gemini-default` is now `gemini-3.5-flash` / `global`. Note: pro-tier hasn't reached 3.5/3.6 on this project at all yet (`gemini-3.1-pro-preview` is the newest pro, still preview) — only flash has 3.5/3.6.

**15. ~~Neither Claude nor Gemini produced machine-checkable citations for the `tasks` module.~~ ROOT CAUSE FOUND AND FIXED 2026-08-11.** The actual cause was sharper than "no format instruction": `contracts/00-capability-synthesis.md`'s old "What NOT to include" line said *"Do not attempt... an evidence-references section with fact IDs"* — ambiguous enough that both models read it as "don't cite evidence inline anywhere," when it was only meant to rule out a separate, standalone Section 14 listing (now built deterministically). The compact fact table already exposes the exact `id`/`file`/`line` columns needed to cite — the contract was actively discouraging their use. Fixed by adding an explicit "Citing evidence inline (required, not optional)" section with the two exact citation forms (fact-ID and file+line) `validateCitations()` checks for, plus rewording "What NOT to include" to distinguish "no standalone list" from "yes to inline citations." Re-ran `tasks` through Gemini with the fixed contract: **19/19 citations, all verified, zero fabricated** — full fix confirmed on the first retry, no format struggle.

**16. Structural compliance was perfect for Gemini across all three modules tested (`tasks`, `building`, `admin`); content depth was consistently shallower than Claude's for the same facts.** Gemini 3.5 Flash matched every contract section number/title exactly (0-14, including the "7-8" combined section) on all three, with no parse failures and no missing sections even on `building` (the repo's largest/most complex module, 11 capability packs). Content-wise it consistently stayed at a higher level of abstraction than Claude's output for the same facts (e.g. `building`: ~9.1K words via Gemini vs ~13.9K via Claude for the same module). Not evidence of a broken pipeline — every citation it made checked out (see item 15) — but a real, repeated quality signal worth tracking as more modules get run, per Plan 04 Stage 6.

## Repo-level design gaps

**8. No repo-level reduce script exists at all.** Only a design sketch exists (architecture brief Section 3.3). This is the single largest concrete gap against the originally-envisioned three-part pipeline. → Plan 04 Stage 4.

**9. The evidence scope for repo-level citation validation is undecided.** `validateCitations()` currently always checks claims against one module's evidence-graph facts. A repo-level report's claims could reference any module's facts — needs an explicit decision (most likely: concatenate every module's evidence-graph facts into one repo-wide array) before the repo-level reduce can validate its own citations. → Plan 04 Stage 4.

**10. No real cost model exists yet for the full-repo run.** The only real, measured numbers are for `building`. `organization` (13 submodules) and `user` (10 submodules) are structurally larger and plausibly comparable-or-more-expensive; nothing has been measured for them yet, so any total-repo figure right now would be an unverified projection. → Plan 04 Stage 2 (and Stage 2 explicitly requires converting the projection into real measured numbers once Stage 3 actually runs, not stopping at the projection).

**11. Whether a repo-wide consolidated API/interface catalog is in scope is undecided.** Right now there are 11 separate per-module API references and nothing tying them together repo-wide. Could be built as part of the repo-level reduce, or explicitly deferred — currently neither has been decided. → Plan 04 Stage 4.

**12. Whether `01c`'s (or any successor's) output should be promoted to the `knowledge-corpus/` "official" location is undecided.** That directory currently holds only two stale, pre-Plan-03 runs, so the corpus's canonical location is itself out of date relative to the actual best available output on disk. → not yet scheduled in Plan 04; worth resolving alongside Stage 5.

(New, 2026-08-11) Tested `thinkingLevel: HIGH` on Gemini's connective-tissue call for `building` — modest improvement, not a fix for the depth gap in item 16.** Added real `thinkingConfig.thinkingLevel` support to `callGemini` (`_shared/llm-adapter.ts`; new `gemini-default-highthinking` config entry, scoped to the connective call only — the 11 cheap capability calls didn't show the depth gap, no reason to pay more for those). Re-ran the connective-tissue step only (reused existing capability outputs, no Stage A re-spend) and diffed Sections 12-13 against the default-thinking version: risk bullets got slightly more enumerated/specific (3 named permission examples grouped under one bullet instead of one generic "coarse permission checks" line), but the two deepest findings Claude caught — the RBAC-inconsistency-across-siblings pattern, and the "5 unattributed `permission-denied` errors" red flag — were still absent. **19. (New, 2026-08-11) Real API responses were never checked against the requested model — fixed.** Prompted by a direct question ("are you sure we're using gemini-3.5-flash?"), verified via a live minimal call that `response.modelVersion` does report back the actually-served model, and confirmed it matched. Then found this was never wired into the pipeline itself: `LlmCallResult` only ever echoed back the *requested* model (`config.model`), never checked what the provider's own response said actually served it. Fixed for all three providers — new `servedModel` field (`response.modelVersion` for Gemini, `data.model` for Anthropic/OpenAI), with `callLlm()` now `console.warn`-ing (not throwing) on any mismatch, and `servedModel` persisted into the `SYNTHESIS_LLM_CALL_COMPLETED` notification for real traceability, not just a console line.

**20. (New, 2026-08-11, found while testing item 18) Second occurrence of the notification-ID collision bug — this time across `LLM_CONFIG_KEY`s, not capabilities.** `buildNotificationId()` was fixed earlier (Plan 03) to distinguish by `file`, but running the *same* module/relPath through two different configs (`gemini-default` then `gemini-default-highthinking` for `building`'s connective call) produced identical IDs anyway, since `file` doesn't vary by config — the second run's usage/servedModel data silently overwrote the first's (confirmed lost: only 1 of 2 real connective-tissue calls for `building` survived in `run-notifications.json`). Fixed by adding `llmConfigKey` as a distinguishing field in `buildNotificationId()`, and threading `LLM_CONFIG_KEY` through as a new optional parameter on `runDocumentCalls()` at all 7 call sites (`00`, `01`, `01a`, `01b`, `01c`, `01d`). Relevant for Plan 04 Stage 6 and any future `COMPARISON_MODE` use — without this fix, comparing more than one non-default provider/config against the same module would keep losing all but the last run's usage data.

**21. ~~Cross-cutting depth gap (items 16, 18).~~ CLOSED 2026-08-11 via a contract fix, not a model/thinking-level change.** `contracts/01-module-synthesis-reduce.md`'s Section 9/13 instructions already told the connective step to do cross-capability judgment, but only gave a concrete worked example for ownership conflicts, not for permissions — so the model had the raw data (Permissions extracts for every capability) but no explicit technique for what to *do* with it. Added two concrete, generalized techniques to the contract: (1) build a mental RBAC-enforcement tally across all capabilities and name the asymmetry if some enforce checks and comparably-sensitive siblings don't; (2) flag unattributed security-relevant signals (permission-denied errors, guard branches) by capability name and exact count, not generic language. Re-ran `building`'s connective call on `gemini-default` (no thinking-level change, to isolate the variable) against the identical facts already tested twice: Section 9 now explicitly states *"Comparing the security implementations across all 11 submodules reveals significant asymmetries"* and names the RBAC-backed vs. no-RBAC group split by capability; Section 13 goes further than the original Claude finding by connecting the RBAC-inconsistency and Firestore-rules-gap observations into one compound privilege-escalation risk. Citations held at 262/262 verified, zero regression. Conclusion: the depth gap was a prompting/contract-instruction issue, not a model capability ceiling — worth remembering before reaching for a more expensive model or more thinking budget as a first response to a quality gap.
