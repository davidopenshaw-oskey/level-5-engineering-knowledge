# Findings — Real, Current Practice on Agentic Tool-Call/Turn Budgets

Answers `13-priming-brief-agentic-turn-budgets-2026-09-06.md`. All claims below are from live web search/fetch run 2026-09-06, cited inline.

## Headline finding

**This project's own two real failures are not edge cases — they are the field's single most commonly named unsolved problem with agentic turn budgets, right down to the exact phrasing.** A real, current, open-source issue (OpenHands `software-agent-sdk` #2406) describes this project's Step 13 failure almost verbatim: *"the conversation abruptly terminates with an error event. Any work the agent has done but not yet synthesized into a final answer is lost."* That issue's own proposed fix is structurally the same idea as this project's already-drafted synthesis-budget reserve — refined with real detail (percentage-based warnings, not a fixed turn count) — but was **closed as not planned**, a real, honest, telling data point that even a well-resourced, actively-maintained agent framework hasn't shipped a clean fix for this yet.

## 1. Real, current, named tool-call/iteration limits in production agentic systems

Real, named example bands found: `maxTurns: 3` for simple tasks (time-display agent), `maxTurns: 5` for data-retrieval/rendering agents, and **"Exploratory or search-heavy agents — 10 to 20 turns"** as a named real category. A separate, independent budget mechanism also exists: `maxBudgetUsd`, capping spend directly rather than turn count. | [Claude Code Docs — the agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop); [Instagit — Understanding Sub-agent maxTurns Limits](https://instagit.com/shanraisshan/claude-code-best-practice/understanding-subagent-maxturns-limits/) |

**Direct read for this project's own number**: 25 is not an outlier or obviously wrong — it matches Cursor's own standard-mode default exactly. But every real system found here that publishes more than one number treats 25-ish as the *small/default* tier, with an explicit, much larger tier for harder work (Cursor's Max mode: 200; OpenHands' default: 500) — not as the single number applied uniformly regardless of task difficulty.

## 2. Is a small, fixed cap the right shape, or does real practice scale it?

**Real practice clearly scales it — this is the most direct, well-supported finding of this round.** Three independent, real, named confirmations:

- Claude Code's own documented guidance explicitly bands turn budgets by task shape — 3 for simple, 5 for data-retrieval, **10-20 for "exploratory or search-heavy agents"** — a real, named category this project's own atomic-PRD agent structurally belongs to (it is, by its own persona's design, a search-heavy agent).
- Cursor ships two real, distinct, user-facing tiers (25 vs. 200) rather than one number — the harder-task case gets a real, order-of-magnitude-larger budget, not a marginal increase.
- OpenHands' default (500) is high enough to function as a true backstop rather than a routine constraint — the real design intent there is "this should almost never be hit in normal operation," a structurally different posture than this project's 25, which today's two real aborts show is being hit in genuine, non-degenerate cases.

**Direct implication for this project's specific failures**: both of today's real aborts are evidence this project's single fixed 25 is being asked to do two different jobs at once — a routine ceiling for typical questions (where it currently works, per the real Q1a/Q1b successes recorded in `06-step6-...md`) and a hard backstop for genuinely hard, multi-repo breadth questions (where today's two real failures show it's too tight). Real practice elsewhere treats these as two different numbers, not one.

## 3. Real, published practice on "knowing when to stop and answer"

**Real, decisive, directly actionable finding — and it identifies a real gap in this project's own diagnosis, not just its fix.** A real, current (2026) research framing, found via multiple independent sources, states the core problem precisely: *"a verifiable stop condition is one the agent can check deterministically, with no judgment required... asking an agent to 'keep trying until the result looks good' hands it a subjective judgment call, and the agent either exits too early, too late, or runs indefinitely."* Real, current academic work (arXiv 2607.14890, "Proof-or-Stop"; arXiv 2604.14170, evidence-driven RAG with iterative reasoning) converges on the same real principle: **"enough information" needs a number, a list of required items, or some other checkable criterion** — not a subjective confidence judgment.

**This directly reframes this project's own Step 13 root cause.** The real failure recorded there wasn't (only) "no reserved synthesis budget" — it was that the model held a `confident: true` result and *judged* it insufficient, then burned turns on variants that couldn't work. Real current practice says the fix for *that specific failure mode* is a **verifiable stopping criterion** (e.g., "if a result carries `confident: true` and the queried field/type appears in it, stop searching that thread now"), not only a budget reserve — the budget reserve (this project's already-drafted fix) is real, valid, and separately confirmed by practice (next paragraph), but it addresses the *symptom* (running out of budget with no answer) more than the *root cause* (not recognizing sufficiency) found in Step 13.

**Real, separate, independent validation of the already-drafted budget-reserve idea, with a concrete refinement — and a fuller, corrected story after reading the real comment thread directly (via GitHub's API, not just the rendered page).** OpenHands issue #2406 (real, current, 2026) proposes — for the *exact* failure this project experienced — injecting budget-awareness directly into the agent: **"You have a budget of {max_iterations} steps for this task. Plan your approach to complete the task within this budget,"** plus **warning injections at 80% and 95% budget usage**, or at minimum a final-step message: **"You are about to reach the maximum number of steps allowed. This is your FINAL step."**

**Correction to this report's own earlier read of this issue**: it was not deliberately rejected. The real comment history shows a maintainer (`enyst`) engaged substantively, an automated agent (`openhands-ai[bot]`) actually built the fix and opened a real PR (**#2739, "fix(sdk): surface iteration budgets gracefully"**, implementing all four proposed pieces — budget visibility, final-step warnings, a distinct iteration-limit status, and tests), and that PR **passed most of its own CI** (96.7% integration-test success rate) — but was ultimately **closed without being merged**, with no human explanation visible in its own comment thread beyond automated CI reports. The parent issue was then auto-closed by a stale-bot after 50 days of inactivity, not by a maintainer decision. **Corrected verdict**: this is not "the community decided this is a bad idea" (the original read) — it's "a real, working version of this exact fix was built and nearly shipped, then went stale for unknown, non-technical reasons." An even more useful and more encouraging data point for this project than the original finding.

**Two further real, directly relevant details surfaced only by reading the full thread:**
- A maintainer noted **OpenAI's `codex-cli` reportedly has no max-iterations cap at all** — "It goes on until it decides to answer the user and beyond" — a real, if single-sourced, data point that at least one other real, current system uses no hard turn cap whatsoever, at the opposite end of the spectrum from this project's 25.
- The same maintainer raised a genuinely important, real distinction this project's context doesn't have: **for OpenHands' primary *interactive* use case, hitting the limit isn't meant to be a hard stop at all** — "the expected behavior is not to have a reminder, and is not to stop completely: instead, a new user message would clear the error and the agent continues for another round." The graceful-termination problem matters specifically for **unattended/eval-style runs with no human turn to rescue them** — which is exactly this project's own situation (`atomic-prd-agent` runs once, to completion, with no human in the loop to send a follow-up message if it stalls). This sharpens rather than weakens the relevance of the fix to this project specifically, even though it explains why a general-purpose interactive tool like OpenHands might deprioritize it for its main audience.
- **Real, quantified, independent confirmation of this project's own Step 13 root cause, at a completely different scale**: a real benchmark run posted to the same thread (Commit0 eval, 16 real instances, `max_iterations=500`) found **6 of 16 instances ended in `status=running`** — exhausted all 500 iterations without ever calling the finish tool — including one (`tinydb`) that had **already reached 100% pass rate** but still didn't recognize completion and stop. This is real, external, quantified evidence that "not recognizing sufficiency and stopping anyway" is a real, recurring failure mode independent of how large the budget is — 500 didn't prevent it any more than this project's 25 did.

## 4. Real, current guidance on recovering from an exhausted budget gracefully

**Real, named, converging practice — validates this project's own aspiration (a partial, caveated answer) as the real industry-standard target, not an ad hoc idea.** A real, current framework (MindStudio's Claude-Code-agent-loop guide) names three explicit stopping-criterion categories used in practice — **"success stopping,"** **"failure stopping,"** and **"budget stopping"** (the last triggered by turn count or cost threshold) — and states the real, recommended practice for the budget-stopping case directly: define **"what the agent should do if it hits a stopping condition before the task is fully complete — whether that's committing partial work, rolling back, or generating a summary of what was done and what's blocked."**

**Real, concrete, named example of graceful degradation already shipped in production**: GitHub Copilot's coding agent's own 59-minute wall-clock limit comes with **proactive warnings as the limit approaches, specifically so the agent can wrap up before being cut off** — i.e., a real production system already does, today, exactly what this project's Step 13 proposes to add (advance warning before a hard cutoff, so the agent chooses to synthesize rather than being forcibly aborted).

**No real example was found of a system that silently fails or retries-with-expanded-budget automatically as its default behavior** — every real, named practice found here (Copilot's time-warning, MindStudio's "budget stopping" category, OpenHands' proposed-but-unshipped percentage warnings) converges on the same shape: **warn before the limit, then synthesize whatever is available**, not silent failure and not automatic retry.

## Summary — direct answers to the report's own framing questions

- **Is 25 too low, roughly right, or is a fixed small cap the wrong shape entirely?** Roughly right *as a routine default* (it matches Cursor's own standard-mode number exactly) but **the wrong shape as a single, undifferentiated number for this project's actual task mix** — real practice elsewhere (Claude Code's task-banded guidance, Cursor's 25-vs-200 tiers, OpenHands' 500-as-backstop) treats "routine ceiling" and "hard-task backstop" as two different numbers, and this project's own two real failures are exactly the population that falls into the gap between those two roles today.
- **Does real practice validate the synthesis-budget-reserve idea from `10-...md` Step 13?** **Yes, validated and refined, but incomplete on its own.** Real, independent practice (OpenHands #2406, GitHub Copilot's own shipped time-warning behavior, MindStudio's "budget stopping" category) converges on the same shape this project already drafted — warn before the hard limit, then synthesize partial findings rather than aborting silently. The real refinement worth adopting: percentage-based warnings (80%/95% of budget) rather than a fixed absolute turn count, since it generalizes automatically if this project moves toward angle 2's finding (a variable budget by task type).
- **What's missing from this project's own diagnosis, per real current research?** A **verifiable stopping criterion** for evidence sufficiency specifically (angle 3) — real 2026 research explicitly warns that a subjective "is this good enough" judgment call is the actual failure mode this project's Step 13 hit, distinct from and prior to the budget-exhaustion question. This project's persona currently has no such checkable rule; real practice suggests one is needed alongside, not instead of, the budget reserve.
- **How much of this space is genuinely opaque vs. documented?** More documented than the first pass of this research found. A follow-up pass — reading OpenHands issue #2406's real comment thread directly via GitHub's API, rather than relying on the rendered page — resolved both of the first pass's honest gaps: SWE-agent's real default (`mini-swe-agent`: 250 steps / $3 cost limit, with cost explicitly favored over steps) was found, and the "closed as not planned" mystery turned out not to be a mystery — a real fix was built and nearly merged (PR #2739), then went stale for non-technical reasons. The lesson generalizes: a rendered GitHub issue page can hide its own most useful content (the comment thread); the API is worth reaching for directly rather than trusting a page-level fetch/summary when the "why" behind a real decision matters.
- **Real, converging evidence on cost vs. turn-count as the more fundamental resource in 2026 practice**: SWE-agent's own explicit rationale ("step counts vary wildly across models... a $-per-task budget normalizes this") and Devin's ACU-based billing (no published turn cap at all) both point the same direction as the general 2026 industry trend already found (token/cost budgets, not turn counts, as the real production constraint). This project's own `maxTurns`-based cap (a Genkit mechanism) is a real, reasonable, common choice (Claude Code and Cursor both use the same shape), but is worth knowing it's the less-favored of two real, legitimate design philosophies found in this research, not the only one.
