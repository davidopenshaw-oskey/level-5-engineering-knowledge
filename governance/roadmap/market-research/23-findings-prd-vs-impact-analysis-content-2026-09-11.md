# Findings — What Real PRDs vs. Real Impact-Analysis Documents Actually Contain

Real research question: given the same underlying fact corpus, what should actually go *inside* a PRD versus an impact-analysis document — real sections, real content types, real differences between the two — not how the generation pipeline is wired (that question was already answered by `21-findings-agent-prd-template-vs-dynamic-structure-2026-09-09.md`). Findings from live web research, 2026-09-11. This is a synthesis of what real sources contain, not a recommendation for what this project should build — that is a separate, later decision.

---

## Q1: What do real, named companies/practitioners actually put in a PRD?

| Source | Sections (as published) | Mentions "impact analysis" / "affected systems"? |
|---|---|---|
| **Notion** (own help docs, [notion.com/help/guides/building-a-product-requirement-document-in-notion](https://www.notion.com/help/guides/building-a-product-requirement-document-in-notion)) | Core attributes named: Context, Goals/Requirements, Constraints, Assumptions, Dependencies | No. Explicitly states *"Ask 5 different people, and you'll get 5 different answers on what a PRD should include."* No fixed template asserted. |
| **Aha!** ([aha.io/roadmapping/guide/requirements-management/what-is-a-good-product-requirements-document-template](https://www.aha.io/roadmapping/guide/requirements-management/what-is-a-good-product-requirements-document-template)) | Overview, Objective, Context, Assumptions, Scope, Requirements, Design, Metrics, Open questions | Not as a named section. Step 8, "Consider impact," asks *"Are there known dependencies? What other areas of the product will this release affect? What level of ongoing maintenance will be needed?"* — folded into dependency/scope planning, not its own heading. |
| **Product School** ([productschool.com/blog/product-strategy/product-template-requirements-document-prd](https://productschool.com/blog/product-strategy/product-template-requirements-document-prd)) | Title, Change History, Overview, Success Metrics, Messaging, Timeline/Release Planning, Personas, User Scenarios, User Stories/Features/Requirements, Features Out, Designs, Open Issues, Q&A, Other Considerations | No. Attributed to named practitioners: Minal Mehta (Head of Product, YouTube) — PRDs as "living documents" — and Raja Mukesh Krishna Balakrishnan (Group PM, Flipkart) on common PRD pitfalls. |
| **Atlassian Confluence** ([atlassian.com/software/confluence/templates/product-requirements](https://www.atlassian.com/software/confluence/templates/product-requirements)) | PRD basics/team roles, Objective, Success metrics, Assumptions, Options, Supporting documentation, Open questions, Out of scope | No. |
| **Amazon — PR/FAQ ("Working Backwards")** (secondary-sourced: [workingbackwards.com](https://workingbackwards.com/concepts/working-backwards-pr-faq-process/), [hustlebadger.com](https://www.hustlebadger.com/what-do-product-teams-do/amazon-working-backwards-process/)) | A fundamentally different shape, not a variant of the User-Stories template: a mock press release (headline/subtitle/date/intro/solution paragraphs) plus **External FAQ** (customer/press-facing) plus **Internal FAQ** (anticipates hard questions from *every department* — a real, named company doing something structurally different from every other source here) | No "impact analysis" heading, but the Internal FAQ is the closest real analog to a cross-functional "who's affected, what could go wrong" section — expressed as anticipated Q&A, not a structured report. |
| **Jama Software** — regulated/traceability-oriented requirements management ([jamasoftware.com/requirements-management-guide/.../product-requirements-document/](https://www.jamasoftware.com/requirements-management-guide/writing-requirements/product-requirements-document/)) | Product Overview & Release Objectives, Functional Requirements & Use Cases, Non-Functional/System Requirements, Assumptions/Constraints/Dependencies | Explicitly **not** a PRD section here. Impact analysis is described as a separate, formal traceability practice: *"Live Traceability™ shows every linked test case, design element, and risk item that needs review"* when a requirement changes, gated by *"a formal change control process."* This is the one source that names impact analysis directly, and it deliberately keeps it outside the PRD, as a change-control artifact tied to a requirements-traceability matrix (relevant to regulated/aerospace/medical-device contexts more than typical SaaS product work, but a real, direct data point). |

**Real answer to the core question**: across every named source checked, **"impact analysis" or "affected systems" never appears as a PRD section heading.** It shows up, at most, as a sub-question inside a "dependencies"/"scope" section (Aha!), or is deliberately kept as a separate downstream artifact from the PRD entirely (Jama Software's traceability-driven change control). This project's current template (User Stories / Technical Proposal / Acceptance Criteria / Constraints) is missing, relative to the sources above: an explicit **Success Metrics** section (present in Product School, Aha!, Atlassian), an explicit **Open Questions** section (present in Notion, Aha!, Atlassian, Product School — and notably close to this project's own `[NEEDS CLARIFICATION]`-style honesty concern from `21-...md`), and an explicit **Out of Scope / Features Out** section (present in Atlassian, Product School). No source suggests the template is missing an impact-analysis section — the real, converging signal is that impact analysis belongs *outside* the PRD as its own thing, which is exactly the split this project's own ADR-006 §2b already anticipated independently, before this research ran.

## Q2: What does a real, named software-engineering "impact"/"change impact" document actually contain?

No single, real, named software-engineering document is *titled* "Impact Analysis" in the sources found — the real, concrete content lives inside adjacent, well-established document types instead. In descending order of how directly comparable the content is:

- **Kubernetes Enhancement Proposal (KEP) template** — fetched directly from source ([raw KEP template, kubernetes/enhancements](https://raw.githubusercontent.com/kubernetes/enhancements/master/keps/NNNN-kep-template/README.md)). This is the single most concrete, structured real example found for engineering-specific change-impact content. Full section list, in order: Release Signoff Checklist, Summary, Motivation, Goals, Non-Goals, Proposal, User Stories, Notes/Constraints/Caveats, **Risks and Mitigations**, Design Details, Test Plan, Graduation Criteria (Alpha/Beta/GA/Deprecation), Production Readiness Review Questionnaire — itself containing **Feature Enablement and Rollback**, **Rollout, Upgrade and Rollback Planning**, **Upgrade / Downgrade Strategy** (*"If applicable, how will the component be upgraded and downgraded?"*), **Version Skew Strategy** (*"how will the component handle version skew with other components?"*), **Monitoring Requirements**, **Dependencies**, **Scalability**, **Troubleshooting** — then Drawbacks, Alternatives. This is real, itemized, checklist-shaped impact content (rollback, dependency call-outs, who/what breaks under partial rollout) baked directly into an engineering proposal template, not treated as generic prose.
- **Michael Nygard's ADR template** — corroborated across multiple secondary mirrors of the original ([joelparkerhenderson/architecture-decision-record](https://github.com/joelparkerhenderson/architecture-decision-record/blob/main/locales/en/templates/decision-record-template-by-michael-nygard/index.md)). Real, minimal, freeform: a single **Consequences** section — *"What becomes easier or more difficult to do because of this change?"* — with no further structure. Real and widely adopted, but the opposite of the KEP's itemized checklist approach: one open question, not a taxonomy of impact types.
- **Google design docs** — fetched directly ([industrialempathy.com/posts/design-docs-at-google](https://www.industrialempathy.com/posts/design-docs-at-google/)), written by a named former Google engineer and widely cited as the closest public description of Google's real internal practice. Sections in order: Context and Scope, Goals and Non-Goals, The Actual Design, Alternatives Considered, **Cross-Cutting Concerns** — the closest analog found to an "impact"/"affected systems" section, explicitly for *"security, privacy, and observability"* concerns — plus a recommended **system-context-diagram** that *"shows the system as part of the larger technical landscape."* Confirmed against a second primary source, Google's own *Software Engineering at Google* book (Abseil-hosted, [abseil.io/resources/swe-book/html/ch10.html](https://abseil.io/resources/swe-book/html/ch10.html)): that chapter states Google's real internal templates *"require engineers to consider aspects of their design such as security implications, internationalization, storage requirements and privacy concerns"* but does not publish the template's literal section list — an honest gap, not filled in from the secondary source.
- **RFC templates** (Rust, fetched directly from [rust-lang/rfcs](https://github.com/rust-lang/rfcs/blob/master/0000-template.md); Uber H3, fetched directly from [uber/h3](https://github.com/uber/h3/blob/master/dev-docs/RFCs/rfc-template.md)) — weaker real precedent than KEP or Google's design docs. Rust's template has a **Drawbacks** section (*"Why should we not do this?"*) and folds impact-on-maintainability into the Guide-level-explanation section, but has no dedicated affected-systems/blast-radius section. Uber's H3 RFC template is thinner still — Summary/Motivation/Approaches/Proposal/Footer, with impact only implicit in Motivation. Real, but not strong evidence of a dedicated impact-analysis pattern.
- **Academic grounding for the term itself**: "change impact analysis" as a formal term originates with Robert Arnold and Shawn Bohner's 1996 book *Software Change Impact Analysis* (found via search snippets and secondary academic citations, not the book itself, which is not available online — an honest gap). Their definition: *"identifying the potential consequences of a change or estimating what needs to be modified to accomplish a change,"* framed as a **change-set → impact-set** computation, not a document-authoring problem. This matters directly for this project's framing: the term's own academic origin treats impact analysis as an algorithmic/structural output (a set of affected elements), not primarily a narrative report — which lines up with Q3's finding below.
- **Honest negative**: generic "change impact assessment" business-change-management templates (OCM Solution, ProjectManager.com, and similar listicle sites) turned up repeatedly in search but were not fetched as primary sources — they describe generic organizational-change impact (people/process/systems/training/communications), not software-specific blast-radius content, and read as SEO-oriented listicles rather than named practitioner sources. Excluded from the real findings above for that reason, matching `21-...md`'s own sourcing bar.

## Q3: Real precedent for a document mostly derived from a dependency/call graph rather than freeform narrative

**Yes — but the real precedent is a live, tool-generated report or CI annotation, not a standalone written document**, which is itself a significant, honest finding worth stating plainly (see below).

- **Nx `affected`** — fetched directly ([nx.dev/docs/features/ci-features/affected](https://nx.dev/docs/features/ci-features/affected)). Purely structural: maps changed files to projects, walks the project graph to include dependents, and outputs a filtered project/task list — with `nx graph --affected` for a visual rendering and JSON export for programmatic use. No narrative prose in the core output; this is the cleanest real example of "impact = graph traversal, full stop."
- **Bazel `query rdeps`** — fetched directly ([bazel.build/query/guide](https://bazel.build/query/guide)). `rdeps(u, x)` computes reverse dependencies within a transitive closure, explicitly framed by Bazel's own docs around the impact-analysis question *"if you're going to change some code, you might want to know what other code you're about to break."* Output is a plain list of target labels — again, no narrative layer by default.
- **Terraform "blast radius" (Overmind)** — fetched directly ([overmind.tech/blog/difference-terraform-plan-and-overmind-blast-radius](https://overmind.tech/blog/difference-terraform-plan-and-overmind-blast-radius)). The most directly relevant real precedent for *this project's specific ambition* (graph-derived structure plus a synthesized narrative layer on top, delivered as a document/PR comment rather than just a CLI list): Overmind builds a dependency graph, then adds a **risk-scoring layer** and **"human-readable risk assessments"** on top of it, delivered as a GitHub PR comment. This is real, named, concrete evidence that "mostly graph, with a thin synthesized narrative layer" is a shipped pattern elsewhere — though for infrastructure-as-code, not application code.
- **CodeScene "change coupling"** — a different but related real mechanism: derives affected-together files from *git commit history co-occurrence* rather than a static call graph, and explicitly works across repository boundaries ([codescene.com/blog/change-coupling-visualize-the-cost-of-change](https://codescene.com/blog/change-coupling-visualize-the-cost-of-change)). Relevant as an alternate, real, non-LLM signal source for "what's likely affected," complementary to this project's static-analysis-derived `cross_repo_edges`, not a substitute for it.
- **GitHub Dependency Graph / Dependabot** — real precedent for graph-derived "affected repositories" detection at scale, though for the different domain of supply-chain vulnerability propagation rather than internal call-graph impact ([docs.github.com — dependency graph](https://docs.github.com/code-security/supply-chain-security/understanding-your-software-supply-chain/about-the-dependency-graph)).

**Honest negative result, stated plainly**: no real, named example was found of a **written, narrative "impact analysis document"** (the document-shaped artifact this project's own task framing assumes) generated primarily from a call/dependency graph. Every real precedent found is a **live, embedded, structural artifact** — a filtered project list (Nx), a target-label list (Bazel), a CI/PR-comment risk annotation (Overmind) — not a standalone document a person reads the way they'd read a PRD. This is a real, worth-recording finding for this project specifically: the graph-driven precedent that exists in the wild argues for impact-analysis output looking more like a **structured report or PR annotation with a thin narrative layer** (closest real analog: Overmind's blast-radius pattern) than like a freeform document matching the shape of a PRD. That's a genuine content-shape difference between the two document types this research was asked to compare, not just a difference in section headings.

## Q4: Sourcing rigor

Directly fetched and read in full (primary sources): Notion's own PRD help guide, Aha!'s PRD template guide, Product School's PRD template article, Atlassian's Confluence PRD template page, Jama Software's PRD/requirements-management guide, the Kubernetes KEP template (raw source file), Michael Nygard's ADR template (mirrored raw source file), the Rust RFC template (raw source file), Uber H3's RFC template (raw source file), "Design Docs at Google" (industrialempathy.com), Google's own *Software Engineering at Google* book chapter 10 (abseil.io), the Overmind blast-radius blog post, and Bazel's official query guide.

Secondary/aggregated or explicitly weaker: the Amazon PR/FAQ section (multiple secondary write-ups — [workingbackwards.com](https://workingbackwards.com/concepts/working-backwards-pr-faq-process/), [hustlebadger.com](https://www.hustlebadger.com/what-do-product-teams-do/amazon-working-backwards-process/) — not Amazon's own internal template, which isn't public); the Arnold/Bohner 1996 definition (sourced from search snippets and secondary academic citations, the original book is not available online); CodeScene's change-coupling description (vendor blog, not independently verified against a real customer report). Reforge's "7 PRD templates" article returned HTTP 403 and could not be fetched directly — excluded rather than guessed at. Generic organizational-change-management "impact assessment" templates (OCM Solution and similar) were found repeatedly in search but deliberately excluded from the findings as low-rigor SEO listicles, not real named practitioner or company sources — flagged here as a genuine negative result (Q2) rather than padded into the findings.

## Bottom line

1. **No real source puts "impact analysis" inside a PRD as a named section.** It appears, at most, as a sub-question under scope/dependencies (Aha!), or is deliberately kept as a wholly separate downstream artifact from the PRD (Jama Software's traceability-driven change control) — independently corroborating the split this project's own ADR-006 §2b already proposed.
2. **Real software-engineering impact content is itemized and checklist-shaped where it's taken seriously** (Kubernetes KEPs: rollback, upgrade/downgrade, version skew, monitoring, dependencies, scalability), not a single freeform prose section — Nygard's ADR "Consequences" and Google's "Cross-cutting concerns" are the freeform-prose end of the same spectrum, and are visibly thinner as a result.
3. **The strongest real precedent for graph-derived impact content is a live structural artifact (a filtered list, a PR annotation with light narrative), not a standalone written document** — this is a genuine, honest negative result that bears directly on how this project should think about impact-analysis output shape, not just its section headings, once that becomes a design decision (out of scope for this task).
