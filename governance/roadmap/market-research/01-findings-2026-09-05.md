## 1. Grounding/retrieval architecture

**Found:** The 2026 commercial and academic consensus has moved decisively away from "pure dense-vector RAG" for code, toward hybrid lexical + dense + graph retrieval:

- **Sourcegraph Cody** shifted away from its original embeddings-only backbone toward a hybrid of its Search API and code-graph context — "embeddings have been at the backbone of Cody's retrieval stack since the product launched in beta, and now that Cody Enterprise is generally available, they're leaving them behind (for now)" ([Sourcegraph blog](https://sourcegraph.com/blog/how-cody-understands-your-codebase); [Augment Code comparison](https://www.augmentcode.com/tools/sourcegraph-cody-vs-continue-enterprise-comparison)).
- **Augment Code's Context Engine** and its **Claude Context MCP server** explicitly combine BM25 sparse lexical matching with dense vector search, "treating code as a semantic graph rather than text collections" ([augmentcode.com/context-engine](https://www.augmentcode.com/context-engine); [Claude Context MCP](https://www.augmentcode.com/mcp/claude-context-mcp-server)).
- **LARGER** (arXiv 2605.16352, 2026) is an academic framework built specifically because "existing agents navigate repositories primarily through lexical search, often missing structural relations such as imports, call chains, type hierarchies" — it anchors lexical matches to a graph and does confidence-filtered local expansion, gaining +11.8 to +13.9 points of localization accuracy over the strongest baseline ([arxiv.org/abs/2605.16352](https://arxiv.org/abs/2605.16352)).
- **Citation-Grounded Code Comprehension** (arXiv 2512.12117, Dec 2025) directly measured this project's own failure mode: across 30 real repos and 180 developer queries, "cross-file evidence discovery is the largest contributor to citation completeness, but it is largely overlooked because existing systems rely on pure textual similarity without leveraging code structure." Their fix — BM25 + dense embeddings + Neo4j graph expansion via import relationships — beat single-mode retrieval by 14-18 points and recovered cross-file evidence missed by pure text similarity in 62% of architectural queries, reaching 92% citation accuracy with zero hallucinations ([arxiv.org/abs/2512.12117](https://arxiv.org/abs/2512.12117)).
- General 2026 RAG literature confirms the underlying tension this project found by hand: "the failure point is almost always the retrieval," bi-encoder embeddings are lossy by design, and graph-based RAG reports up to 35% precision gains over vector-only retrieval ([turingpost.com/p/ragtypes](https://www.turingpost.com/p/ragtypes); [edge-ai-vision.com](https://www.edge-ai-vision.com/2026/02/a-practical-guide-to-recall-precision-and-ndcg/)).

**Verdict: Confirms the architecture, but flags a concrete, actionable gap.**

The three-way split in ADR-005 (graph traversal for impact analysis, retrieval-over-facts for PRD scoping, narrative synthesis for sanity reports) matches where the field has actually converged in 2026 — not a niche choice. The recall-vs-precision problem `15-workflow-clustering-and-angular-ux-facts.md` found by hand (the right fact existing in the index, ~24 near-identical `TypeName.inhabitantType` facts, but not reliably ranking in the top-10/25) is the *exact* problem the Citation-Grounded Code Comprehension paper and LARGER were built to solve, and both papers' fix is not "better embeddings" but **adding a second, non-embedding retrieval channel** (BM25 sparse lexical + graph expansion via real structural edges), not relying on cosine distance alone.

The real, concrete gap: this project's retrieval today is pure pgvector dense-vector search (per ADR-005/`15-...md`). None of the fixes tried so far (the `model_property` description enrichment, raising `RESULT_LIMIT`) add a second retrieval channel — they all still operate purely on embedding distance. The two most directly comparable real systems found this session (Augment's Claude Context, the Citation-Grounded paper) both report meaningful gains specifically from adding BM25/sparse keyword matching alongside dense vectors. Given this project's own near-duplicate problem is fundamentally lexical (many `TypeName.inhabitantType` facts differing mainly in `TypeName`, a token BM25 would weight much more heavily than a dense embedding does), prototyping a hybrid BM25+pgvector retrieval pass is a concrete, evidence-backed next experiment worth running before investing further in Task 1's workflow clusters as the sole fix for Q1b's still-open gap.

## 2. Human-in-the-loop discipline

**Found:** "Human-in-the-loop" (HITL) is a real, named, actively-documented 2026 industry pattern, not an ad hoc habit: "people reviewing, correcting, or approving the AI's output before anything moves forward," with review gates at defined checkpoints before AI output takes effect ([Velt, May/June 2026](https://velt.dev/blog/human-in-the-loop-ai-review-layer); [Neotalogic](https://www.neotalogic.com/blog/human-in-the-loop-ai)). It's also now a regulatory requirement, not just a best practice: the EU AI Act's Article 14 mandates human oversight for high-risk AI systems starting in 2026, with 700+ U.S. bills pushing the same direction; cited accuracy differences are stark — "human review workflows achieve 99.9% accuracy compared to 80% for fully automated AI systems" (same Velt source).

**Verdict: Confirms the general shape; this project's specific variant is more rigorous than what was found, not behind it.**

"AI drafts, human confirms before it's trusted" is a real, named, increasingly regulation-backed pattern in 2026 — this project's Step 6 human-review gate in `01-workflow-seeding-tasklist.md` is squarely within that norm, not an outlier. No source found describes a pattern as specific as this project's own discipline — constraining the LLM's draft to *only* reason over a pre-assembled, graph-connected fact cluster, never open-ended reasoning over code or docs (`01-workflow-seeding-tasklist.md` Step 4). Generic HITL examples found (fraud detection, clinical triage, content moderation) gate the AI's *output*, but don't describe constraining the AI's *input* to a verified evidence set the way this project does. That's not a gap — it means this project's grounding discipline is ahead of, not merely consistent with, common HITL practice as described in the sources found.

## 3. Staleness/freshness over time

**Found:** Documentation drift is now a named, tooled 2026 problem category, not a hypothetical: "AI-assisted development makes documentation staleness worse... GitHub saw 986 million commits in 2025, meaning more commits result in more drift, faster" ([Atlan, Context Drift Detection guide, 2026](https://atlan.com/know/context-drift-detection/)). Concrete tools doing exactly "flag drift after code changes" exist right now:

- **drift-vscode**: "code-documentation governance engine using AST analysis to mathematically enforce sync between code and docs" ([GitHub](https://github.com/pallaprolus/drift-vscode)).
- **fiberplane/drift**: "bind specs to code and check for drift" ([GitHub](https://github.com/fiberplane/drift)).
- **CAI Drift Check**: a Claude Code skill that "scans your codebase and specs to ensure AI context stays synced with code changes, automatically scanning documents and comparing metadata against Git commit history... markdown files can declare anchors to code, and when bound code changes, drift check flags the doc as stale" ([mcpmarket.com](https://mcpmarket.com/tools/skills/cai-drift-check)).
- **Swimm**: documentation that "lives next to the code and updates when the code changes," auto-generating PR summaries and re-syncing on change ([moge.ai](https://moge.ai/product/swimm); [Info-Tech](https://www.infotech.com/videos/swimm-how-ai-is-used-in-documenting-code)).

A second, distinct pattern also exists in 2026 — regenerate-from-spec rather than maintain-and-flag: "OpenAPI reference pages regenerate when a spec changes, closing the drift problem more completely than most alternatives" ([Mintlify, best-code-documentation-tools 2026](https://www.mintlify.com/library/best-code-documentation-tools)).

**Verdict: Confirms — real, current 2026 precedent exists for exactly this project's "refresh after merge, flag drift, prompt a human" direction.**

drift-vscode and CAI Drift Check are doing, right now, almost exactly what Task 2 of the workflow catalogue (not yet sketched) intends: bind a piece of documentation to real code/facts, detect when the underlying code changed, and flag rather than silently trust. This is a live, real, currently-built category, not speculative. Worth noting as a genuine nuance rather than a gap: the industry also has a second, structurally simpler pattern — regenerate-on-demand from a machine-checkable spec (OpenAPI) — that this project's narrative workflow catalogue can't fully adopt, because a `workflow_cluster`'s human-authored name/purpose and its `human_asserted_out_of_system` steps have no spec to regenerate *from*; only the fact-derived evidence underneath them does. That's a real, structural reason this project's fact_ids-and-commit-SHA staleness design (`01-workflow-seeding-tasklist.md` Step 7) is the more applicable of the two real 2026 patterns for this specific content, not a shortfall relative to the simpler alternative.

## 4. Trust/provenance labeling

**Found:** Provenance labeling is a real, fast-moving, but largely *media-and-compliance*-focused space in 2026, not an internal-engineering-tooling one:

- The **EU AI Act's Article 50** requires labeling AI-generated content starting August 2, 2026, and the **C2PA "Content Credentials"** standard is real and adopted — described as "a nutrition label for digital content" ([pandectes.io](https://pandectes.io/blog/labeling-ai-generated-content-what-the-new-rules-require/); [OpenAI, Advancing content provenance](https://openai.com/index/advancing-content-provenance/)).
- At the code-attribution granularity closer to this project's concern, the space is described as immature and actively contested: Microsoft's VS Code briefly made Git append a Copilot co-author trailer to commits by default in April 2026, which was reversed after backlash in May 2026 — "AI attribution via the Co-authored-by trailer lacks the granularity required to distinguish between minor inline completions and substantial agentic contributions" ([Windows Forum](https://windowsforum.com/threads/vs-code-copilot-co-author-trailer-backlash-ai-provenance-opt-out-restored.416417/); [thecodersblog.com](https://thecodersblog.com/github-commit-message-standards-for-ai-assistance-2026/)).
- One real, closely analogous product does exist: **Exceeds Ink**, "an on-machine provenance layer that writes a portable, line-level attestation alongside every commit, capturing tool, model, session, interaction mode, and token cost across Claude Code, GitHub Copilot, Cursor, Codex, and Windsurf" ([penligent.ai](https://www.penligent.ai/hackinglabs/vs-code-copilot-co-author-when-ai-attribution-becomes-a-supply-chain-trust-problem/)) — a real, per-artifact trust-tier tag, though for code commits, not product documentation.
- No source found describes a documentation or PRD-generation tool exposing a visible AI-generated-vs-human-verified distinction to its end users the way this project's `generationMethod`/`evidence_basis` fields do (Mintlify's own docs, checked directly, describe citation-backed AI answers but no verified/unverified badge system).

**Verdict: Flags a real gap, not a confirmation.**

Broad regulatory/media provenance standards (C2PA, EU AI Act) exist and are real, but they target public-facing generated content (misinformation risk), not internal engineering-knowledge trust tiers. At the granularity this project actually needs — is this specific claim/fact/step AI-drafted or human-confirmed — the nearest real-world analog (Copilot's commit co-author trailer) is itself contested and was rolled back for being too coarse-grained to be trustworthy. This project's `generationMethod: llm_drafted_human_confirmed` / `evidence_basis: fact_derived | human_asserted_out_of_system` design is more precise than anything found in the market — a genuine finding worth taking seriously in both directions: it means there's no existing standard to borrow or benchmark against (real design risk, no proof-of-concept to validate the UI/UX of surfacing this to a PM), but also that this project would be ahead of, not behind, current practice if it ships this well.

## 5. Content that can't be grounded in code at all

**Found:** This exact concept — a workflow step performed by a human with no application or engine trace — is not new or AI-specific; it's a decades-old, standardized primitive in Business Process Model and Notation (**BPMN**): the **Manual Task**, defined as "a Task that is performed without the aid of any business process execution engine or any application... such as a telephone technician installing a telephone at a customer location" ([Visual Paradigm](https://skills.visual-paradigm.com/docs/bpmn-fundamentals-for-beginners/bpmn-process-modeling/bpmn-task-types-manual-service-user/); [Flowable docs](https://documentation.flowable.com/latest/reactmodel/bpmn/reference/manual-task)). BPMN even distinguishes it precisely from a **User Task** (human acting through a system interface) — the same distinction this project's `fact_derived` (code-backed, even a UI form binding) vs. `human_asserted_out_of_system` (a verbal handover, a signed contract) split is drawing, independently.

Separately, process-mining tooling (Celonis, the market leader) structurally confirms the same boundary from the opposite direction: it "reconstructs processes from the transaction data that enterprise resource planning (ERP) and customer relationship management (CRM) systems already store" — meaning by construction it can only ever see system-touching steps, and real practitioners keep automated discovery and manual process mapping as separate, explicitly distinguished inputs rather than pretending mined data covers everything ([Celonis blog](https://www.celonis.com/blog/automated-process-discovery)).

No AI-native PRD/workflow-documentation product was found that has built an explicit equivalent for this — the concept exists in classic BPM tooling, not in the AI-PRD-generation product category this project otherwise sits in.

**Verdict: Confirms the concept is real and well-precedented, but flags that this project is applying an established BPM idea to a genuinely underserved intersection.**

This is good news framed honestly: `human_asserted_out_of_system` is not a novel or fragile invention — it's structurally identical to BPMN's 20+-year-old Manual Task vs. User Task distinction, a validated, well-understood modeling primitive. The real, concrete recommendation this finding supports: consider aligning this project's terminology/documentation to BPMN's existing vocabulary (Manual Task) rather than inventing parallel language, since it's a known concept a wider audience (including any future PM/PO reviewer) may already recognize. The genuine gap is that no AI-native, code-grounded PRD tool was found doing this — this project would be first-of-kind in that specific combination (AST-fact-grounded retrieval + BPMN-style manual-task tagging), not adopting a proven AI-industry pattern.

## 6. The product-facing trigger interface (ADR-006's open question)

**Found:** This is the angle with the strongest, most directly load-bearing real precedent found this session — multiple live 2026 products implement almost exactly the shape ADR-006 §2b speculates about (a natural-language business request dispatched to a template/rules/task combination):

- **Atlassian Rovo** has a shipped, GA (2026) "**Product Requirements Guide**" agent for PMs, and its general agent-building flow explicitly starts with "choosing a trigger that selects what starts the agent (a Jira event, a scheduled run, a Chat invocation, or a manual request)"; agents can be "assigned work, mentioned in comments, and embedded into Jira workflows" ([Atlassian support docs](https://support.atlassian.com/rovo/docs/atlassian-agents/); [aiotests.com](https://www.aiotests.com/blog/rovo-agent-jira-ai-transformation); [tryprotege.com](https://www.tryprotege.com/blog/atlassian-rovo-complete-guide)).
- **ChatPRD**, a dedicated AI copilot for PMs, is reachable via chat, Slack (quick messages, proactive updates), and MCP integration directly into IDEs (Cursor, Claude Desktop, VS Code) — "querying the codebase or logs for error frequencies to answer PMs' questions with precision," and can "push finished PRDs to Linear as tickets" ([chatprd.ai/product/mcp](https://www.chatprd.ai/product/mcp); [chatprd.ai/learn/ai-agents...](https://www.chatprd.ai/learn/ai-agents-product-management-integrations-tools)).
- MCP itself is the real, live connective layer enabling both — the same protocol this project's own pipeline scripts would plausibly need to expose behind (ADR-006 §2a's "typed interface" gap).

**Verdict: Confirms strongly — this is directly load-bearing, not just reassuring.**

ADR-006 explicitly frames the trigger question as open and names Gemini Enterprise only as an unverified hypothesis. Rovo's "choose a trigger: Jira event / scheduled run / chat invocation / manual request" model is a real, shipped, productized version of exactly the dispatch layer ADR-006 sketches (template + rules + task-definition), and it's vendor-agnostic proof the pattern works in production, not merely plausible. Concrete, actionable follow-up this finding supports: study Rovo's five-step agent-build flow and ChatPRD's MCP integration model directly as reference architectures before ADR-006's "typed interface" work (§2a) is scoped, since both already solve the "how does a business request reach a backing pipeline" problem this project has not yet designed.

## 7. Multi-repo, partial-coverage reality

**Found:** Both commercial products and independent best-practice guidance treat partial/incremental multi-repo coverage as the normal, expected shape of a real rollout, not an edge case:

- **Augment Code** processes "400,000-500,000 files across multiple repositories" with a context engine designed for that scale ([augmentcode.com](https://www.augmentcode.com/tools/13-best-ai-coding-tools-for-complex-codebases)); **Sourcegraph Cody**'s multi-repo indexing runs "in the background without blocking development work," explicitly supporting incremental onboarding rather than requiring a complete corpus upfront ([theroadtoenterprise.com](https://theroadtoenterprise.com/blog/onboarding-to-new-codebase-with-ai-tools)).
- Independent enterprise knowledge-graph guidance states the rollout best practice directly: "pulling data from multiple sources at once creates a fragile rollout; a more reliable approach connects one or two high-value sources first, validates accuracy, and then layers in additional systems over time" ([Actian, knowledge-graph guide 2026](https://www.actian.com/knowledge-graph/)) — this matches, almost verbatim, this project's own real sequencing (Firebase → Angular → node-iot, PGO-scoped POC first, per `01-qa-vision-and-examples.md` C1/C2).
- A real, sobering counter-data-point also surfaced: "fewer than 15% of enterprises [move] beyond pilot stage" on enterprise knowledge graphs, with most stalling on "ontology design, entity resolution accuracy, or query performance at scale," and "if source data is incomplete, outdated, or inaccurate, the Knowledge Graph will reflect these deficiencies" ([Promethium buyer's guide 2026](https://promethium.ai/guides/enterprise-knowledge-graph-buyers-guide-2026/)).

**Verdict: Confirms the approach, with one real, honest caution attached, not just "seems fine."**

The project's own repo-by-repo, PGO-scoped rollout (explicit in `01-qa-vision-and-examples.md` C1/C2: prove TypeScript repos first, then interfaces, then extend to mobile/Kotlin/Swift/hardware repos) matches current, explicit 2026 best-practice guidance, not an improvised workaround for being behind schedule. The real concern worth carrying forward, not glossed over: the <15%-past-pilot statistic and the "garbage in, garbage out" warning are a genuine base-rate risk for *any* project in this category, this one included — the memory note that "most 'missing' cross-repo data is already loaded/embedded, just under-described" (ADR-005 session, per project memory) is a positive sign against that base rate, but the entity-resolution/ontology-design failure mode named in the source (e.g., this project's own 42-symbol cross-repo type-mirroring ambiguity found in `15-...md`) is exactly the kind of problem cited as where most such efforts stall — worth treating as a real, live risk to actively manage, not a solved problem.
